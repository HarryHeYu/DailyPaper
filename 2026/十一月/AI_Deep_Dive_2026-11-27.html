2. 一句话定位

预训练视频 VAE 的有效感受野其实很局部；用因果窗注意力（CWA）重写成流式编解码器，再经三阶段蒸馏保住原潜空间，从而在不重训扩散主干的前提下同时加速编码与解码。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

3. 人话版

现在很多视频生成模型已经能“边出边看”，但把像素压进潜空间、再从潜空间解出来的视频 VAE，往往还在用很重的卷积或整帧注意力。编码端尤其被忽略，于是参考视频条件生成、流式编辑这类必须先编码的路径，会被 VAE 卡住。这篇论文先做了一个很具体的检查：已有视频 VAE 在编、解码一个图块时，梯度能量几乎都落在它的时空邻居上——空间上 7×7 邻域就能覆盖 95–100% 的梯度能量（Fig. 2）。既然并不真的需要全局建模，就把注意力限制在当前及之前若干潜帧的局部窗口里，并用滚动 KV cache 做流式推理。为了能直接替换官方 VAE，他们先分别蒸馏编码器和解码器，再联合微调。主结果在 MiniMax-H3 上：相对官方 VAE，编码快 5.2–6.2 倍、解码快 3.0–3.3 倍，而且 PSNR 还略高（Table 1）。再加上算子融合、分区编译和（仅在 1080p/2160p 启用的）FFN FP8，端到端加速被说到“至多 13.4×”。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

4. 背景与缺口

视频扩散模型由 VAE 与扩散/DiT 两部分组成。近年来采样步数和 DiT 注意力都被大幅加速，VAE 反而变成交互式生成和编辑的主要时延来源。已有加速路线多半只改解码器，编码器仍走官方权重，于是“先编码再生成”的流式条件任务受益有限。另一类工作用 KV cache 做因果注意，但仍在整段潜变量上计算，代价随帧数二次增长。缺口因此很清楚：需要一种同时覆盖编码与解码、缓存有界、并且能插入现有潜空间的流式 VAE。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

5. 核心 insight

视频 VAE 看起来像全局模型，有效感受野却是局部的。只要把注意力限制在大小为 T×H×W 的因果窗，计算量从与全部时空 token 相关变成与窗口大小相关，KV cache 也只要保留 T−1 帧。第二层 insight 是：要保住“即插即用”，必须先把学生编码器对齐教师潜空间，再让解码器适应学生潜变量，而不是一上来端到端对打。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

6. 方法逐步拆解

教师 VAE 的时间、空间压缩比为 M、S。输入视频 x∈ℝMf×Sh×Sw×3 被编成 z∈ℝf×h×w×C。学生编码器 ES 与解码器 DS 在 f×h×w 潜网格上操作，token 索引为 i=(t,y,x)。

因果窗注意力（CWA）。对 token i，窗口 W(i) 包含满足 0≤t−τ<T 且空间距离不超过 (H−1)/2、(W−1)/2 的邻居（奇数窗、边界向内平移而不补零）。在至多 THW 个 token 上做标准缩放点积注意力，并对 query/key 施加与基础 DiT 对齐的 3D RoPE。为了调用成熟的二维邻域注意力核，窗口按潜帧切开：先在每一帧做 2D 窗注意力得到 Oτ(i) 与 log-sum-exp Lτ(i)，再按权重合成 3D CWA。推理时每块维护滚动 KV cache：算完当前帧就写入，并丢掉 t−T+1 帧，缓存长度有界。复杂度为 O(nTHW)，n=fhw。

网络。编、解码器都是 L=12 个 CWA 块。H3 的隐维分别是 2048 与 2560，Wan2.2 是 2560 与 2496；注意力头维 d=64。默认窗为 2×7×7。H3 学生总参数 2.08 B，低于教师 2.60 B（Table 1）。

三阶段蒸馏。Stage 1（80k step）只训编码器：潜空间 ℓ2 + 后验 KL，外加经冻结教师解码器回打的重建损失。Stage 2（200k step）只训解码器：教师编码器出潜变量，学生对像素。Stage 3（5k step）联合微调，并加 Real-ESRGAN U-Net 判别器的对抗损失；权重保持 EMA（decay 0.999）。像素重建始终是 ℓ1 + λp LPIPS。

推理栈（第 3.4 节）。A：注意力算子融合；B：分区编译；C：除解码器最后一块外的 FFN 做 FP8，并用与部署一致的伪量化做 QAT。EMA 权重只在 FP8 下使用。Table 1 写明 FP8 仅用于 1080p 与 2160p。学生与教师的潜变量通道数保持一致，空间压缩比同样是 16，所以现有 MiniMax-H3 或 Wan2.2 的 DiT 不需要改输入形状。流式路径按潜帧推进：编码端吃进一个时间块（H3 对应若干像素帧），写出一帧潜变量并更新 cache；解码端每次只读当前潜帧加上至多 T−1 帧的历史 key/value，再写出对应像素块。这使交互式编辑可以在“新帧到达”时只做增量编解码，而不必重跑整段视频。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

7. 核心公式

因果窗（内部位置、奇数窗）为

W(i)={(τ,y′,x′):0≤t−τ<T, |y′−y|≤(H−1)/2, |x′−x|≤(W−1)/2}

窗口内的 CWA 即

CWA(i)=∑j∈W(i)exp(qikj⊤/d)∑m∈W(i)exp(qikm⊤/d)vj

重建损失与三阶段目标为

ℒrec(x,x^)=‖x−x^‖1+λpLPIPS(x,x^)
ℒE=ℒlat+ℒrec(x,DT(zS)),ℒlat=λz‖zS−z‖22+λKLDKL(qS(z∣x)‖qT(z∣x))
ℒD=ℒrec(x,DS(ET(x))),ℒjoint=ℒlat+ℒrec(x,DS(zS))+wℒG(DS(zS))

默认权重为 λp=0.33、λz=1.0、λKL=10−3、λadv=0.1（第 4.1 节）。直觉：窗约束把全局注意变成局部因果聚合；ℒlat 把学生钉在教师潜空间里，对抗项只在联合阶段用来补感知细节。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

8. Toy example

以下为本文自造算例，数字不是论文结果，只用来说明窗口与 cache 如何工作。

假设潜网格为 f=4 帧、每帧 3×3 个 token，窗为 T=2、H=W=3。看第 3 帧中心 token：它只能看见第 2、3 帧里自己周围最多 9 个位置，总共不超过 18 个 key，而不是全部 4×9=36 个 token。流式走到第 4 帧时，cache 丢掉第 2 帧、写入第 4 帧，驻留仍是 2 帧。若有人误以为“窗越大越好”，可以把 T 加到 4：计算和 cache 都近似翻倍，但若感受野本来就在 2 帧内，PSNR 可能几乎不动——这正是 Table 11 想检验的事情。来源：abs · pdf · html · 项目页 livevae.github.io（文中给出，检索时未独立核验仓库状态）

10. 实验设置

  • 视频 VAE 的有效感受野高度局部：空间 7×7 可覆盖 95–100% 梯度能量。

论文 2｜Maco-RL：用混合任务强化学习直接扩展 agent 能力 NEW Reinforcement Learning

1. 基本信息

标题：Maco-RL: Scaling Agent Capabilities with Mixed-Task Reinforcement Learning。作者：Jiacheng Zhang、Qixing Zhou（共同一作），Haiyang Wang、Qipeng Gu、Shuzhe Wu、Feiyang Pan、Lue Fan、Dandan Tu、Zhaoxiang Zhang。单位：中国科学院自动化研究所、华为技术有限公司。arXiv：2611.34703。主类 cs.LG。提交时间 2026-11-25 16:59:27Z（约 2026-11-26 00:59 Asia/Shanghai），列入今日公布的周四批次。34 页，16 张表，非 BACKFILL。方向：Reinforcement Learning（LLM/Agent MixRL）。代码 Not Reported。训练加速器型号 Not Reported。训练基于 verl，环境在 Kubernetes 管理的 Docker 容器中运行。PDF 共 2,727,781 字节，arXiv HTML 可访问。Qwen3.5-27B 分 S1/S2 两阶段逐步加入任务类型；Qwen3.8-27B 则在单一阶段从一开始就同时使用全部四类任务。来源：abs · pdf · html

2. 一句话定位

不把各域专家再蒸馏回一个模型，而是在同一个策略上直接做混合任务强化学习（MixRL），用异步 rollout、梯度混合和 Tri-Buffer Sampling（TBS）在增加任务实例与任务类型时保持稳定与可扩展。TBS 把采样预算按 20%、60%、20% 分给 Frontier、Reinforcement 与 History；Claw 因存在部分奖励，不走 TBS 而改均匀采样。来源：abs · pdf · html

3. 人话版

训练能修代码、能操作终端、能做办公自动化、还能按需求文档开发新功能的 agent 时，常见做法是每个任务训一个专家，再想办法合并。MixRL 想走一条更直的路：一个策略同时在多种任务上做强化学习，并在训练中途把新任务加进来。这很诱人，也很容易翻车——任务时长差很多，异步 rollout 会过时，交替更新会让策略在任务间来回漂，稀疏奖励下反复采样永远失败的题还会浪费大量零优势更新。Maco-RL 的对策分三层。第一，rollout 和训练解耦，每个更新都按定额混入所有任务（他们称为梯度混合）。第二，用 TBS 把题目分进三个池：还没做对过的 Frontier、偶尔做对但还不稳的 Reinforcement、以及旧阶段的 History。第三，分两阶段扩展：S1 先训三类任务，S2 从该检查点继续，加入功能开发并扩大旧池。主表上，Qwen3.5-27B 的 Overall 从 43.6 走到 S2 的 60.1，超过 Qwen3.6-27B 的 49.8；Qwen3.8-27B 从 61.4 走到 67.0（Table 1）。值得先记住一个读表顺序：先看 Overall，再立刻回头看 SWE 与 FeatureBench，以及 Table 13 的置信区间。否则很容易把 Claw-Anything 从 12.0 到 64.6 的跃升，误当成五个基准同步变强。S1 在 FeatureBench Tests Passed 上从 37.9 掉到 28.6，说明“先扩展再补回来”是真实发生过的，而不是平滑曲线。来源：abs · pdf · html

4. 背景与缺口

Agent 强化学习已经能在 SWE-bench、终端基准等单域上取得进展，但能力扩展往往依赖“分域训练 + 事后合并”。多任务 RL 文献讨论过梯度冲突与调度，可对长程、稀疏奖励、工具调用的 agent 来说，真正卡住的常常是：异构任务的 rollout 时间差、异步策略滞后，以及增量加入新任务时旧能力回退。论文认为，在这种设置下，控制策略漂移比单纯缓解目标冲突更紧迫。缺口就是一套能直接、持续、稳定地在混合任务上做 RL 的训练框架，而不是再做一个新的 agent 脚手架。和训练一个更强的单域 SWE agent 不同，这里的难点是异构任务要在同一组参数上共存：终端任务步数短、SWE 轨迹更长、功能开发又会在 S2 才出现。如果框架不能在中途加任务，所谓持续扩展就只能停下来重新做混合或蒸馏。来源：abs · pdf · html

5. 核心 insight

两件关键判断。其一，每个更新都混合所有任务，比按任务交替更新更能抑制异步训练中的策略漂移；消融里交替更新会在 S2 第 25 步把奖励打到 0，并出现工具调用失败（Figure 7）。其二，稀疏奖励下“从未成功”的题目产生不了 GRPO 风格的非零优势，所以采样预算必须被显式切开：一部分继续探索，一部分强化刚会但还不稳的题（成功率为 0.25 附近的高斯权重），一部分回放旧任务。来源：abs · pdf · html

6. 方法逐步拆解

任务与两阶段。共享策略覆盖四类任务：代码修复（SWE 风格）、终端操作（Terminal-Bench 风格）、办公自动化（Claw 风格），以及按产品需求文档做跨文件功能开发（CodeWorld / FeatureBench）。S1 只训前三类；S2 从 S1 检查点继续，扩大旧池并加入功能开发（Figure 2）。

异步混合训练。Rollout worker 按任务池独立采样，完成的轨迹进入共享缓存。Learner 按固定的每任务实例配额组装批次，保证每次更新都见到所有任务类型。定期把训练权重同步给 rollout，并丢弃超过版本滞后阈值的轨迹。更慢的任务会分到更多并发槽位，以免短任务先行填满缓存、长任务拖住更新（Table 5：S1 初期 64 张训练设备、32 张推理设备，槽位 Claw/SWE/TMax 为 4/16/12）。

TBS。新题目先跑一组初始 rollout：全失败进 Frontier，至少一次成功进 Reinforcement。Frontier 对连续失败的题会冷却、暂停采样，一旦首次成功就转入 Reinforcement 且不返回。Reinforcement 用最近一组成功率 p^(x) 的高斯权重采样，均值与带宽都设为 0.25。History 均匀回放更早阶段的题，并用当前策略重新生成轨迹。三个池的配额满足 αF+αR+αH=1。

7. 核心公式

论文把可写成方程的核心放在 Reinforcement Buffer 的采样权重（公式 1）。设 x 最近一组 rollout 的成功率为 p^(x)，R 为对应任务的 Reinforcement 池，则

w(x)=exp(−(p^(x)−μ)22θ2),PR(x)=w(x)∑y∈Rw(y),μ=θ=0.25

直觉：权重在成功率 0.25 处最高，既避开全零奖励（没有优势信号），也不把预算全砸在已经接近必胜的题上。配额层则是硬约束

αF+αR+αH=1

优化端采用 RLOO：同一提示的 8 条 rollout 互为基线来估计优势，再在裁剪区间 [0.20, 0.28] 内做策略更新；文中关闭 KL。梯度混合本身不是新公式，而是把所有任务轨迹放进同一次参数更新，而不是按任务交替。来源：abs · pdf · html

8. Toy example

以下为本文自造算例，数字不是论文结果，只用来解释 TBS 为什么把成功率瞄在 0.25 附近。

假设 Reinforcement 池里有三道题，最近 8 次成功率分别是 1/8、2/8、7/8，即 0.125、0.25、0.875。取 μ=θ=0.25，则偏离 0.25 的距离平方分别是 0.015625、0、0.390625，高斯权重大约是 0.88、1.00、0.04。于是采样会极度偏向“刚刚会一点”的第二题，几乎不再打已经很稳的第三题，同时仍给第一题不少机会。若没有这层权重、只均匀采样，计算会被第三题的高成功率和第一题的多次全零组稀释。Frontier 的冷却则防止某一道永远失败的题每个循环都占掉 8 次无信号 rollout。来源：abs · pdf · html

11. 指标教学

Pass@1 是单次尝试成功率。Pass³（文中写作 Pass^3）是 Claw-Eval 上的三次相关成功率，比单次更稳，但不能直接与 Pass@1 比大小。FeatureBench 的 Resolved 更接近“整题通过”，Tests Passed 是测试点通过率，后者更细、也更容易在没完全解出时上升。Overall 把不同尺度的指标做未加权平均，所以 Claw-Anything 从 12.0 涨到 64.6 会强烈拉动总分；反之 SWE 只加 1.2 个点时，Overall 仍可能看起来很好看。Table 13 的 95% 置信区间是增益的区间，穿过 0 表示在该协议下还不能声称显著改进。来源：abs · pdf · html

14. Ablation

三组消融都有正文数字。混合 vs 单任务：在匹配 Claw 实例数时，混合把 Claw-Eval 峰值从 76.5% 提到 80.3%，说明存在正迁移，而不是简单的预算平摊。梯度混合 vs 交替更新：S2 里交替更新在约第 25 步奖励归零并伴随工具失败，梯度混合保持稳定（Figure 7）。TBS vs Vanilla：FeatureBench Tests Passed 在每个给出的检查点上 TBS 都更高，step 25 为 +3.09 pp；与此同时 Vanilla 解出更多新实例。TBS 的价值更像是把采样压在“可学且尚未稳定”的区域，而不是最大化完全解出的题目数。来源：abs · pdf · html

15. Claim vs Evidence

“27B 模型经 RL-only 后可与更大模型竞争”需要加限定：Maco-RL-3.8 的 Overall 67.0 高于表中 Qwen3.5-397B 等若干更大模型在作者坐标下的位置（Figure 1a），但低于 Claude-Opus-5 的 72.1，且部分前沿分来自第三方榜单。S2 相对 3.5 的 +16.6 Overall 被 Table 13 的综合 CI 支持，但 SWE 与 FeatureBench 的分项 CI 穿过 0，不能把五项改进说成同样可靠。S1 在 FeatureBench Tests Passed 上明显退步，说明“持续扩展任务类型”并不自动单调。代码与加速器型号缺失，外部复现成本高。奖励黑客与评分过松的问题在附录 F/G 中被作者自己记录，并做过规则修补——这是加分的诚实，也说明最终数字依赖于修补后的环境。来源：abs · pdf · html

16. 贡献

可核实的贡献有三条：（1）把 MixRL 做成可增量加入任务类型的两阶段流程，而不是一次性多任务；（2）用异步 rollout + 每步混合批次解决异构任务下的漂移与吞吐；（3）TBS 把探索、巩固与回放写成带配额的采样规则，并在 FeatureBench 上给出相对 Vanilla 的曲线。主结果展示了 27B 密集模型经纯 RL 后 Overall 的大幅度提升，尤其是 3.5 的 Claw-Anything 与 3.8 的 SWE-bench。来源：abs · pdf · html

17. 局限

结论没有单独开“Limitations”节，但证据里限制很清楚。训练硬件型号与代码未给出。评测不全是统一复跑。Table 1 与 Table 13 口径不完全一致。SWE 在 3.5 上几乎不动。S1 对 FeatureBench 有伤害。交替更新的崩溃说明方法对批次构成敏感。附录还记录了奖励黑客与评分协议漏洞，意味着环境本身在训练过程中被修过。3.5 的 Thinking mode 关闭，结果不能直接外推到长思维链 agent；3.8 在 Table 11 中打开了 Thinking mode，因此两代 27B 的训练配置本身就不是同一套超参，不宜只比较 Overall 增量。来源：abs · pdf · html

18. 复现要点

按 Table 6 固定优化器与批次：Adam 10−6、RLOO、8 rollout、32 实例、无 KL、裁剪 [0.20, 0.28]、BF16。S1 与 S2 的同步频率、响应长度和槽位分配必须分开设置（Table 5–6）。实现 TBS 时，先做 8 次初筛再分池，Reinforcement 权重用 μ=θ=0.25，History 均匀回放并重新 rollout。不要用交替任务更新去“简化”实现。评测要同时报告 Table 1 口径与 Table 13 的公共子集 + CI。若没有 64+32 级设备，至少应保持每更新的任务配额比例，否则梯度混合的稳定性结论可能不再成立。同步频率也不要随手改：S1 每 3 次更新同步一次、S2 每 2 次，滞后过大的轨迹会被丢弃，改稀同步会既浪费计算又放大漂移。奖励与终止规则应以附录 B.3 与环境修补后的版本为准，不要用论文早期被黑客的旧判定去复现最终分数。来源：abs · pdf · html

19. 研究价值

对 LLM/Agent RL 来说，这篇把“要不要把所有任务放进同一次更新”从一个偏好问题变成了有失败案例的实证问题：交替更新会崩，混合更新能继续涨。TBS 则针对稀疏奖励里零优势组的浪费，给出可实现的采样规则。它也提醒：Overall 被单个基准大幅拉动时，必须回头看分项与置信区间。来源：abs · pdf · html

20. 可执行迁移

（1）若你已经在跑多任务 agent RL，先把“按任务轮流更新”改成“每次更新都按定额混入所有任务”，并记录策略版本滞后；这是成本相对低、本文消融最强烈的一刀。（2）给训练题建三个池：全失败、部分成功、旧任务回放；部分成功池用峰值在低成功率（如 0.25）的权重，而不是均匀或只打难题。同时为完全失败的题加冷却，避免零优势组占满预算。来源：abs · pdf · html

21. 方向专用分析

这是典型的 RL-for-Agents 论文：环境是长程工具任务，信号是可验证的成功/测试通过，算法问题是信用分配之前的采样与稳定性。它与昨日的 U-Statistics 论文不同，几乎不谈估计器理论，而谈大规模混合训练如何不塌。Agent 连续两天后，今日用它覆盖 RL 主线而不是再选一篇记忆/脚手架 Agent 文，是因为贡献落在训练方法而非新的 agent 接口。若只关心单域 SWE，3.8 的 70.2→79.0 仍然有用，但 3.5 上同一指标几乎不动，说明 MixRL 的红利高度依赖起点模型和任务配比，不能把 3.8 的 SWE 增益自动写到所有 27B 上。来源：abs · pdf · html

22. Attack / Verification

最有效的质疑是换口径：只用 SWE-bench 与 FeatureBench 的 CI，3.5 的“全面提升”会大幅缩水；把第三方榜上的前沿模型改成同一 harness 复跑，Figure 1a 中“接近更大模型”的位置可能移动。验证上，应固定随机种子与评测尝试次数，重出 Table 13；并检查在未修补的旧环境里奖励是否仍可被黑客。若无法负担完整训练，至少应用公开检查点（若未来发布）复现五基准点估计。另一个可执行的审计是：只重跑 Table 13 的 150 题公共子集，确认 Claw-Anything 的 12.00→71.33 与 Overall 的 43.61→61.49 在相同协议下可复现，再决定是否采信 Table 1 的全量点估计。来源：abs · pdf · html

1. 基本信息

2. 一句话定位

在 PD 分离的专家并行 MoE 推理里，prefill 的瓶颈是最忙一秩的 token 数，decode 的瓶颈是最忙一秩的活跃专家数；RankCast 用同一套“保住 Top-p、其余在 Top-L 里挑”的路由约束，分别用秩价格和专家关闭去压这两个最大值。默认候选宽度在 235B 上为 L=16，在 397B 上为 L=20，两阶段都保护每个 token 的 Top-2。来源：abs · pdf · html

3. 人话版

大 MoE 服务通常把专家权重切到不同 GPU（EP），每层都要等最慢的那张卡。训练时用的辅助损失只能管长期平均，管不住某一批请求打到同一组物理秩上。更麻烦的是，prefill 和 decode 慢的原因不一样：prefill 偏计算，多一个 token 就多一块 GEMM；decode 在中等批次下偏内存，一张卡上活跃专家越多，越要来回搬权重，token 再多一点反而不是主因。因此把同一套“再平衡专家放置”的办法同时用到两阶段，往往一边有效、另一边失效。RankCast 的做法是不改权重放置，只改这一层每个 token 最终选哪些专家：先保住模型最看好的 Top-p，剩下 k−p 个名额在更大的 Top-L 候选里，按阶段目标来挑。Prefill 给繁忙的秩标高价，让灵活名额流向空闲秩；decode 则在最忙的秩上关闭一部分专家。他们在两台 8×H800 节点上测 Qwen3-235B-A22B（EP=8）和 Qwen3.5-397B-A17B（EP=16），prefill 输入吞吐最多加约 19%，decode 的 TPOT 最多降约 10%，质量损失声明低于 1 个百分点。读这些数字时有两个容易混的地方。第一，19% 是 prefill 输入吞吐，10% 是 decode 的 TPOT 下降，二者不能加在一起叫“端到端 29%”。第二，LongBench 上的相对增益明显更小，说明当计算或通信瓶颈不在最忙专家秩上时，改路由的空间会变窄。因此这项工作更像给 PD 分离的 MoE 服务提供一把按阶段使用的扳手，而不是一张在所有负载上通用的加速卡。来源：abs · pdf · html

4. 背景与缺口

DeepSeek-V3 已提到域偏移会在推理时造成专家不均，并在服务中用冗余专家应对。UltraEP 报告训练与 prefill 中秩间不均衡可达 1.30–4.01，且热门专家随 microbatch、层和域变化。在线 EPLB 一类方法用历史负载做放置或复制，跟不上“每一批都在变”的瞬时不均，复制还会占用本可用于 KV 的显存。PD 分离之后，两个阶段的目标函数也不再相同。缺口是：在不重排权重、不破坏 token 最核心专家的前提下，对 prefill 的最大 token 负载和 decode 的最大活跃专家数分别做在线、按批的秩级均衡，并真正接到 SGLang/DeepEP 这类服务栈里。只做离线重放是不够的：价格要在每层、每批之间算完，还得和已有的 dispatch/combine 重叠，否则均衡带来的等待减少会被求解本身吃掉。这也是为什么开销数字（约 0.5–0.9%）必须和吞吐增益放在同一节里读。来源：abs · pdf · html

5. 核心 insight

第一，真正决定一层延迟的不是单个专家的长期利用率，而是当前这批数据在物理秩上的瞬时最大值。第二，每个 token 并不需要把 k 个专家都订死：只要保住预测的 Top-p，剩下的灵活名额就可以被价格或关闭决策挪走。第三，prefill 适合用运输问题的对偶价格一次性摊负载，decode 更适合从 Top-k 出发、在最忙秩上按代价关闭专家，因为 decode 的 GEMM 时间几乎不随每专家 token 数变化，而随活跃专家数近似线性变化（文中斜率 0.52 ms/专家，R2=0.99）。来源：abs · pdf · html

Prefill。灵活名额 d=k−p。设 N 个 token、P 个 EP 秩，秩 q 的灵活负载目标为 cq（扣除保护集后的均衡目标，总和为 Nd）。用 0-1 变量选择“token–秩–候选”对，最大化分数并满足每个 token 恰好 d 个灵活选择、每秩恰好 cq 个负载（公式 2）。对偶变量是 token 阈值 αi 与秩价格 βq：token 按 ai,q,j−βq 排序，繁忙秩价格升高。实际只做一轮扫描，并用直方图交换残差分数，避免把每个分数送到所有秩。目标层最终取

8. Toy example

以下为本文自造算例，数字不是论文结果，只用来说明价格如何挪走灵活名额。

设 k=3、p=2，所以只有 d=1 个灵活名额。两个 token 的保护专家分别已经落在秩 A 与秩 B，但他们的第三候选都最想去秩 A。若都选 A，则 A 的灵活负载为 2、B 为 0。RankCast 给 A 标更高的 βA，于是第二个 token 的次优候选（在 B 上）按调整分数可能反超，最终负载变成 1 和 1。Decode 侧可以想象秩 A 上有 6 个活跃专家、秩 B 有 4 个：若两个专家都还可关，一次联合关闭会让 A 先关 2 个，把最大值从 6 降到 4，而不是只在 A 上关 1 个却发现 B 也是 4、最大值不动。来源：abs · pdf · html

9. Baselines

服务栈基线是 SGLang 原生 Top-k。放置类对照为在线 EPLB（每 50 个 forward 重平衡）以及带冗余专家的 EPLB-R（235B 加 8 个，397B 加 16 个）。Decode 的算法对照是 XShare 与 OEA，但二者没有开源的 EP 实现，因此只在离线、用真实 router 分数的条件下比较（Table 7）：它们在相同 M 下会挪动 1.9–6.0 倍的路由概率。不要把离线概率位移直接读成在线吞吐。放置类基线里还有一个容易漏看的细节：冗余专家会占用显存、减少并发，因而 EPLB-R 的吞吐增益在两款模型上都低于不加冗余的在线 EPLB。在 LongBench v2 上，EPLB 与 EPLB-R 只去掉 6–43% 的超额负载，吞吐变化落在 −1.2% 到 +0.9% 之间，几乎帮不上忙。来源：abs · pdf · html

14. Ablation

保护前缀 p：Table 5 在 p=2 时，235B prefill 上真实 top-1 落在预测 top-1 的比例为 77.8%，落在预测 top-2 为 91.4%；decode 在关闭之后仍有 99.4–99.5% 的 token 保住真实 top-1。正文还写，p 在 0/1/2 之间对 prefill 吞吐影响不超过 0.3%。深度帽 D 与质量权重见 Table 9：关掉质量权重、D=4 时，1/TPOT 可到 +7.7%，但 LiveCodeBench 降 1.49 pp，已经超过“低于 1 个点”的主结果承诺，说明质量权重不是装饰。候选宽度 L 与直方图箱数 B 的离线回放在附录 Table 10–11。η 单独 vs 完整价格见 Table 2，上文已读。来源：abs · pdf · html

15. Claim vs Evidence

“最多 19% prefill、最多 10% decode TPOT、质量代价低于 1 个百分点、去掉超过 75% 的超额负载”在 Table 1–4 上对得上，但要注意范围。19% 出现在 235B 的 ShareGPT/CodeContests 8K，不是 LongBench，也不是 397B 的全部设置。10% 是 TPOT 下降，表中最大 1/TPOT 增益是 11.1%。质量上，主结果开启质量权重；若关掉，Table 9 会出现 1.49 pp 的掉点，所以该声明不能离开默认配置。397B 的 Both 质量未在主表列出。实验只覆盖同一家族的两个模型、最多 EP=16，结论写明 group-limited 或 sigmoid 路由未测，也没有与专家放置联合测量。改变路由不是无损的，需要精确原路由的部署应改用放置方法。来源：abs · pdf · html

16. 贡献

可核验的贡献是：（1）把 prefill 与 decode 的不同最大值瓶颈写进同一个“保护 Top-p、灵活名额在 Top-L 中选择”的约束；（2）给出可在 DeepEP 通道上走的价格估计与关闭求解器，而不是只做离线仿真；（3）在 235B/397B 上同时报告吞吐、不均衡、TPOT、质量与开销，并把放置类基线比下去，尤其是长上下文。（4）用 Table 2 证明按批价格不是可选项：慢偏置 η 在稳定短上下文上能收回大部分收益，但在 32K LongBench 上几乎无效，必须每批重算价格。来源：abs · pdf · html

17. 局限

第 6 节写得很清楚：路由被改写，因此不是无损；未与放置/复制联合评测；只测一个家族的两个模型；group-limited 与 sigmoid 门控未测；最多 16 卡；kernel 与服务集成尚未充分优化，开销是上界。另外，XShare/OEA 没有在线 EP 对比，公开代码仓库 Not Reported，外部只能依据方程和附录 C 的参考实现去复现求解器。来源：abs · pdf · html

18. 复现要点

先在 SGLang + DeepEP 上接好 PD 分离与对应 EP 度（8 或 16）。保护集 p=2、候选 L=16，prefill 走公式 2–5 的一轮价格，decode 走公式 6–8 并打开质量权重与合理的 D。应用层必须用本层真实分数做最终 Top 选择，预测只用于算价格或掩码。评测要分开报 prefill 输入吞吐、max/mean、decode 中位 TPOT 与 1/TPOT，并列出 Table 4 那种分项质量，而不是只给平均值。附录 C 的 NumPy 参考实现可用于核对 GPU 掩码是否 bit-exact。硬件应按 8×H800 节点来对时延数量级，换卡后绝对值会变，相对增益是否还在需要重测。测量协议应包含 warmup、与基线交替跑、以及与 Table 6 交叉核对相对增益。若只报百分比不报绝对千 token/s，将无法发现 50.0→59.7 与 19.4% 是否同一组实验。Decode 侧要同时记录最忙秩活跃专家数，以便对照文中 14.4→9.7 和 0.52 ms/专家的线性拟合。来源：abs · pdf · html

19. 研究价值

它把 MoE 服务里一个常被混为一谈的问题拆开：同一套不均衡，在 prefill 和 decode 里不是同一个优化量。对做推理系统的人，这提供了“改路由但不改放置”的一条可部署路径，并且用长上下文上 EPLB 失效的例子，说明历史放置跟不上按批波动。它也把“改路由可加速”和“改路由是否近似无损”拆开报告：主配置下质量掉点不超过 0.84，但关掉质量权重就会超过 1 个百分点，因此系统论文同样需要把保护约束和质量权重当成方法的一部分，而不是事后补丁。来源：abs · pdf · html

20. 可执行迁移

（1）在现有 EP 服务里先打点：记录每一层最忙秩的 token 数（prefill）和活跃专家数（decode），看延迟是否随这两个最大值线性变化；如果 decode 已接近文中那种线性关系，关闭专家可能比复制专家更划算。（2）不要一上来改 k。先给每个 token 留一个保护前缀（Top-1 或 Top-2），只在剩余名额上做负载挪移，并像 Table 4 那样把质量和吞吐放在同一张决策表里，避免用关掉质量权重的激进帽去刷吞吐。来源：abs · pdf · html

21. 方向专用分析

相对昨日的 LoomKV（压缩 KV 以扩大容量），RankCast 动的是 MoE 路由与秩负载，不碰 KV 布局，二者正交。相对推测解码或量化，它也不改生成算法或数值精度，而是减少同步等待。这正是今日 Inference 选题避开“又一篇解码算法”的原因。收益上限受非专家部分的延迟约束：文中 decode 截距 20.1 ms 是 shedding 砍不掉的部分，所以不能指望活跃专家减半、TPOT 也减半。把 RankCast 接到推测解码或 KV 压缩上是自然的下一步，但本文没有提供组合数字（Not Reported）。若要做，应分别测量 prefill 与 decode 的时间占比，因为推测解码主要改 decode，而本文 19% 的头牌数字来自 prefill。来源：abs · pdf · html

22. Attack / Verification

攻击这项主张，可以换路由类型（sigmoid / 分组限制）、把 EP 拉到远大于 16、或把 RankCast 与 EPLB-R 同时打开看是否互伤。也可以专门构造“保护集已经很不均”的批次，因为灵活名额只有 d=k−p。验证上，应复现 Table 1 与 Table 6 的对应关系，检查 19.4% 是否就是 50.0→59.7；并用附录参考实现对齐掩码。质量评测必须按附录重复次数重跑，单次点估计不够支撑 0.x 个百分点的差异。一个很便宜的健全性检查是：在关闭 RankCast 与打开它之间交替运行同一组请求，确认 Table 1 的不均衡下降与吞吐上升同时出现；如果吞吐升了但不均衡几乎不变，增益可能来自其他系统波动，而不是秩级均衡本身。来源：abs · pdf · html

23. 记忆总结

  • Prefill 看最忙秩的 token 数，decode 看最忙秩的活跃专家数，两者不是同一目标。
  • 统一约束：保住 Top-p，其余 k−p 个名额只在 Top-L 里选。
  • Prefill 用一轮对偶价格把灵活负载推向空闲秩；分数用直方图汇总。
  • Decode 从 Top-k 出发，按代价在最忙的若干秩上联合关闭专家。
  • 235B ShareGPT 8K prefill +19.4%，不均衡 1.75→1.08，超额负载去掉约 89%。
  • 397B CodeContests 的 TPOT 52.19→46.97（约 −10%），1/TPOT +11.1%。
  • 长上下文上在线 EPLB 接近零收益，甚至为负；按批价格在 Table 2 里是关键增量。
  • 默认配置下质量下降不超过 0.84 pp；关掉质量权重会出现 1.49 pp 的掉点。
  • 开销约 0.5–0.9% 的 step 时间，且被作者视为尚未充分优化的上界。
  • 只评了同一家族两个模型、EP≤16；公开仓库 Not Reported；与放置方法尚未联合测量。
