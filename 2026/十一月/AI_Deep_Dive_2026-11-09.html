Paper 1 · SpecOPD: Branch-Parallel On-Policy Distillation for Speculative Decoding BACKFILL

Tianyu Liu 等；Qwen Business Unit of Alibaba、浙江大学等；arXiv:2611.02846v1，2026-11-02；预印本，未核实正式接收；代码公开状态 Not Verified；BACKFILL。
原文：https://arxiv.org/html/2611.02846　|　摘要：arXiv Abstract

01. 定位与人话版

一句话：把原本必须一轮一轮执行的推测解码 on-policy 蒸馏，改写成以参考序列为主干、以当前 drafter 的采样为分支的并行监督问题，从而提高训练数据生成速度，并让 draft token 更容易被 target 接受。

先想象你在训练一个能一次猜出七个 token 的小模型。大模型充当裁判，检查哪些猜测正确。常规方法依赖真实的完整解码链：本轮裁判接受了前三个 token，下一轮才能知道从哪个位置继续，随后才能采集下一条训练数据。GPU 在采集和训练之间切换，并且大量时间耗在等待前面的决定。SpecOPD 发现，训练小模型所需要的关键反馈，不一定非要来自一条完整执行完的推测解码轨迹。只要固定一段真实前缀，再让当前小模型自行采样后续内容，就可以让大模型对这段“真实前缀加模型自己犯的错”评分。不同锚点的评分彼此独立，适合批量执行。论文在三个尺度的 target 与多种 drafter 上报告了更长的接受长度；最突出的结果是某个训练设置下受监督 token 的吞吐量达到顺序 rollout 方案的 16.09 倍。它的意义不是简单增加训练数据，而是把“策略当前会犯的错”保留下来，同时从训练数据采集链中去掉不必要的串行依赖。

02. 背景、研究缺口与判断边界

推测解码的目标是让 target 用一个前向验证多个候选 token。假设大模型每步耗时很长，而 drafter 能非常快地给出连续七个 token，则验证一批候选可能比大模型逐 token 输出快。然而速度不仅取决于 drafter 的生成成本，还取决于 target 接受了多少。若总是第一枚 token 就被拒绝，即使 drafter 零耗时，验证每轮还是只推进一小步。

传统蒸馏大致有三条路线：用 target 的真实文本训练的 SFT/CE、在参考轨迹上对齐分布的离线蒸馏、在 drafter 当前采样的状态上反复由 target 提供监督的 on-policy 蒸馏。前两者容易实现和并行，却忽略错误前缀；第三者能够逼近实际部署时的状态，却常被串行 rollout 拖慢。比如 target 在代码补全上下文里写出 if，drafter 偏偏采样出 while；如果训练只观察 target 的正确序列，就不知道 after-while 的后续预测会偏离到何处。在线采集可发现这种偏差，但又不得不等候一次次验收。

论文的缺口是训练采集依赖，不是推测解码的正确性证明。其贡献针对已存在并行 drafter 的训练系统；在运行阶段它并没有改写 target 的验证规则，也没有声称所有接受长度增益都会等比例转为实际吞吐量。其参考主干来自预收集回复，分支来自当前参数，因而是“在分支局部 on-policy”，不是完整交互分布意义的严格 on-policy。尤其对于 SWE/Terminal 类型 Agent 场景，论文使用记录下来的工具交互历史，仅评估续写效率，不测真实工具调用后的任务成功率。这个区分决定了后面迁移到 Agent 时不能直接宣称提升 Agent 能力。

03. Core Insight：真正能并行的依赖

作者抓住了一个被常规 rollout 实现混淆的依赖关系：为了在某个历史 h 上监督 qθ 的下一个 token，target 只需要知道 h；它并不需要知道另一条训练分支最终在哪个 token 被接受。完整在线 rollout 的跨轮依赖是为模拟部署而产生的，不是每个局部训练样本的逻辑前提。给定参考前缀 x≤a，当前 drafter 的局部样本 y1…yw 可以独立从各个 anchor 生长；同一个训练 batch 的多个 anchor 之间没有先后关系。

这是算法层面的条件独立观察，后面仍有工程障碍。若每条分支都复制完整长前缀，大模型重复计算会抵消并行收益；若只给完整注意力加树形 mask，却在 GDN 这类递归状态层之间共用 hidden state，则各条分支会互相污染；若稀疏注意力的压缩索引跨过 anchor，不恰当的共享又会把未来参考 token 泄漏进当前分支。SpecOPD 的有趣之处是把目标条件独立与三类目标架构的“历史隔离机制”绑定。

需要谨慎理解实验归因：训练流程改变了采样数据、并行批次构成、监督的 token 数量和优化路径。一次看到接受长度变好并不能归结为“树形注意力本身改善了模型”；树与 replay 首先保障并行评分的效率与语义正确，真正改善接受分布的是 current-policy prefix 加 E2E-TV 优化。作者在附录中说明部分训练路线计算分配不同，因此 off-policy 对照不能当成完全同算力的纯因果消融。

04. Method Deep Dive：从数据到参数更新

Input → 预收集参考回复 → 随机抽取 response anchor → 使用当前 drafter 独立采样分支 → 构造共享主干的 proposal tree → 架构匹配的 branch-parallel target scoring → 计算前缀存活和 E2E-TV → 对 drafter 更新参数 → 用独立解码集测接受长度与吞吐量。

步骤一，准备参考序列 x1:L。它包含用户 prompt 和一个此前收集的 response，来自目标模型的离线重生成或数据集提供的回复。只在 response 区域随机取 B 个锚点，避免每个分支只学 prompt 初始化。此时“参考”是定位训练状态的一条主干，而不是每个位置必须拟合的唯一标签。严重的分布偏移来自参考回复与真实部署请求不匹配；后续在 agent 轨迹上的研究应单独做 reference source ablation。

步骤二，对每个 anchor b，保留 x≤ab，再使用当前 qθ 独立采样 W 个 token。第 i 个位置条件于参考前缀和自己分支先前采样的 token，不得读取其他分支，也不得读取 anchor 之后的参考答案。在工程上若将所有分支误写成同一条扁平 batch 序列，模型会产生未来信息泄漏，训练 loss 可能异常好，却严重损害 acceptance。

步骤三，构造树。相同的参考主干只计算一次；每个锚点接出一条独立 continuation。父指针记录当前节点能看到哪些祖先。普通 GQA 全注意力通过 tree-causal mask 保证每个 query 只能访问自己的参考前缀和当前分支历史；共享主干 KV 节省重复 prefill。此处 mask 应以“逻辑祖先”而非内存布局判断可见性。

步骤四，稀疏 QSA 要对索引单独处置。作者的索引压缩以四个 token 为一组，完整处在 anchor 之前的组可共享主干 indexer key；跨越 anchor 的边界组需按分支重新组合并压缩。每条分支的 top-k 只从自身可见的完整组里检索，尚未组成完整组的因果 tail 单独参与注意力。否则，即使 attention mask 正确，路由到的稀疏块已经被其他分支的未来 token 污染。

步骤五，GDN 的状态不能靠 mask 隔离。它把过去压成递归矩阵，后继状态依赖此前每次更新。方法沿参考主干存周期 checkpoint，并从每个分支 anchor 之前最近的 checkpoint 重放较短的中间 token；之后在每个分支私有状态里前进。训练时共享主干计算，却不共享已经分叉的递归状态。checkpoint 间隔太大则 replay 成本高，间隔太小则主干 checkpoint 内存上升。

步骤六，target 沿各分支的真实条件历史给出 p，drafter 给出 qθ，使用分布重叠构造连续可优化的接受长度 surrogate。这不是训练一个单独 verifier，也不需要每条 branch 都得到完整工具环境奖励。训练完成之后，部署仍然使用标准的 speculative verify/accept 过程；因为推理阶段的分布不被改变，理论上的 lossless 性质来自推测采样算法而非 SpecOPD 训练。

05. 公式、变量与数学直觉

论文式（1）定义 h(b,i)=(x≤ab,yb,<i)，yb,i~qθ(.|h)。这里 a 是 anchor，x 是共享参考，y 是该分支当前 drafter 采样，θ 是训练参数。为什么强调 yb,<i 而不是 x 的后续 token？因为部署时恰恰会遇到模型自己生成的历史；如果永远沿 x 的正确历史训练，就在错误前缀上缺乏校准。

论文式（8）给出 α(b,i)=Σv min(qθ(v|h),p(v|h))=1−TV(qθ,p)。TV 是 total variation distance，越小代表两种词表概率分布越接近，理论上的 token 接受概率越高。例如词表只有 A/B，target=(0.8,0.2)，draft=(0.6,0.4)，重叠为 min(0.8,0.6)+min(0.2,0.4)=0.8。如果 draft 改成 (0.79,0.21)，重叠为 0.99；这不是简单提高 argmax 的正确率，而是让整个采样分布更接近。

连续多个 token 同时被接受需要“前缀全活下来”，所以 E2E-TV 不把每个位置 α 简单相加，而是让前面位置的匹配概率乘入后续位置贡献。直觉上第二枚 token 的收益只有第一枚没被拒绝时才兑现；第七枚 token 即便单步 α 很大，前六枚概率很低时对最终速度贡献仍然有限。梯度优化围绕这个前缀概率进行，而不是普通 teacher-forcing CE 的每位置预测错误。

注意总变差是分布级指标，实际部署仍依赖具体 acceptance sampling；温度、top-p、tokenizer 一致性都会影响估计的可转移性。此外 E2E-TV 是 surrogate，低训练 loss 不必然意味整体加速，论文自己用 Figure 8 的 off-policy 失配说明了这一点。

对于稀疏索引的式（6），κ̄(b,g) 在完整前缀组时使用共享 trunk 表征，在跨越 anchor 时对该分支的四个原始索引 token 重新执行压缩 Cg。对于 GDN 的式（7），先从 checkpoint Sc 重放到 Sa，再令 Sb,j=F(Sb,j−1,zb,j)。这些不是装饰性技术公式，而是说明怎样严格避免不同 branch 的历史串扰。少量重复计算换来树枝独立，是此系统的关键正确性成本。

06. Toy Example：从错误前缀到可监督分支

假设参考指令是“编写函数并返回非负值”，target 的参考代码中包含 return max(x,0)。在 return 后的五个位置取三个 anchor。第一个 anchor 的 drafter 采样 max(x,0)；第二个采样 abs(x)；第三个采样 x if x>0 else 0。三条分支共享指令和此前的正确代码，但从 anchor 开始具有不同的 token 历史。

若按普通 CE，只用 max(x,0) 作为真实标签，其余两条分支的历史不被训练。按 SpecOPD，target 分别对每条分支的实际 prefix 输出概率分布。假设位置一二三的 α 分别是 0.9、0.8、0.7，则通过前三个 draft token 的近似存活权重是 0.9×0.8×0.7=0.504；另一分支为 0.95、0.95、0.95，则是 0.857。训练因此更愿意改善早期接受瓶颈。这里的数值只是解释 surrogate 的自构示例，不是论文实测。

树形 mask 要保证第二分支不能看到第一分支的 max 后续；稀疏索引跨 anchor 的四-token 组不能包含参考代码的未来 token；若 target 使用 GDN，重放到不同 anchor 后必须复制私有状态。最后一次 target 前向可批量评分所有分支，但监督仍以各自条件历史为准。完成训练的 drafter 再在 HumanEval 和数学输入上真实运行 target verification，这时才能测 acceptance length 和 output tokens/s。

07. Baseline 深比较与 strongest baseline

第一类对照是原始 DFlash、DSpark、DFlash V2 checkpoint。它们已经是高效的并行 drafter，能在相似的推理接口上直接测 AL，因此是回答“训练是否有价值”的基础对照。8B 的 DFlash 增益最大，但 27B 的 DFlash V2 原始接受长度已经很高，改进空间小。

第二类是顺序 Draft-OPD。它用当前 drafter rollout，再用 target 校验并更新，优点是训练上下文更接近实际全轨迹；缺点是收集依赖导致流水线低利用。它是**训练吞吐量方面的 strongest baseline**，因为目标最相似、直接体现是否减少串行采样。16.09 倍比较不应被误写成“推理加速 16.09 倍”。

第三类是 off-policy CE。固定 target 参考文本做 token 分类，吞吐高、实现简单，劣势是没有 drafter 自身错误条件历史。第四类是 off-policy E2E-TV。其 loss 已关注接受长度，不再是普通 CE，但仍沿固定参考历史评分，从而能拆分“objective 好”与“状态分布好”的不同来源。论文的消融显示后两类下降并不等于所有离线蒸馏都无效，因为超参数和计算资源配置还会影响结果。

第五类是 AR、原始推测解码、MTP 等部署参照。AR 的 target 输出给速度定义一倍基线；原始 drafter 对照回答升级有没有真实价值；MTP 等方法结构不同，不能机械把其参数规模与训练成本视为相等。对模型和 benchmark 的比较须坚持“同模型、同温度、同并发、同数据”的配对前提。

08. 实验设置、Metrics 与研究问题

模型范围是 Qwen3-8B 的 DFlash、DSpark，Qwen3.8-27B 的 DFlash V2，Qwen3.8-Flash-Next-125B 的 DFlash V2；覆盖普通 GQA、GQA–GDN 和 QSA–GDN。训练参考数据来自 Open-PerfectBlend，serving 以 SGLang 评估。主要任务五类：MT-Bench、HumanEval、MATH-500、记录版 SWE 和 Terminal 历史。后两者是固定前缀续写，不进行实时工具调用，因此不提供 agent task-success 证据。

附录 A.1 给出评估集合：MT-Bench 160 turns、HumanEval 164 prompts、MATH-500 500 prompts、SWE 1662 个请求和 Terminal 177 个请求。Terminal 的 64 条原始轨迹被明确标注与训练数据可能重叠，其官方 benchmark subset 成员也未得到确认，这是非常重要的数据污染风险。

主要 decoding 分别使用 T=0 与 T=1，proposal 为七个 draft token，验证位置八个。T=0 使用 greedy；T=1 使用 top-p=0.95、top-k=20。AL=每个请求完成的 token 数/验证轮数，再先对请求后对 benchmark 平均，越高通常越好，但它忽略每轮时间。吞吐 TPS=完成 token 数/真实 client 活动 wall-clock，越高越好；若验证额外开销过大，AL 提高也可能降低 TPS。

训练 metrics 包括 updates/s、supervised tokens/update、supervised tokens/s，最后一项是前两项乘积。它只计算进入 loss 的预测行，不把上下文前缀也算为监督 token。GPU activity 来自指定 profiling 窗口，不等同于集群总能耗或训练总成本。Research Question A：分支独立监督能否增加接受长度？B：能否避免串行 rollout 的 GPU 空等？C：增益在 8B、27B、125B 和 Agent 历史上是否均稳健？D：提高 AL 是否实际带来 output TPS 提升？

09. Results：八项数据、最强与最弱证据

结果一，Table 1 的 T=0 8B DFlash 五类平均 AL 从 2.649 升至 3.747，增幅约 41.45%；这是论文报告的最大平均接受长度增益之一，但因为初始 AL 较低，不该推断所有高质量 drafter 都能增加四成。

结果二，8B DFlash 的 Terminal 从 1.620 到 2.940，增幅约 81.5%。这是最显著的单项接受长度变化，但 Terminal 仅是已有轨迹的续写，而且存在数据重叠提示，不能直接宣称 Agent 任务成功率提高八成。

结果三，同样 T=0 的 DSpark 平均从 3.674 到 4.439；这说明方法不专属于 DFlash，但增益比 DFlash 小，提示初始化水平影响收益。

结果四，27B DFlash V2 从 5.103 升至 5.242，约 2.7%，远不如 8B 的改善，论文也明确指出 agentic 样本在部分设置几乎不变。最弱证据恰恰说明 “更强 drafter 的接受长度平台”没有被普遍打破。

结果五，125B 在 T=0 从 3.941 到 4.122，增幅约 4.6%。考虑更大模型和复合稀疏线性层，这支持训练框架有跨架构可用性，但不代表每个训练环节在部署中都廉价。

结果六，Figure 1 与训练效率实验给出 4.95 倍 updates/s、3.25 倍 supervised tokens/update，乘积 16.09 倍 supervised-token throughput；这是训练生产率结论，数据统计不包括离线 reference 准备。

结果七，GPU activity 从 26.37% 增至 77.23%，是串行收集改为批量 target scoring 的直观证据；然而不能简单换算为真实成本节省百分比，因为 GPU 价格、批量大小和参考数据准备未统一折算。

结果八，27B 的真实 serving 最高达到相对 AR 的 3.56×，而五个任务的几何平均在并发 1、8、32 时分别 2.97×、2.23×、1.35×；相比原始 DFlash V2 的额外吞吐最多 2.83%。这说明大部分加速来自 speculative decoding 基座，SpecOPD 的边际提升较小。特别是 SWE 在并发 32 时反而慢于原 drafter，清楚地构成吞吐量 failure case。

另一个警告来自 Figure 8：离线 CE 的 loss 随训练下降，但 acceptance 也可能下降；作者指出第七位置的 prefix survival 在 SpecOPD 最佳 checkpoint 上升 4.33 个百分点，在 off-policy CE 中下降 2.57 个百分点。指标之间的错位支持采用 acceptance-aware training，但纯从曲线尚无法断言每个改进完全由 on-policy 数据造成。

11. Claim vs Evidence、创新与局限

Authors Claim：可以避免顺序 rollout 收集，保持当前 drafter 条件下的监督，并提高接受长度和训练吞吐。Experiments Actually Show：在三类目标架构、所选数据集和训练设置里 AL 有改善，训练监督吞吐有极显著改善；针对 27B 的真实 serving 加速存在但边际幅度有限。What Is Not Yet Proven：端到端训练总美元成本下降同等倍数、复杂真实 Agent 任务成功率提升、任意架构都能无偏地共用 reference trunk，以及离线 reference 与真实在线上下文没有分布错位。

Contribution 1 [New Mechanism]：从完整在线轨迹切成 reference-anchored 的独立 on-policy 分支。Contribution 2 [New System / Engineering]：对 GQA/QSA/GDN 的 branch-specific 历史隔离与评分，尤其是稀疏索引边界组和递归状态 replay。Contribution 3 [New Empirical Finding]：接受长度与常规离线 loss 存在明显不一致。E2E-TV 本身引用已有工作，并非本文原创 objective；共享前缀 tree mask 也不是从零发明，创新在组织这些部件支持复合目标架构的有效训练。

作者明示的限制包括 125B drafter 的初始训练不包含 agentic 数据，因此 Agentic 领域改善受限。附录还揭示 Terminal 来源轨迹与训练语料重叠的问题。进一步的推导限制包括：reference trunk 的分布可能与长交互后的当前 policy 状态不同；多个 anchor 采样相关、不同任务长度不同，会改变监督样本的有效权重；并行批次可能引入更高峰值显存；树形索引、GDN state 的微小数值差异对近乎相等的概率分布可能放大成输出差异。

这一论文最应避免的偷换是把“目标接受概率优化”直接解释成“推理质量提升”。在分布保持的 SD 前提下，target output quality 不该因为 drafter 更聪明而变好；获益主要是以更少轮次完成同样的 target 输出。若观察到任务质量明显改变，应优先检查采样算法、mask、数值精度和 benchmark 的配对策略。

12. 复现视角、指标教学与工程陷阱

最小版本先选择 Qwen3-8B 与已有 DFlash drafter，避免初期就处理 125B QSA/GDN。用 Open-PerfectBlend 的可合法使用部分准备 reference，定义 anchor_sampler(seed,response_mask)、draft_branch_sampler(theta,anchors,W=7)、tree_parent_mask、target_score 和 e2e_tv_loss 五个模块。第一阶段只做 dense attention：在 8 个参考响应上采样三个 anchor，每个 anchor 取七枚候选，检查 target logits 与把每条分支分别独立前向得到的 logits 数值一致，再扩大 batch。

第二阶段再实现稀疏 indexer 的 4-token 组边界重算，并对跨边界 anchor 施加随机 shift 测试；第三阶段实现 GDN checkpoint 和 indexed replay，强制加入状态矩阵的最大绝对/相对误差单元测试。不能只测试最后 logit，因为错误的 state 有时会被后续 gating 部分抵消。对于 branch-specific 卷积，缓存也必须遵守父指针，不可在多个 CTA 之间共享被修改的历史。

训练对照固定相同 reference sequences、anchor 数、采样长度、优化器步数与验证集合。把 on-policy E2E-TV 与固定 reference 上 E2E-TV、普通 CE、顺序 Draft-OPD 放在同一验证脚本，用统一 temperature 与并发设置测 AL。记录 updates/s、supervised tokens/update、wall-clock、峰值显存和真实 output TPS；若只报告 AL，则无法判断系统价值。

优先验证 Table 1 的 8B DFlash 五任务均值从 2.649 到 3.747，而不是立刻追逐 125B。敏感项包括 W、anchor 采样分布、分支数、GDN checkpoint 周期、tree mask 的祖先判定、target 与 draft tokenizer/温度一致性、FP32/BF16、参考集与评估集重叠。每次性能提升需要同时报告 target scoring 时间和 GPU 利用率，避免“有监督 token 更多”掩盖了离线数据准备成本。

01. 定位与人话版

一句话：在 Gated DeltaNet 与 MoE 混合的大模型里，推测解码不能单纯“越多验证越好”，HybridSpec 把验证长度、激活专家成本和循环状态恢复统一到真实吞吐量目标上。

假设小模型一下猜出 15 个 token，大模型一次性检查。对于普通 dense Transformer，多看几个 token 可能并不增加多少额外计算；但目标模型若混合了需要逐步更新状态的 GDN 层，以及每个 token 会激活不同专家的 MoE 层，长度从 4 增至 16 可能显著增加验证开销。多验证的后半段又往往由于前面的错误而被丢掉，导致接受长度更大反而 TPS 下降。HybridSpec 先从 drafter 的置信度估算接受收益，选择初始验证长度；随后故意多让一枚 token 运行到第一层专家路由边界，查看这枚 token 会不会复用已有专家，再决定是否继续完整验证。它还针对 GDN 的递归状态设计块并行内核，不再为每枚候选保留笨重的状态副本。论文在三个混合模型上报告，相比 AR 解码达到 1.75–1.88 倍速度，相比 DFlash 为 1.30–1.33 倍。这是一篇典型的“目标算子形态决定推测解码策略”的系统论文；其瓶颈与视频动态计算、Agent 多步生成中的请求特征也有明显联系。

02. Background & Research Gap

常规推测解码有两个角色：drafter 非常快地猜出多个 token，target 对这些 token 做并行验证并决定接受前缀。若 target 的验证成本近乎与候选长度无关，则验证较长块通常有利；但当 target 的成本随长度陡增，较长块即使增加了 AL，也可能更慢。文献已有按置信度截断的 D-Cut、EVICT 等方案，却主要关注“这枚 token 会不会被接受”，没有把目标模型内部真正的 MoE 专家调用与 GDN 状态恢复成本完整纳入。

GDN 与全注意力不同：它以递归矩阵保存历史，在同一个验证轮处理 16 枚候选时，要能在只有前 3 枚被接受的情况下把状态准确恢复到第三枚。若每一枚都保存状态，内存很贵；若每次回放重算，速度很慢。MoE 的成本也不是简单的 token 数乘固定值；两个 token 若路由到相同专家，其额外成本可能比启用全新专家小。对单请求而言，distinct expert 的数量更贴近真实 kernel 工作量。

作者所做的瓶颈 profile 很关键：Qwen3.6-35B-A3B + DFlash，在验证长度从 4 增至 16 时，目标验证时间上涨 71%；对照的 Qwen3-4B dense target 只上涨约 4–6%。这个差异是实验观察，不是对所有硬件和所有 GDN 的普适定律。论文研究的是 single-request 低并发场景的 token 生成速度，并没有证明在 32、64 或更大持续批调度下全部收益仍能保持。

03. Core Insight：把验证看作资源投资

核心判断不是“预测接收多少 token”，而是“追加这一枚 token 的预期收益能否覆盖其额外 GPU 时间”。更长验证最多多接收一段前缀，但后面 token 的接受概率一般依次降低。与之相反，GDN 递归更新、MoE expert 激活和 graph launch 的成本随候选长度非线性变化。于是必须综合估计 tokens gained 和 time paid，不能只看接受率。

第二个洞见是 target 的 MoE 路由结果只有运行 target 才知道，但为了完整验证也不需要立刻跑完所有专家。把计算截在第一个 MoE router 之后，便能用已经得到的 expert assignment 判断多处理一个 token 是便宜还是昂贵；这叫 router-boundary correction。若新 token 复用专家，可能值得让它进入后续层；若打开很多新专家，宁愿少算一点。

第三个洞见来自 GDN：验证的全部 token 输入已知，递归方程可以按块转换为下三角线性系统。于是每个 token 不必严格一个接一个执行，也无需每个位置保存完整 S。最终只恢复真正被接受前缀对应的状态。此处更像为固定短块设计的结构化算子内核，而不是训练新模型或近似丢弃历史。

这三者分工很清楚：length selection 控制高层调度，router correction 提升成本估计精度，parallel GDN 降低底层每轮固定与长度相关开销。它们的结合可能产生超加性效果，因为长度决策必须以真实 kernel latency 曲线为依据；把一个优化组件拆开单独放进旧框架，收益并不一定可复现。

04. Method Deep Dive：完整推理回路

Input → drafter 输出候选 block → drafter-only 接受概率及延迟曲线估计 → GPU 端选择 nominal length w0 → Stage 0 运行前 w0+1 枚到第一层 MoE router → 依据 distinct experts 决定额外 token 是否值得保留 → Stage 1 只完成选中 token 的后续验证 → 比对 target 与 draft 并确定接受前缀 → GDN compact state reconstruction → 输出 token 并进入下一轮。

步骤一，预先标定。按 target 与 drafter 配对在 calibration prompts 上记录不同验证长度的 GPU 时间、每位置接受率以及专家复用信息，拟合成本模型。运行时 GPU 上的选择器读取 drafter 置信特征，估计每个候选长度 w 的 token 产出 G(w) 和时间 L(w)。不做每次 CPU 读回，否则分支控制的 CPU–GPU 往返本身会吞掉性能。

步骤二，长度选择。枚举可行长度，对每一个计算类似 G−ρL 的分数，再选分数最大者。ρ 代表参考工作负载的 pooled token throughput。不能只看平均每轮 G/L，因为服务总体吞吐是“总完成 token/总时间”，而不是各轮单独速度的普通平均。论文附录还说明 latency 曲线可能非凸或非单调，因此没有采用遇到第一个差值为负就停止的贪心法。

步骤三，Stage 0 只处理 Layer-0 GDN + router。先按照 nominal w0 再多向前探一枚 token，保存被访问的 hidden states、residual 和 routing weights。利用 CUDA Graph conditional node 从 GPU 发起匹配长度的已捕获图，避免选定长度回到 CPU 再发命令。额外 token 虽然被运行到了 router，但若最后没有留下，其后续大量专家和 GDN 计算并不会发生。

步骤四，route correction。用实际新开专家数替换事先的平均成本预估，仅在额外 token 的 expected acceptance benefit 超过 runtime price 时保留它。注意这不是对 token 内容的真值裁决，只是在验证前控制硬件工作量；最终 token 是否被接受仍由 target 分布决定。

步骤五，Stage 1 恢复 Layer-0 边界之后的验证，执行选中长度，target logits 与 drafted tokens 相比确定接受前缀。在 GDN 层中使用块并行解法，不为每个候选完整存储 S_i，而是保留用于最终恢复的紧凑因子。若只有前 m 枚被接受，就恢复到第 m 枚；之后下一轮从这个状态继续。

步骤六，输出与检查。greedy 模式下对已接受前缀按原目标规则推进，采样模式理论上使用保持分布的 speculative sampling 规则。作者明确将 exactness 证明限定在精确算术；实际 BF16 浮点实现中接近相等的 logits 可能改变个别 token，因此还必须做下游任务非劣性检查，不能仅凭数学公式宣称逐 token bitwise 一致。

05. 核心公式：吞吐目标、GDN 与短块求解

GDN 一头的递归写成 z_i=β_i(v_i−α_i S_(i−1)k_i)，S_i=α_i S_(i−1)+z_i k_iᵀ，输出 o_i=S_i q_i。这里 S 是 d_v×d_k 的历史矩阵，k、v 是当前键值，α 为状态衰减系数，β 为写入强度。α 小会更快忘记旧内容，β 大会更激进更新当前值；这两者是已训练目标模型内部量，不是 HybridSpec 在推理时任意设置的调参旋钮。

将递归展开得到 S_i=e^{g_i} S_0+Σ_{j≤i}e^{g_i−g_j}z_j k_jᵀ，g_i=Σ_{j≤i} log α_j。一个短块内所有 token 都已知，可把 z_i 的相互依赖组织成单位下三角 H，解 HZ=diag(β)(V−diag(e^g)K S_0ᵀ)。关键不是改变数学语义，而是用短块矩阵运算并行求解依赖。附录 D.2 对不同块长使用专门逆矩阵构造；最长测试至 16，不代表任意长块都应直接求逆。

在调度层，设 p_i 为第 i 枚候选前缀全部通过的估计概率，则本轮期望输出 G(M)=1+Σ_{i=1}^M p_i。额外的 1 是 target 自身产生的 bonus token。L(M) 包括 drafter、target、graph 调度、接受和状态提交的预期轮次时间。真正吞吐目标是 ΣG/ΣL，不是 Σ(G/L)。优化可转为每轮选择使 G(M)−ρL(M) 尽量大的长度，ρ 由校准工作负载估算。

公式的经济学直觉非常直观：追加 ΔM 个候选仅在 ΔG>ρΔL 时有利。即使额外 token 几乎必然被接受，若它导致太多新 expert 被加载、令 ΔL 大于每 token 预算 1/ρ，也可能不值得验证。反之，即使某个额外 token 的接受概率不高，若它完全复用现有专家、延迟几乎不增加，也可能值得保留。

与 strongest baseline EVICT 的区别不只是阈值大小。EVICT 根据已有 draft 置信度和估计成本裁剪候选链；HybridSpec 把已观察到的 Layer-0 expert 激活纳入第二阶段，并使 GDN 恢复更便宜。若把该策略直接迁移到普通 dense model，专家复用部分不再有意义，收益可能只剩核调度或低层 kernel。

06. Toy Example：验证 16 枚为何不一定最好

假设一轮 drafter 生成 15 枚 token。可选 target 输入长度 w 包括 bonus 位置。w=4 时预期输出 3.2 枚、target 轮次 2.0 ms，速度 1.6 token/ms；w=16 时预期输出 4.8 枚但由于 GDN 与新专家开销耗时 4.0 ms，速度反而只有 1.2 token/ms。这里的数据是为了说明目标函数的自构示例，并不是论文测试。

假设校准 ρ=1.5 token/ms。从短窗口延伸需要多 2.0 ms，预期仅多 1.6 枚，ΔG−ρΔL=1.6−3<0，因此不合算。若 Layer-0 router 发现第五枚 token 只复用已在本轮加载的专家，增加完整验证的成本仅 0.1 ms，而它的前缀存活概率 0.5，增益 0.5−1.5×0.1>0，则把它加入验证。

完成 target logits 后发现前三枚通过、第四枚不通过。此时 GDN 的正确状态应该是接收前三枚后的状态，绝不能保留先前为了估计成本跑到第五枚或完整验证时使用的状态。HybridSpec 用压缩的块内解重构前三枚的状态，然后根据 target 的输出继续下一轮。若写成“先跑到第五枚并直接提交状态”，哪怕当前输出文本恰好正确，下一个生成 token 也可能受到未来猜测污染。

Toy Example 说明为什么调度控制、router 可观测信息和 state commit 必须共同设计。只做前两者容易赢得表面延迟，却牺牲语义正确性；只优化 GDN kernel 而不调整过长验证窗口，则仍会把算力花在高概率被拒绝的尾部 token 上。

07. Baseline 比较与 strongest baseline

Baseline 一是 AR target，每次真实生成一枚 token，不做 drafter 推测。它没有额外验证机制，结果定义 SR=1；在部分最不适合推测的短且高熵任务里，AR 甚至可能接近乃至超过未经优化的 speculative 方案。

Baseline 二是 vanilla DFlash，它用相同 draft 模型一次猜测完整窗口，target 全部验证，优点是实现简单、AL 往往最高，劣势是混合架构中验证后半段成本高。它是最直接的工程效果参照：HybridSpec 不靠更好 drafter 获胜，主要靠少算目标模型。

Baseline 三是 D-Cut，基于 draft 置信度选固定比例窗口，合理而高效，但对每轮复杂 MoE routing 的事后信息利用不足。Baseline 四是 EVICT，代表另一类自适应 verification truncation，表 1 中经常比 D-Cut 更强，是本文在适应性长度策略上的 **strongest baseline**。Baseline 五是 ReplaySSM，以及 EVICT + ReplaySSM，后者同时尝试剪裁长度与优化 GDN 复现，是最接近本文组件组合的强控制组。

作者为公平比较让这些 SD 方法使用同一个 DFlash drafter，并将 D-Cut/EVICT 映射到 DFlash proposal chain；ReplaySSM 使用 SGLang 默认实现。必须注意某些 baseline 并非天然为该硬件和模型设计，其默认 kernel 参数可能不最优，所以跨实现速度优势包含系统工程细节。作者的“更快”是 SGLang 0.5.16、A100 80GB、指定模型与请求并发下的结果，不是算法理论普遍性。

08. 实验设置、Metric 与研究问题

主要模型为 Qwen3.5-35B-A3B、Qwen3.6-35B-A3B 和 Qwen3.5-122B-A10B-GPTQ-INT4，使用对应官方 DFlash drafter。运行于 SGLang 0.5.16，硬件为 NVIDIA A100 80GB，主结果每次只服务一个请求。测试来自 SPEED-Bench Qualitative 的七类：coding、math、reasoning、RAG、summarization、writing、roleplay。校准和测试各 280 prompts，每类 40；不在测试集调阈值。作者还在另外四个未见类别测试，无重新校准。

主指标 SR 是 pooled decode token throughput 相对配对 AR 的倍数；统计包括真实 decode 的 CPU control、graph dispatch、同步和 padding，但不包括前置 prefill。AL 是完成 token 数/验证轮数，含 target bonus token。二者方向均是更高越好，但只提高 AL 而不降低每轮时间可能恶化 SR。另一个相关指标是 end-to-end task accuracy：不能单凭数学精确性排除 BF16 数值路径差异。

Research Question 1：GDN–MoE 的验证开销是否随长度超线性上升？Figure 1 的 71% 增长正面回答。Question 2：选短窗口是否真正加速而不是简单减少接受长度？Table 1 同时报告 AL 与 SR，正是为此设计。Question 3：选择器、router correction、GDN 内核哪个贡献最大？Table 3 给出替换式消融。Question 4：收益是否仅在训练过的七类成立？Table 2 的四个未见类别提供有限泛化测试。Question 5：内核是否牺牲了正确性与内存？Table 5 的 kernel profile、附录 D.3/D.4 的对齐实验和状态显存开销提供证据。

硬件依赖是直接的：CUDA Graph conditional node、A100 上特制 GDN kernel 以及专家路由成本剖析都是部署假设。若改为 AMD、Ascend 或不同 MoE kernel，必须重新拟合 cost、检查 graph runtime 支持和内核架构。TPS 与 SR 必须同 prefill 设定、输出限额、随机种子、温度、batch 下比较。

09. Results：八项可验证定量证据

结果一，Figure 1 的单请求 profile：Qwen3.6-35B-A3B 验证长度由 4 增至 16，target 时间上涨约 71%；对照 Qwen3-4B dense 的增加只有约 4–6%。这表明在混合 GDN–MoE 上照搬 dense model 的长验证经验会误判成本。

结果二，Table 1 中 Qwen3.5-35B-A3B 平均 SR，DFlash 为 1.45×、HybridSpec 为 1.88×；相对前者约 1.30×，说明长度与内核调度在固定 drafter 前提下有额外收益。

结果三，Qwen3.6-35B-A3B 的平均 SR 从 DFlash 1.37×到 HybridSpec 1.83×，约 1.33×；AL 反而从 4.79 下降到 4.57，正好构成全文最关键的反直觉证据：接受更少但每枚输出更快。

结果四，大模型 Qwen3.5-122B-A10B-GPTQ-INT4 的平均 speedup 处于作者所述 1.75–1.88× AR 区间；相关类别的 DFlash roleplay 甚至仅 0.95× AR，说明未经截断的 speculative decoding 会在某些输入上变慢。

结果五，Table 3 对 Qwen3.6-35B-A3B：HybridSpec 1.83×；改用校准后的固定长度 7 为 1.54×，说明自适应选择贡献约 1.19 倍；固定 16 更只剩 1.46×，相对差约 1.25 倍。

结果六，Table 3 去掉 router correction 保留 nominal 选择，SR 从 1.83×到 1.73×，对应 1.06×；替换为 SGLang 默认 GDN kernels 则降到 1.74×，约 1.05×。这两项是较小但可量化的机制增益，不应与 length selection 的总体收益混算。

结果七，Table 2 未见类别上 Qwen3.6-35B-A3B，DFlash 平均 SR 1.31×、HybridSpec 1.69×；其中 Multilingual 从 1.57×到 2.01×。同一表里 AL 从 4.35 下降到 4.06，说明模型并不通过“让 drafter 更准确”而获得提升。

结果八，Table 5 的 30 个 GDN 层整段 kernel：w=4 时 SGLang 0.5920 ms、HybridSpec 0.3847 ms，约 1.54×；w=16 时 1.9111 ms 对 0.4728 ms，约 4.04×。大块下更高的微基准加速不能直接当成完整 serving 的 4 倍，因为其他层、draft、graph 和同步仍有开销。

正确性与质量也有边界：附录在 GSM8K 1319 题测试上 HybridSpec 96.06%、DFlash 96.21%，低 0.15 个百分点；作者报告以预设 −1 点为非劣性界，单侧 95% 下界 −0.71 点，但它仍不是严格 bitwise 等价。这里的差异可能来自 BF16 运算顺序而非逻辑错误，不能用来证明所有采样温度下绝不会改变答案。

11. Claim vs Evidence 与 Contribution

Authors Claim：HybridSpec 对混合 GDN–MoE 模型提供吞吐感知的验证长度、MoE 路由修正与高效状态重构，而且在精确算术中不改变 target 解码分布。Experiments Actually Show：指定 Qwen 混合模型、SGLang/A100/单请求条件下，多个类别的 decode SR 明显优于同 drafter baseline；内核微基准和替换消融分别支持其贡献。What Is Not Yet Proven：所有生成 token 在 BF16 下完全一致、任意 batch 大小与硬件均稳定盈利、不同 MoE 专家映射模型可复用相同校准曲线、长上下文 KV 压力下没有额外瓶颈。

Contribution 1 [New Objective / Engineering]：使用总 tokens/总时间而非平均单轮 ratio 的 throughput-aware 长度选择；Dinkelbach 变换是已有数学工具，贡献在 runtime 特化应用。Contribution 2 [New Mechanism]：在第一个 MoE router 后动态决定额外 token 是否值得继续执行，依赖观察到的 expert assignment。Contribution 3 [New System]：适用于短验证块的 GDN 并行求解与只恢复接受前缀状态。Contribution 4 [New Empirical Finding]：接受长度降低但 TPS 上升，以及 distinct expert 预测比 token 数更接近硬件成本。

对“lossless”须分层讨论：数学上选定 M 不改变标准推测验证的目标输出规则；实现上 BF16 的运算顺序、图调度和 kernel 重构可能出现微小 logits 偏差；任务上 GSM8K 0.15 点差异在统计容差内，但不能推出在所有高风险任务上的严格逐字一致。作者在附录列出单轮两阶段分割正确性对照，还在正文明确代码计划接收后发布；当前不能把代码仓库状态写成公开已可复现。

12. Limitation、复现视角与系统指标

作者的明显约束是目标类别较窄：混合 GDN–MoE、同一组官方 DFlash drafter、三种模型、指定硬件环境。更广泛的生产系统还需验证多租户 continuous batching，CPU/GPU 调度竞争，跨 GPU expert parallel 通信，以及带长输入的 prefix cache。单请求更容易观测到 router 局部差异；大并发下每个 expert kernel 的 batch shape 和复用规律会改变。

复现应从不修改 target 的 DFlash 跑起，记录 AR 与 DFlash 在 280 测试 prompt 的逐请求 TTFT、decode TPS、AL、每轮验证长度、专家分配与 kernel 时间。首先固定单请求和相同输出限额，确保表 1 指标可重算。其次在自己的 GPU 上扫 w=2..16，按长度拟合 C_target(w)，记录所有 Layer-0 distinct expert 数与端到端 verify time 的相关性。再实现 GPU 居留选择器并与静态长度 7/16 比较。

第三阶段才实施 conditional CUDA Graph 的两阶段 Stage 0/Stage 1；如果设备不能支持，先使用普通 host dispatch 版本验证逻辑，再量化 host round-trip 的成本。最后加入 GDN triangular solver 和 accepted-state commit。必须做对照：对随机 token 块，用默认逐 token GDN 得到 S_m；新 kernel 只提交前 m token 时的 S_m 要在指定容差内相同，覆盖 m=1、m=w/2、m=w、不同 β 和 α 的数值极端情况。

关键指标表：TTFT=Not Reported（主报告是 post-prefill decode）；TPOT=Not Reported（未统一给逐模型完整 TPOT 表）；Tokens/s=用归一化 SR 形式报告；Throughput=1.75–1.88× AR；GPU Memory=附录报告 GDN state buffer 减少，Qwen3.6-35B-A3B 的原 1.88GB 变成更小的 compact factors；KV Memory=并非本方法主要优化对象；FLOPs=Not Reported 的全模型统一降幅；Quality=GSM8K 96.06% vs 96.21%。图示中 w=16 的 GDN kernel 提速 4.04×，不等于总延迟等比例下降。

额外风险是 cost model drift：不同文档长度、输出 entropy、并发量改变 p_i 和 expert hit 率。若 rho 校准过高，选择器会过度偏好短块；过低可能浪费算力验证长块。应记录校准与测试的分布差异，用 shadow traffic 对成本模型做周期更新，并报告更新频率、额外显存与能耗，而非只给峰值速度。

13. Research Value、迁移方案与验证攻击

Baseline Potential：高，固定 drafter 使 HybridSpec 能作为推测解码系统调度的强对照。Migration Potential：高，预算约束下按“额外收益/额外真实时间”决策可迁移到视频帧预算、VLM token 选择与 Agent 验证长度。Systems Potential：高，CUDA Graph 路由边界、GDN state 重构与成本模型各自可独立工程化。Attack Potential：中，可用极端专家多样性输入触发 cost 估计失效。Evaluation Potential：高，AL/TPS/正确性三联指标是避免只看 FLOPs 的好模板。Benchmark Potential：高，构造控制 expert fanout、entropy、上下文长度的系统 stress set。New Paper Potential：取决于能否在高并发和跨硬件场景得到可泛化收益。

迁移 A，Original Problem：长视频 VLM 每个查询不需要同样多帧，但帧编码与视觉 token 选择消耗真实时间。Transferable Mechanism：预估质量收益与真实时间成本，先少量试探，再依据已观察到的视觉 evidence 决定是否扩大预算。New Research Question：动态帧数由“回答质量增益/延迟”决定，会比纯相似度 top-k 更有效吗？Method Modification：用轻量帧选择器给出 top-2/4/8/16 关键帧，并以两帧预览获得 query-conditioned uncertainty，只有 expected accuracy gain 大于 λ×额外 GPU 时间时继续。Minimum Experiment：Video-MME 选 1000 问，固定一款公开 7B/8B Video VLM，在单张 GPU 上对 2/4/8/16 帧记录真实 prefill、decode、end-to-end latency，训练小成本预测器。Model：LLaVA-OneVision。Dataset：Video-MME。Baseline：uniform 8帧、固定 top-k、uncertainty-only、oracle dynamic budget。Metric：accuracy、95th latency、FPS、visual tokens、GPU memory、Pareto AUC。Expected Contribution：构建 runtime-aware frame budget 选择范式。Risk：探测帧开销超过加速收益。Collision Risk：与 adaptive frame sampling 和 query-aware video pruning 高度重叠，必须查新。

迁移 B，Original Problem：Agent 生成工具调用时，验证所有候选计划会浪费大量 target tokens 和工具环境步骤。Transferable Mechanism：在便宜的早期路由节点观察可测成本，再选择下一阶段验证预算。New Research Question：能否根据候选工具计划之间的共享技能/工具模块降低 rollout 成本？Method Modification：将工具 schema 分类看成“专家路由”，先用小模型提出 4/8/16 个动作候选，仅执行低成本 validity check，按已观察到的工具复用与预期成功增益筛选完整 sandbox rollout。Minimum Experiment：ALFWorld 200 个测试任务，Qwen2.5-7B 为候选生成器，冻结更强评估器或环境 verifier；记录候选数、成功率、总环境调用数与每任务 wall-clock，比较固定预算 4/8/16、置信阈值、自适应两阶段预算。Metric：task success、verified actions/s、total cost、无效工具调用数。Expected Contribution：cost-aware Agent planning，不仅提升 token 生成速度。Risk：早期工具类别复用并不一定反映真实执行成本；reward hacking 可诱导过早停止验证。Collision Risk：与 tool-use RL、adaptive search-depth 方向存在潜在重叠。

Attack/Verification Lens：设计 adversarial prompts 让 MoE 每个候选激活不同专家，测实际 verify latency 和预测偏差；另设长上下文与近乎相等 logits，比较 HybridSpec 与 AR 逐 token 结果、任务正确率及数值误差。黑盒 probe 可以在相同 token 预算下只改变任务文体，测 SR 是否因 expert diversity 波动；没有 profiler 时不应反推出具体 expert identity。建议新指标 Cost Model Calibration Error=(预测 verify time 与实际时间的差)/实际时间，及 Acceptance–Throughput Inversion Rate（AL 高但 TPS 低的请求占比），这是本报告建议而非论文已提出的 metric。

14. 十句话记住本文

第一，HybridSpec 研究的是混合 GDN–MoE target 的推测验证成本。第二，长窗口可能增加 AL 但降低 throughput。第三，单请求 profile 给出长度 4 到 16 时验证时间增加 71% 的例子。第四，选择器优化 pooled emitted tokens 除以 pooled time。第五，GPU 端长度选择避免 CPU round trip。第六，在 Layer-0 MoE router 后看实际专家复用，能决定是否多保留一枚候选。第七，GDN 通过短块下三角求解减少逐 token 状态保存。第八，表 1 上三款目标模型比 DFlash 有明显增益。第九，微基准 4.04 倍不能等同于全系统 4.04 倍。第十，迁移到视频或 Agent 时必须重新测真实 wall-clock 和质量损失。

Cross-Paper Synthesis · 联合研究判断

共同趋势是把 speculative decoding 从“固定模型 + 固定验证窗口”的单层算法问题，拆成 训练的接受分布 与 运行时的单位时间收益 两个可优化层。SpecOPD 让 drafter 在自身错误条件历史上接受更直接的目标监督；HybridSpec 让 target 验证只消耗值得消耗的硬件时间。前者是供给端，后者是需求端：一个改善可接受候选的分布，另一个决定每轮购买多少候选计算。

机制互补意味着可以有联合基线，但也意味着不能假设收益乘法叠加。SpecOPD 改善 prefix survival 会改变 HybridSpec 最优验证长度、expert footprint 和校准的 ρ；HybridSpec 在同一 accepted-length 分布下可能选择短窗口以降低 GDN–MoE 成本。两篇并没有在同一 target、同一 drafter、同一硬件上给出联合实验，因此 Strongest Collision 标记为“可检验的目标不一致”，而非已有论文抢先完成。

机会 A：Cost-Aware Drafter Distillation。 将 E2E-TV 的前缀存活目标加入真实 target 验证成本：不只最大化 E[AL]，而是尝试学习最大化 E[emitted tokens]/E[target verification milliseconds]。实施先在相同 Qwen hybrid target 上训练 baseline E2E-TV、cost-weighted E2E-TV，再配置静态 DFlash、HybridSpec 两种 verifier，形成 2×2 因子实验。主要证据是四种组合的 AL、TPS、训练成本和质量一致性。由于目标与设备耦合，必须报告跨 GPU 泛化。

机会 B：动态预算的学习/推理一体化。 面向 Agent 或 Video，可以把 branch-local training 与 runtime-cost-aware scheduling 组合，学习在什么状态多算、什么时候停止，但不能把“专家复用”想当然地等价为“视频帧相似”或“工具调用可复用”。最小验证从固定日志回放开始，再在在线系统测真实成功率与端到端延迟。潜在 benchmark 维度包括概率熵、prefix survival、上下文长度、expert diversity、batch concurrency、可恢复状态成本。

Collision / Overlap。 与已有的 on-policy drafter distillation、EVICT、D-Cut、DSpark、Bebop E2E-TV 等密切相关，联合研究需要明确新增的 cost-aware objective 和非平稳校准协议，而不是把两个现成模块直接拼装宣称全新机制。优先级：要快速复现从 HybridSpec 的静态长度及 ablation 入手；要发展训练论文从 SpecOPD 8B 分支独立评分测试入手；要发展系统论文从混合模型动态成本与吞吐折中入手；要发展 metric/benchmark 从 AL 与 TPS 的反向排序入手。
