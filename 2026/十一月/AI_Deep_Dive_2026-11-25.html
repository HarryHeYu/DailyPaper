论文 1｜Language Model Harnesses can be Compositional Generalizers：在神经符号 harness 里把组合泛化做成可训练的局部策略 NEW Agent / Multi-Agent × RL

1. 基本信息

标题：Language model harnesses can be Compositional Generalizers
作者：Alex L. Zhang, Souradip Chakraborty, Omar Khattab（MIT CSAIL；通讯 altzhang@mit.edu）
arXiv：来源：abs · pdf · html · 12 页正文，含附录共 63 页 · 提交 2026-11-20 · cs.CL
代码：github.com/alexzhang13/harness-cg；SFT 轨迹 a1zhang/synthetic-rlm-sft-data（论文脚注；仓库可运行性 Not Verified）
方向：Agent / Multi-Agent × Reinforcement Learning

2. 一句话定位

这篇论文要论证的不是“再给智能体加一个工具”，而是：如果 harness 能把全局新任务切成局部仍可解的语言模型调用（作者称为 locally in-distribution，LID），那么只需在短任务或合成替代环境上训练根策略，就可以组合出更长、跨域甚至递归的求解行为。

3. 人话版

想象一个项目经理（根模型）并不把整份卷宗塞进自己的工作记忆，而是把材料放在共享文件夹里，自己只写一段可执行的分工脚本：先切段、再派若干短上下文同事去标注、最后在代码里汇总。同事每次看到的都是他们本来就会做的短任务；经理每次看到的，也只是“如何分工”这类相对稳定的程序，而不是不断膨胀的聊天记录。训练时，你甚至不必让经理在真实的百万字卷宗上熬夜——可以先用一本结构相似、材料更便宜的假卷宗，教会他那套分工脚本。换一本更厚或题材不同、但分解结构相近的真卷宗时，这套脚本仍能复用。这就是文中的 Recursive Language Model（RLM）路径，相对 ReAct 那种把全部轨迹当作提示词往上堆的做法。

4. 背景与缺口

现代语言模型作为智能体部署时，几乎总是待在某种 harness 里。主流“trajectory-as-a-prompt”设计（ReAct 及其后裔）让编排模型在每一步看到不断变长的历史。作者指出，这等于把长度外推和轨迹分布外推的负担，重新压回 Transformer 本身：训练时常要在目标环境上滚完整轨迹，换一个 harness 或领域又得重新收集数据。经验上，即便子问题单独可解，输入一变长或换一套用词，模型仍会退化，多轮里还会出现 context rot。

缺口因此是双重的。第一，组合泛化在纯神经网络里仍然不可靠，不能指望“把更长的任务再拿来训一遍”就能便宜地外推。第二，现有的 coding agent 抽象——上下文外置、程序化工具调用、子智能体——已经被广泛使用，但缺少一个可检验的说法：这些抽象究竟如何降低泛化负担，以及它们能否被强化学习真正学到、并迁移到训练时没见过的长任务和跨域任务。作者把讨论放在文本级分解，而不是回路级的神经机制解释。

5. 核心 insight

核心判断是：harness 的价值在于把全局 OOD 任务改写成一组局部仍“像训练分布里会出现的提示”的调用。LID 并不要求每条局部提示都在训练集里出现过，只要求根策略写出的分解，能把子调用送到模型已经靠谱的能力范围内。只要根轨迹在更长或跨域任务上仍然相似，并且被委派的子任务确实执行正确，组合泛化就不再完全依赖 Transformer 对超长提示的外推。

由此推出训练策略：不必总在真实长程环境上对整条 rollout 做 RL。可以针对 harness 里某一个语言模型（通常是根模型）构造合成替代环境，甚至用假工具 / 假子调用，专门训练它的分解程序；真实工具在评估时再接回去。若分解程序本身也能被当成子 harness 递归调用，新学会的求解器又可以成为更大任务里的可复用组件。

6. 方法逐步拆解

第一步，固定可比较的 harness 抽象，而不是做任务特化脚手架。基座 Transformer 代表把全部上下文当作提示的路径；评测超出窗口时对它使用 YaRN。Pi-mono 代表带终端、压缩和子智能体的 ReAct 循环，并把长上下文外置到文件。LM + REPL（CodeAct）保留程序化工具调用和上下文外置，但去掉程序化子智能体与输出截断，用来消融“会写代码”是否足够。RLM 同时使用上下文外置和程序化子智能体；正文采用 depth=1，以便与常见 coding agent 的子智能体调用对齐。

第二步，在可控的短任务上做 RL，再看长任务和跨域任务。长度泛化（表 1）只在短划分上训练，评测同一任务族的 2–64 倍更长划分：MRCRv2 从 32K–64K、2-needle 到 2M–4M、8-needle（64×），Ada-LEval 从 8K 到 128K（16×），其余为 2–8×。策略泛化（表 2）则换领域、保留分解结构，例如 OOLONG 的 trec-coarse（32K）迁到 spam（132K），OBLIQ 的写作类比迁到数学类比。除 Pi 对根和子智能体都计损失外，RLM 的损失只落在根轨迹，子调用 token 不进损失，类似于 Recursive Agent Optimization、且没有额外的委派奖励。

第三步，诊断 LID：根轨迹是否被复用，子任务是否真的做对。作者用加权 Jaccard 等 token 级相似度，比较训练成功轨迹与长评测轨迹；并在有中间标签的任务（如 OOLONG）上直接计算被委派子任务的准确率。图 5 还把每条长评测轨迹与最邻近的三条训练轨迹的奖励加以对照，用来说明“根轨迹像”并不自动等于“奖励能迁过去”——Pi 在 OOLONG 上就是反例。

第四步，surrogate harness training。对表 3 的八个更脏、更难的长基准，作者用 Opus 5.5（经 Claude Code）阅读公开的非评测划分与若干基座 RLM 轨迹，提出候选 LM 程序，再构造上下文不重叠、但同一套程序也能解的合成环境。BrowseComp-Plus、ExpertLongBench、OBLIQ 上的子调用可换成预置的 oracle 假回答。然后把候选程序当作提示，让 RLM 在合成环境里打轨迹，用 GPT-5-mini 评判加环境奖励筛样，得到 8,015 条仅根轨迹的合成 rollout，以及 LongReason 上 1,465 条子智能体轨迹。RLM-27B 是对 Qwen3.8-27B 做全参数 SFT 的产物；作为对照，也在同一批合成环境上、关掉提示，直接做 RL。

第五步，递归组合。从 RLM-27B 能解（avg@3 为 97.5%）而 Qwen3.8-27B 不稳（57.7%）的 87 个任务中，随机抽四个排成元任务：必须按顺序解对才能解锁下一题。默认设置把四题拼在同一条根轨迹里；进一步用替代训练教模型“先解当前题，再对剩余任务启动子 RLM”，把已学会的求解器递归装回去。

7. 核心公式

正文把 LID 主要当作经验现象来写，定量分解放在附录 D。把根策略写成 πH，局部执行（含子调用）写成 πL，任务 (x,c) 上的期望奖励为

Jp=𝔼(x,c)~p𝔼z~πH(·∣x)𝔼y~πL(·∣z,c)[R(x,y)]⏟Qx(z,c)

这是附录式 (5)：根模型只负责写出分解 z，真正得分是局部执行的价值 Qx(z,c)。训练任务 (x,c) 与测试任务 (x′,c′) 的差距可以拆成

J1−J2=(𝔼z~πH(·∣x)Qx(z,c)−𝔼z~πH(·∣x′)Qx(z,c))⏟(A) root controller shift+𝔼z~πH(·∣x′)[Qx(z,c)−Qx′(z,c′)]⏟(B) execution / sub-call shift

式 (7) 的意思很直白：(A) 是根控制器有没有写出“测试任务也用得上”的分解；(B) 是同样的分解在测试上下文里，子调用是否还能执行好。LID 要同时压低这两项。附录给出的保证（式 (13)）把测试奖励下界写成

Jq≥Rmax−ϵtrain−RmaxϵH−ϵL

即测试表现至少是：最大可达奖励，减去训练误差、根抽象偏移，再减去局部执行偏移。变量直觉：ϵH 小，说明根轨迹在新任务上仍像训练时学会的程序；ϵL 小，说明被派出去的子任务仍然在模型能力圈内。训练时 RLM 的损失只加在根助手 token 上，正是在直接优化 (A) 这一侧，而把 (B) 交给已有能力和 LID 分解。

8. Toy example

以 OOLONG 为例。短训练划分大约是 32K token、trec-coarse 标注；长评测划分把同类问题 bulk 到 256K。纯 Transformer 必须在更长的提示里“自己再学一遍如何扫完全文”。RLM 的根模型若在短任务上已经学会“按行切块、批量调用子模型做六分类、再在 REPL 里汇总”，那么到 256K 时它只需把同一段程序多跑几轮。子调用每次只看到一行或一小段，输入分布几乎没变。表 19 给出直接证据：OOLONG 上被委派的单行标注，训练准确率从 86.1% 到 85.6%，评测从 81.7% 到 83.7%，两边都维持在可用水平。跨域时把 trec-coarse 换成 spam，评测子任务准确率甚至从 70.6% 升到 87.3%。相反，若根模型学成“只读固定几页、或手写一长串中间列表”，提示再像，奖励也会在更长输入上掉下去——这正是 Pi 在图 5 中的失败模式。

9. Baselines

  • Base Transformer + YaRN：代表 trajectory-as-a-prompt；长上下文靠模型窗口或 YaRN 硬撑，是“没有外部化上下文”的下界。
  • Pi（base / 短任务 RL）：现代 coding agent 的最小抽象（ReAct + 子智能体 + 文件外置）。用来检验“会派子智能体”是否已经足够。
  • LM + REPL：会写代码、能外置上下文，但不能程序化地扇出子智能体。用来分离“程序化求解”和“语义子任务组合”。
  • RLM（base）以及 + RL（短任务 / 合成任务）：同一 harness 下的基座、短任务 RL 和合成环境 RL，用来把训练数据来源与 harness 本身分开。
  • 参考点 GPT-6 Astra + RLM：图 3 中的前沿参考，不是同参数量对照，只提供长度外推的上限直觉。

11. 指标教学

任务分数 / 平均分：各基准自带指标，表 4 的 Avg. 是八个评测集的未加权平均。不要把 26.9% 读成“绝对百分点”——它是相对同一 harness 下 Qwen3.8-27B 基座的相对提升（58.5 对 46.1）。

回合、子调用、Delegates、Turn Cap：表 5 统计根回合数、平均子调用次数、至少一次委派的轨迹占比，以及撞上 40 轮上限的占比。Turn Cap 高通常表示循环或拖沓，而不是“更努力”。

Token 用量：根与子调用的输入 / 输出要分开读。摘要中的“约 2 倍更少”指推理期总 token；第 4.2 节另报根输入约 6 倍更少、回合约 3 倍更少，三套分母不同。

Partial / Full solve：四题链式元任务里，partial 是单题通过率，full 是四题全对的元任务比例；置信区间以元任务为独立单位。

加权 Jaccard 与子任务准确率：前者只说明根程序像不像，后者才说明局部计算是否可靠。

12. 可核验结果

  1. 短训到长评测：图 3 在六个可控长度环境上显示，RLM 的评测奖励更贴近训练奖励，基座 Transformer 则常常训得好、迁不走。外推倍数按表 1 为 2–64×。具体曲线高度以图为准，正文未把每个环境的终值写成单行数字。
  2. 策略迁移：图 4 在三个领域完全不同、分解结构相似的任务上，RLM 的评测奖励同样更跟得上训练奖励；Pi 与 LM+REPL 在需要稠密处理的 OBLIQ 上偏弱。
  3. 主结果，Qwen3.8-27B 同 harness：表 4 中 RLM 基座均分 46.1，短任务 RL 到 48.5（+2.4），合成环境 RL 到 52.9（+6.8），SFT 得到的 RLM-27B 到 58.5（+12.4 分，相对 +26.9%）。CTC 从 19.1 到 39.8，ExpertLongBench（ELB）从 53.1 到 71.2，LooGLE 从 51.4 到 82.0。BrowseComp-Plus 从 64.8 到 64.9，几乎持平，收益主要在轨迹效率。
  4. 效率：表 5 中 Qwen3.8-27B 的 RLM 基座为 18.4 回合、根 263K/5K、子调用 443K/10K（合计约 721K token），Turn Cap 32.9%。RLM-27B 降到 6.5 回合（约 3× 更少）、根 44K/3K、子调用 276K/62K（合计约 385K，约 1.87× 更少，与摘要“∼2× fewer tokens”一致），Delegates 升至 97.4%，Turn Cap 降至 1.1%。根输入 263K→44K，约 6×，与第 4.2 节文字一致。
  5. 较弱基座上的不对称：Qwen3-30B-A3B 的短任务 RL 把均分从 15.3 提到 22.3（+7.0），合成 RL 到 25.0；token 用量下降。作者明确写：弱模型更倾向少委派、改走程序化解法，强模型则更稳定地扇出子智能体。因此“短任务 RL 一定更省 token”不成立。
  6. 递归组合：表 6 中 RLM-27B 默认 full solve 为 55.2%±2.2；只加递归提示反而降到 47.2%±2.2；加上递归合成数据的 SFT 后升到 77.5%±1.8（partial 84.4%±1.4）。2000 条链。

14. Ablation

训练数据来源是主消融。对 Qwen3.8-27B，短任务 RL 只加 2.4 分且更费 token；合成环境上的无提示 RL 加 6.8 分、七个任务中七个上升，但“没有明显效率收益”，行为也与带教师提示的 SFT 不同；SFT 的 RLM-27B 同时拿到分数和效率。因此，合成环境本身有用，但“有没有提示轨迹、用 SFT 还是 RL”会收敛到不同策略。

表 8 把短任务混合拆成单环境训练：在本任务短划分上训练通常最强，但迁移不均，说明模型不只是“更会用 harness”，而是学到了可迁移的任务族行为。表 10–11 的宽混合（约 20 个真实任务族，训 1,000 步）在 Qwen3-30B-A3B 上把六集均分推到 31.6，只略强于合成 RL 的 31.0，说明“把更多真实短任务搅在一起”并不能自动解决表 3 那种更脏的长任务。附录图 7 去掉 RLM 的 orchestration hint 后，总体趋势仍在，但 MRCRv2 会学到不可泛化、并出现上下文窗口问题——提示并非无关紧要的包装。

15. Claim vs Evidence

成立得比较实的部分：在表 1 的受控长度轴和表 2 的策略轴上，RLM 的训练—评测一致性强于基座 Transformer，这个定性结论有图 3、图 4 和根轨迹相似度、子任务准确率两套诊断支撑。把 RLM-27B 与同一 harness 的 Qwen3.8-27B 相比，表 4 与表 5 的分数、回合、token、Turn Cap 是对得上的；26.9%、约 3× 回合、约 2× 总 token、约 6× 根输入，都可以从这两张表直接算出或与第 4.2 节文字对上。

需要收窄的部分：摘要把 26.9% 写在“CTC-Bench 与 ExpertLongBench 等”之后，但 26.9% 是八集平均的相对提升，不是这两个基准单独的相对提升（CTC 为 39.8/19.1−1≈108%，ELB 为 71.2/53.1−1≈34%）。合成环境是在了解目标任务族、并看到非评测划分与基座轨迹之后，由 Opus 5.5 设计的，属于针对性教学，不是通用自动课程。表 12 显示 CTC、ELB、OOLONG-Real、CorpusQA 的题干重叠偏高，LongReason / OBLIQ / BrowseComp-Plus 则低——平均分被不同污染风险的集合绑在一起。递归实验的 87 个任务是按 RLM-27B 已会、基座不会来选的，77.5% 不能外推到任意任务链。图 3、图 4 的纵轴终值在正文中没有逐点表列。

证据不足或未报：多种子稳定性 Not Reported；Pi / LM+REPL 在表 4 的八集上没有与 RLM-27B 同配方后训练的完整对照；GPT-5-mini 作筛样评判的一致性 Not Reported。

16. 贡献

  • 把 harness 抽象（上下文外置、程序化工具、子智能体）重新表述为对 LID 的结构设计，并用长度、策略两条轴给出可比较的 RL 证据。
  • 提出并实施 surrogate harness training：用合成环境甚至假子调用，定向训练 harness 内单个模型（主要是根策略），得到 RLM-27B。
  • 展示递归子 harness 可以把新学会的分解再组合，使四题链式 full solve 从 55.2% 升到 77.5%。
  • 提供轨迹相似度、子任务准确率和题干重叠统计，让“组合泛化”不只停留在口号。

17. 局限

RL 学到的 harness 行为不必是可组合的：同样的短任务混合，在弱模型和强模型上会走到少委派或费 token 的不同策略。Pi 与 LM+REPL 在需要稠密语义处理的任务上明显弱于 RLM，说明“会写代码或会派子智能体”不够。合成数据依赖对目标任务族的事先理解、专有教师模型和评判模型；假子调用在训练和真实延迟之间仍有差距（表 13–14 的 wall-clock 也不总是合成更快，例如 Qwen3.8-27B 在 CorpusQA 上合成均值是真实的 1.52 倍）。题干重叠在部分基准上偏高。主实验关闭 thinking，深度固定为 1。代码与数据链接已给出，但本报告未做可运行性审计。

18. 复现要点

先复现表 7 的 prime-rl 配置：GRPO、根 token 才计损失、LoRA 对 Qwen3 / 全参对 Qwen3.8、1,000 步短任务混合。长度泛化必须严格使用表 1 的短训 / 长评划分，并给基座 Transformer 加上 YaRN。要复现 RLM-27B，需要那 8,015+1,465 条轨迹和 32,768 打包 SFT 配方，而不是再跑一遍短任务 RL。评测要固定 40 轮上限，并把根 / 子调用 token、Delegates、Turn Cap 与分数一起报。若做递归实验，需按附录 B.11 构造解锁工具，并分清“只加提示”和“再 SFT”两个臂。验证 LID 时不要只看根轨迹相似度，要同时报子任务准确率，并核对表 12 的题干重叠。

19. 研究价值

它把“智能体泛化难”从模型尺度问题，部分改写成系统设计问题：只要局部提示落在能力圈内，长程训练数据就可以被更便宜的短任务或合成替代物替换。这对正在用 RL 训练 coding agent 的人很实际——与其只在 SWE-bench 一类完整轨迹上堆计算，不如先问：根模型真正要学的是哪一段程序。附录里的差距分解也为后续理论工作留了把手。

20. 可执行迁移

  1. 针对根策略做替代环境，而不是一上来滚真实长程轨迹。先写出你希望根模型产生的工具程序模板，再用假检索 / 假子调用生成几千条根轨迹做 SFT，最后在真实工具上评测回合数、Turn Cap 和分数。直接可对照的是本文表 4 对表 5 的读法：没有效率指标，分数提升可能只是更会“耗预算”。
  2. 把“会解单任务”升级成“可递归调用的子 harness”。若生产系统已经能稳定解一类工单，不要把多工单拼进同一上下文；用显式 handoff 开一条新的 RLM 调用。表 6 显示只加自然语言提示会伤害成功率，需要专门的递归轨迹，而不是一句 system prompt。

21. 方向专用分析

这是一篇 Agent×RL 论文，但后训练并不全是 RL：最强产物 RLM-27B 是 SFT，RL 被用来揭示“短任务可以外推”以及“无提示合成 RL 也能涨点但不省 token”。对智能体研究，真正可迁移的是 LID 设计原则——上下文外置加上程序化扇出，比把轨迹当作提示更利于组合。对 RL 研究，它提醒：奖励上升不等于学到可组合的根策略，初始策略会决定委派程度，损失记在哪一层（根还是子调用）会改变你优化的是式 (7) 的 (A) 还是 (B)。depth=1、关闭 thinking，也意味着这还不是对深度递归或多步推理预算的完整答案。

22. Attack / Verification

最需要盯住的是合成数据与评测之间的泄漏。表 12 已显示 CTC、ELB 等集合的题干 n-gram 重叠很高；验证时应要求作者同时报告低重叠子集（LongReason、OBLIQ math、BrowseComp-Plus）上的增益，并做“打乱合成程序模板 / 换成无关合成环境”的负对照。轨迹由带提示的教师生成、再经 GPT-5-mini 筛选，存在奖励黑客和评判偏差风险；应公开筛样通过率、人工抽检和去掉评判模型后的 RL-only 对照（文中已有合成 RL，但行为不同）。假子调用可能让根模型学会依赖“永远正确的同事”，在真实子调用变差时崩溃——可用故意降低子模型质量的压力测试。评测若只报均分、不报 Turn Cap 与 token，也可能掩盖靠耗尽回合“碰答案”的策略。

23. 记忆总结

  • LID：让每次模型调用看到的提示仍落在可靠能力圈内，而不是让 Transformer 硬啃超长轨迹。
  • RLM = 上下文外置 + 程序化子智能体；损失默认只加在根轨迹。
  • 短任务 RL 可以迁到 2–64× 更长，以及共享分解结构的新领域；基座 Transformer 迁得更差。
  • “根轨迹像”不够，还要看子任务准不准；Pi 在 OOLONG 上是反例。
  • 短任务 RL 在弱模型上 +7.0 分，在 Qwen3.8-27B 上只 +2.4 分，且后者更费 token。
  • 替代训练用合成环境甚至假子调用教根程序；RLM-27B 是 8,015 条根轨迹上的 SFT。
  • 同 harness 下均分 46.1→58.5（相对 +26.9%），回合 18.4→6.5，总 token 约 721K→385K。
  • CTC / ELB 等集合题干重叠偏高，26.9% 不能当成八个同等干净的零样本结果。
  • 递归提示不够，递归 SFT 才把链式 full solve 从 55.2% 拉到 77.5%。
  • 宽混合真实短任务不能替代针对性合成环境；要同时看分数和效率。

论文 2｜Grammar-as-a-Draft：把文法当成第二起草者，让每一步推测解码接受更多 token NEW Inference Acceleration

1. 基本信息

标题：Grammar-as-a-Draft: More Tokens per Speculative Decoding Step on Grammar-Constrained Structured Outputs
作者：John Zhang（通讯 johnqiangzhang@google.com）, Silky Arora；单位 Google
arXiv：来源：abs · pdf · html · 12 页，4 图 6 表 · 提交 2026-11-20 · cs.CL / cs.AI
实现：vllm-torchtpu PR #3321（论文声明；PR 中未在论文出现的数字不写入下文）。独立 Rust 运行时写作时未公开。
方向：Inference Acceleration（结构化输出上的推测解码）

2. 一句话定位

GaaD 不训练新的起草模型，而是把文法引擎已经确定的字符串写成草稿行里的 GRAMMAR 槽：与任意 drafter 拼成一行，校验时对这些槽直接接受、不算 logits，从而在 JSON 等强约束输出上提高每步接受长度；代价是放弃标准推测解码的无损分布保证。

3. 人话版

你要模型填一份格式极其刻板的人物卡：键名、引号、冒号、缩进几乎全部被正则写死，真正能自由发挥的只有十个值字段。普通推测解码里，便宜起草者并不知道这份表格长什么样，于是它常在键名或空格上猜错，整段草稿被一刀砍掉；与此同时，文法引擎其实早就知道下一串字符必须是什么。GaaD 的做法是让调度器在发去校验之前，先把“起草者的猜测”和“文法强迫的 token”合并成一行：猜对的标成文法槽，猜偏了就切断，再用强迫 token 把这一行填到更宽。校验器对文法槽不再提问。结果是每走一步能落下更多 token。但文法锁定的是文本，不是分词；一旦你提交了规范分词，后面的自由字段也可能跟不提交时不一样。

4. 背景与缺口

结构化输出（JSON schema、正则、工具调用格式）和推测解码已经成为服务引擎里的标配。常见接法是：drafter 先提案，目标模型一次前向校验，并在每个草稿位置用 XGrammar 一类引擎给出的 bitmask 做语法掩码。问题是 drafter 看不到文法。在键、分隔符、缩进这些确定片段上，它经常提出非法或另一种拼写的 token，草稿被拒；而正确的字符串其实已经在宿主的文法状态里。

已有的 jump-forward 解码会把强迫字符串另做一次变长 prefill。在 vLLM on TPU 这种提前编译形状的引擎上，这意味着新的 shape、额外编译或填充，并且和 drafter 争夺同一批位置。缺口因此很具体：如何在不增加新内核、不在关键路径上编译的前提下，把文法强迫的 token 变成推测解码已经会处理的草稿行，并与 MTP、DFlash、n-gram 这类现成 drafter 组合。

5. 核心 insight

文法是一个不需要 logits 的第二起草者。把强迫 token 写进草稿行，校验步骤本来就会跑；标记为 GRAMMAR 的槽不必与目标模型比较，因而也不必计算这些位置的 LM head。行宽 K 可以大于 drafter 的份额 KM：模型只填自己那几格，文法把剩下的填满。为了让文法状态与上一轮已接受 token 对齐，带文法草稿的步骤必须同步——宿主要等上一步的 token 读回后再规划下一行。作者同时强调：这不是免费的无损加速。接受概率为 1 的文法槽，会把强迫字符串的规范分词写进上下文，从而改变该点及其后的输出分布。

6. 方法逐步拆解

文法自己的草稿。仅当文法从当前状态只允许唯一续写字符串时，才进入 jump-forward：取最长强迫字符串，用分词器的规范编码切开，并逐 token 检查文法是否按序接受。任一 token 被拒，或根本没有强迫字符串，则文法不起草。草稿在第一个出现多个合法续写的位置结束，并截断到 K。

与模型 drafter 逐位合并。Drafter 仍提出 KM≤K 个 token，并且看不到文法。规划器从已提交的文法状态出发，对每一位询问：若双方提出同一 token，保留并标 GRAMMAR；若该位自由且模型 token 被文法允许，标 MODEL，留给校验；若模型与强迫 token 不一致、或不被允许，立即停止采纳后续模型 token——后面的提案是在错误分词路径上继续的；然后从当前状态继续追加强迫 token，直到行满或不再强迫。被拒绝的 MODEL 槽仍会废掉其后所有槽，包括排在它后面的 GRAMMAR。

何时规划、如何校验。一行的两个输入（上一步接受后的文法状态、本步 drafter 提案）只在上一步结束后才都在宿主上。因此异步调度无法在飞行中的步骤里计算下一跳的 jump 字符串。实现上按 batch 保守处理：只要一批里有结构化请求，整批同步。校验时 LM head 只对 MODEL 槽和 bonus 槽计算；GRAMMAR 被贪心 / 随机拒绝采样器直接接受。目标模型在最后接受位置之后的 bonus token，仍在文法掩码下采样。

实现边界。vllm-torchtpu 基于 vLLM 0.33，改动调度器、步进循环、推测元数据和拒绝采样器，不新增内核，形状在启动时编译。仍在 prefill、推理解析器认为文法尚未生效、需要 logprob 或存在 / 频率 / 重复惩罚、或文法已终止的请求上跳过 GaaD。

8. Toy example

图 2 给了一个具体的 Qwen 分词场景。光标停在自由字段 name 的值里。Drafter 提出 Harry、 Potter、以及结束值的 ",，这些位置文法并不强迫，故标为 M，由目标模型决定名字在哪结束。一旦写出结束引号，文法强迫换行；模型也提出了换行，于是该位变成 G。下一步模型想写两个空格，文法要三个空格，双方分歧，模型部分到此结束。剩下的槽由强迫的缩进和 "house" 键填满。如果前面某个 M 被拒，后面那些看起来“注定正确”的 G 也会被一起扔掉。示意行宽是 7，实验是 K=8、MTP 用 KM=3。

9. Baselines

  • 各 drafter 单独、取其惯用 K=KM，并在每一点选用同步 / 异步中更快的调度：这是表 1 的 best-vs-best 对照，避免把 GaaD 跟一个故意变慢的基线比。
  • MTP 单独且 K=8（异步）：只加宽行、不加文法草稿，用来说明“变宽”本身不加速。
  • GaaD 但 K=KM：只有文法草稿、不加宽，用来分离两个改动。
  • 独立 Rust 运行时中的 MTP 单独：同一套权重、分词器、XGrammar 和工作负载，引擎其余部分都不同；用来说明结果不只属于 vllm-torchtpu。

未与 EAGLE 等其他 drafter 直接对比速度，也没有把 jump-forward 的变长 prefill 当作主表对照臂（第 1 节只在设计上说明它与 GaaD 的关系）。

10. 实验设置

平台是一片 TPU v7x（四芯片、八 TensorCore，拓扑 2x2x1）。张量并行：0.8B 与 4B 为 1，35B-A3B 为 4，397B-A17B-FP8 为 8。Drafter：MTP 配 Qwen3.5-0.8B / 35B-A3B（vllm-torchtpu）以及 0.8B / 397B-A17B-FP8（Rust）；DFlash（z-lab 检查点，块大小 16）与 n-gram 配 Qwen3-4B（仅 vllm-torchtpu）。对照臂 K=KM 为 MTP=3、DFlash/n-gram=7；GaaD 一律 K=8 并保持原 KM。

工作负载是 JSON character-profile 基准：50 条提示循环到 256 个请求（表 1）、64 个（输出对照）或 128 个（Rust）。正则约束一个含 11 个固定键的 JSON 对象（其中 wand 是嵌套对象）、固定缩进；十个值字段为四个枚举、一个数字、五个自由文本。贪心解码，最多 256 个输出 token，关闭前缀缓存。vllm-torchtpu 先完整跑一遍以编译和预热，再在 B≤4 时计 3 次、B≥16 时计 5 次，取中位数。表 1 的 39 个点中，重复运行中位差异 3.2%，97% 的点低于 10%，例外出现在 B=64。Rust 点是单次 vllm bench serve、128 请求。表 1 测量时整引擎关闭异步调度；由于本负载全部是结构化请求，与“按批同步”规则调度等价。

11. 指标教学

τ：每步目标模型前向能落下的输出 token 数（含 bonus）。它几乎不随 batch 变，是“草稿质量”指标，不是墙钟。

Speedup：同一批请求、同一最大并发 B 下，对照臂墙钟除以 GaaD 墙钟。因为分词不同，不要用 tokens/s 比较结构化臂。

Tokens 因子：对照臂输出 token 数 / GaaD 输出 token 数。大于 1 表示 GaaD 用更粗的规范分词写完同样的字符。

Per-step 因子：对照臂每个请求步的墙钟 / GaaD 的对应值。小于 1 表示 GaaD 单步更慢或一步里摊到的请求更少。

Plain TPOT 与 Structured request：混合流量里，前者是不受约束请求的每输出 token 时间（各臂文本相同），后者是结构化请求的平均完成时间（TPOT×平均输出长度）。

Identical：与 drafter-alone 在相同调度下是否 token 级完全一致。

12. 可核验结果

  1. 接受长度：表 1 中 drafter 单独 τ=1.30–2.06；加 GaaD 后 MTP 到 5.26–5.43，DFlash 到 4.11–4.13，n-gram 到 3.61–3.64，且各 B 几乎不变。Qwen3.5-0.8B 的 MTP 从 2.06 到 5.43，35B-A3B 从 1.99 到 5.31。
  2. Best-vs-best 加速：B=1 时为 2.68×（MTP 0.8B）、2.81×（MTP 35B）、2.66×（DFlash）、2.75×（n-gram）；B=16 为 1.44–2.09×；B=64 为 1.14–1.70×。n-gram 在大 batch 上保留得最多（1.70×）。
  3. 三因子分解：表 2 中 tokens 因子 1.31–1.38，τ 因子 2.62–2.81，per-step 从 B=1 的 0.73–0.80 降到 B=64 的 0.31–0.46。例如 MTP 0.8B、B=1：1.38×2.64×0.73=2.68。
  4. 加宽本身无益：同样异步调度下，MTP 单独 K=8 相对 K=3 只有 0.81–0.95×（0.8B）和 0.67–0.89×（35B）。对同一 K=8，GaaD 仍快 1.49–3.58×。只加文法不加宽（K=KM）为 1.03–2.52×，且处处慢于 K=8 的 GaaD。
  5. Rust 复现：表 3，MTP+GaaD 相对 MTP 单独，0.8B 在并发 1/16/64/128 为 2.23× / 1.68× / 1.37× / 1.22×；397B-A17B-FP8 在 1/8/32 为 2.02× / 1.86× / 1.69×。两边都走规范分词时，并发 1 的输出 token 数相差不超过 0.3%；0.8B 上 128/128 条文本相同，397B 上 82/128 相同。
  6. 输出并不相同：表 4 在 vllm-torchtpu 上 64 条请求全部 0/64 identical，token 少 24–28%（如 MTP 0.8B、B=1：10,274 / 7,421）。枚举字段一致率 85–96%，数字仅 47–69%，自由文本 50–74%。fp32 参考下 GaaD 文本更可能的请求为 31/64，中位差为 0；均 log-likelihood 为 −178.58 对 −178.51（0.8B）以及 −137.51 对 −135.03（4B）。未测任务准确率。
  7. 混合流量：表 5，按批同步规则，25–50% 结构化时，B=16 整任务 1.18–1.23× 更快，B=64 为 1.03–1.13×；结构化请求 2.2–3.2× 更快。纯文本 TPOT 在 B=16 上升 7% 与 36%，在 B=64 上升 21% 与 42%。0% 结构化、B=64 时按批规则是 0.81×，作者归咎于把 3 个草稿垫到 K=8，而非 GaaD 算法本身。

14. Ablation

两个核心消融已经写在表 1 的后两列：去掉加宽或去掉文法草稿，都会变慢；只加宽甚至变慢。调度规则是另一组消融。表 5 表明，在全结构化负载上两种同步规则接近，所以表 1 的数字对按批规则也成立；但在 B=64、50% 结构化时，按批规则慢于整引擎同步（15.5 秒对 13.0 秒每遍），作者未给出归因。分词消融则是跨引擎的：Rust 从第一个 token 就进入规范分词，GaaD 很少改输出，加速仍在（并发 1 时 2.02–2.23×），说明即便剔除 tokens 因子 1.31–1.38，接受长度本身仍能换来墙钟收益。

15. Claim vs Evidence

站得住的：在这份 JSON 人物卡、贪心解码、TPU v7x 上，GaaD 稳定提高接受长度，并在两套引擎里都带来加速。三因子表把“更快”拆成更短的 token 序列、更高的接受长度、以及更贵的单步，避免把分词漂移全算进算法胜利。混合流量里结构化请求变快、同批纯文本变慢，也有表 5 的直接数字。

必须一起读的限制：GaaD 明确放弃无损保证。vllm-torchtpu 上 64/64 输出与对照臂不同；质量讨论只做到“都符合正则、fp32 下似然差不多”，没有任务准确率，也没有采样实验。工作负载对 GaaD 友好：11 个键和固定缩进占了输出的大部分，更长的自由字段会留下更少可草稿位置。大 batch 加速衰减未完全解释。0% 结构化时实现仍可能拖慢纯文本。Rust 运行时未发布，不能作为可复现基线。

不要从摘要里推出的结论：2.66–2.81× 只属于 batch size 1 的 best-vs-best；batch size 64 低至 1.14×。3.31× / 3.15× 出现在表 5 的 batch size 1、100% 结构化，对照是异步 MTP，不是表 1 的“更快调度”定义，故比表 1 的 2.68× 更大，不可混用。

16. 贡献

  • 提出 GaaD：把文法强迫 token 与任意 drafter 合并为一行带出处标记的草稿，校验时跳过 GRAMMAR 的 logits，无需新内核或关键路径编译。
  • 在 vllm-torchtpu 与独立 Rust 运行时中实现，并与 MTP、DFlash、n-gram 组合。
  • 提供跨 batch 的 best-vs-best 主表、三因子分解、加宽 / 不加宽消融、混合流量和宿主规划成本。
  • 把 tokenization drift 说清楚，并用 fp32 参考确认：两种合法分词都可以出现，GaaD 固定走规范分词。

17. 局限

第 7 节列得很清楚。混合流量会抬高同批纯文本的 TPOT（vllm-torchtpu 上 7–42%，Rust 上再乘 1.07–1.47）；若产品更在乎纯文本延迟，账不能只算结构化请求。不是无损：强制规范分词会改变后续值；采样下，宿主在校验前丢掉文法禁止的草稿，还会把自由 MODEL 槽的分布改成目标模型的掩码分布（vLLM 的结构化路径在没有 GaaD 时也会丢这种草稿）。范围限于一个基准、贪心解码、0.8B 到 397B、一片 TPU v7x；DFlash 只在 vllm-torchtpu。作者预计规范分词更接近训练文本、不应系统性伤质量，但没有任务指标来证明这一点。

18. 复现要点

硬件需要对齐 TPU v7x 四芯片切片与所述张量并行。软件应对齐 vLLM 0.33 的 torchtpu 后端、XGrammar，以及 PR 中的调度 / 拒绝采样改动。工作负载必须是同一份 character-profile 正则（11 键、固定缩进），贪心、256 token 上限、关闭前缀缓存。对照臂必须是“惯用 KM + 该点更快的调度”，不要只比同步或只比 K=8 的 MTP。报告时同时给出 τ、墙钟、输出 token 数和 identical 比例，并分开 tokens / τ / per-step。若在 GPU 上复现，静态形状与同步开销都会变，不能直接搬表 1 的加速比。不要把 PR 讨论区里的未发表数字写进论文对照。

19. 研究价值

它指出了一个被“文法掩码 + 普通推测解码”遮住的效率来源：确定片段根本不必问模型。对 TPU 这类静态形状加速器，把 jump-forward 从变长 prefill 改写成定宽草稿行，是更贴合硬件的系统选择。同时，它把社区里常被默认的“推测解码 = 无损”敲出一个缺口：一旦接受规则对某些槽变成概率 1，加速和分布保真就不再能同时宣称。

20. 可执行迁移

  1. 在 JSON / 工具调用路径上先做“文法第二起草者”，不要先训更大的 drafter。统计你的负载里有多少 token 落在键名、括号和固定缩进上；若占比高，把 jump 字符串编码进现有草稿行并跳过这些位置的 LM head，通常比把行宽盲目加大更划算。上线必须加两条回归：token 级是否与旧路径相同，以及枚举 / 数值字段的一致率（本文是 85–96% 对 47–74%）。
  2. 混合流量按批同步时，单独预算纯文本 TPOT。用与表 5 相同的切分（0 / 25 / 50 / 100% 结构化，扫并发）决定是否把结构化请求隔离到单独池。若隔离成本高于 7–42% 的 TPOT 损伤，再考虑同池。同时检查实现有没有把纯文本草稿垫到更宽的草稿行列。

21. 方向专用分析

相对昨日的 ALD（在起草阶段做自适应层并行、削减 verifier 空转），GaaD 不改模型内部层流，也不提高“模型草稿”本身的命中率；它增加的是文法确定的那一段接受长度。两者正交：ALD 解决的是起草计算图，GaaD 解决的是结构化约束已经知道的 token。和 EAGLE / MTP / DFlash 的关系也是组合而非替代——表 1 的对照是“同一 drafter 最好的配置”，不是“GaaD 对战某一种超级 drafter”。对推理系统研究，更有启发的是同步调度与静态 shape 的约束：正确的文法草稿以放弃异步为代价，收益会随 batch 被宿主开销吃掉。

22. Attack / Verification

验证应先复现“输出合法但不相同”。若有人声称 GaaD 无损，表 4 的 0/64 已经否证。质量验收不能只看正则是否匹配，要在下游工具调用或信息抽取任务上比字段级准确率，并分别统计枚举与自由文本。采样路径需要单独测：丢弃非法草稿会改变拒绝采样的残差，可能被用来偏向某些值。对抗性 schema——例如在强迫片段里布置多种合法分词、或把关键字段紧挨着缩进——可能放大漂移。安全上，规范分词若与模型偏好的细粒度分词不同，或许会改变拒绝词附近的条件分布；本文没有做红队评估。混合流量测试应防止只展示结构化加速、隐瞒纯文本 TPOT。

23. 记忆总结

  • GaaD：文法是第二起草者，强迫 token 写进草稿行，标为 GRAMMAR，校验时不算 logits。
  • 可与 MTP / DFlash / n-gram 组合，不新增内核，形状启动时编译。
  • 行宽 K=8，MTP 的 K_M=3，DFlash/n-gram 的 K_M=7；示意里的 K=7 不是实验配置。
  • τ 从 1.30–2.06 升到约 3.6–5.4，且几乎不随 batch 下降。
  • B=1 加速 2.66–2.81×，B=64 只剩 1.14–1.70×；衰减全在 per-step 因子。
  • 部分加速来自分词更粗（tokens 因子 1.31–1.38）；Rust 里两边都规范分词时仍有约 2×。
  • 不是无损：vllm-torchtpu 上 64/64 输出不同，自由字段一致率只有大约一半到七成。
  • 混合流量里结构化请求可快 2.2–3.2×，同批纯文本 TPOT 升高 7–42%。
  • 规划本身很便宜（约 1% 步进时间），大 batch 变慢更多来自行宽和同步。
  • 只在一个对 GaaD 友好的 JSON 基准、贪心解码、TPU v7x 上得到这些数字。

论文 3｜CodecOPSD：用经典视频编码信号剪条件 token，再靠 on-policy 自蒸馏把 DiT 适配回去 NEW Video Acceleration

1. 基本信息

标题：On-Policy Codec Distillation for Efficient All-in-One Video Generation（正文简称 CodecOPSD；不要写成与旧文易混的“只叫 OPSD”）
作者：Boyang Wang（Virginia / Adobe 实习）, Kevin Blackburn-Matzen, Oindrila Saha, Matheus Gadelha†, Zezhou Cheng†（Adobe Research 与 University of Virginia；† equal advising）
arXiv：来源：abs · pdf · html · 30 页 · 提交 2026-11-23 · cs.CV
项目页：kiteretsu77.github.io/CodecOPSD_website（可打开核验，数字仍以论文为准）
方向：Video / Multimodal Acceleration

2. 一句话定位

CodecOPSD 先用 H.264 的运动向量和残差，把条件视频 / 图像里“没有新信息”的 VAE token 丢掉，再用教师（能看见被丢掉的 token）在学生自己的去噪轨迹上做 on-policy 自蒸馏，从而在 16 种条件上平均剪掉约 66% 的条件 token，并尽量贴近稠密教师的质量。

3. 人话版

做可控视频生成时，用户会一次扔来肖像、素描、深度、姿态、运动轨迹、要修补的区域……这些东西都会被编成 token，和噪声潜变量排成一条很长的序列。注意力随条件数平方变贵，但其中大量区域其实是静止背景或被前一帧预测干净的内容。这恰好是视频编码器做了几十年的事：记下“这块从哪儿来”（运动向量）和“还剩多少新东西”（残差）。CodecOPSD 先把这些像素级信号汇总到每个 3D VAE token 上，再按阈值或优先级丢掉低能量的 token。只剪还不够——原模型没见过“缺块”的条件，直接剪会跑偏。于是作者让同一个基座模型分饰两角：教师仍看见全部条件，学生只看见留下的部分，并在学生自己滚出来的去噪状态上对齐速度场。推理时只跑学生，教师退场。

4. 背景与缺口

现有加速多半打在去噪器本身：少步采样、FlashAttention、量化、特征缓存、稀疏注意力。作者想做一件正交的事：从源头减少条件 token。条件信号高度可压缩，静态背景在每帧重复，一条运动路径只占少量像素。H.264 等经典编码器能在 CPU 上实时给出运动与残差，且不依赖某一种深度特征。

缺口有两层。第一，codec 信号在像素 / 宏块尺度，而 DiT 的 token 覆盖 32×32 像素、跨 8 帧，直接套用并不显然，还要对不同模态做映射和修修补补。第二，训练免费的剪枝会留下明显质量缺口；普通 SFT（在加噪真值上做流匹配）也关不牢这个缺口。需要一种能让模型学会“codec 图案”、同时不把学生推到不可推断区域的适配方式。

5. 核心 insight

两点合在一起才构成方法。其一，对生成模型来说，“哪些条件 token 是新的”几乎就是视频压缩问题，不必再训练一个昂贵的 saliency 或 DINO 选择器。其二，教师与学生的信息差必须可推断且大小合适：丢掉的 token 作为教师的特权信息，既要足够让教师给得出现稠密指导，又不能让学生面对 90% 空洞而学不会。On-policy 很关键——监督加在学生自己 rollout 的高噪声状态上，而不是加在与学生轨迹脱节的加噪真值上。条件 token 不反看噪声 token 的架构，还让 KV cache 成为自然收益：剪掉的条件不必再占缓存。

6. 方法逐步拆解

从 codec 到 token 分数。H.264 把帧分为 I 帧（帧内预测，有残差、无运动）与 P 帧（块匹配得到运动向量 mt(p) 和残差 rt(p)）。每个 DiT 条件 token ci 覆盖像素集合 𝒫i 与 8 帧集合 ℱi。把更细的 16×16 到 4×4 块信号按条件分辨率缩放后，汇总为运动分 Mi 与残差分 Ri。

两种剪枝。阈值模式在高运动镜头更难压、近静态镜头更好压的观察上，为每条视频找平衡：若 Mi≥τm 或 Ri>τr 则保留。优先级模式把归一化分数合成能量 Ei，按能量从低到高丢，便于固定预算。训练时学生走阈值模式（附录表 S2 的固定阈值）；图 5 的率失真分析走优先级排序。

送进 DiT。每种条件先渲染成图像或视频，用同一个冻结 VAE 编码，再按掩码逐元素相乘。保留的 token 拼在噪声潜变量 xσ 后面；xσ 本身不剪，且每个保留 token 仍用原来的 3D RoPE 坐标，无需改结构。对 MiniMax-H3 这类还要把参考送进 VLM 的模型，同一套 codec 信号也会丢掉 VLM 的视觉 token（ViT 仍看完整图，丢掉的是进入语言模型之前的输出）。

On-Policy Codec Distillation。学生与教师共享冻结基座 vθ，学生多一个只作用在条件 token 投影上的可训练 LoRA ϕ（不对噪声潜变量或 VLM token）。教师看见保留集与丢掉集的并，学生只看见保留集。学生先无梯度地沿推理采样器的 K 个噪声水平 rollout，再在前 N 个高噪声状态上，用双方速度场的均方误差训练 LoRA。损失不出现真值视频。推理只跑学生。

8. Toy example

设想一个几乎静止的客厅，只有一只狗沿地板走过。分割、深度、姿态等条件在大部分空间-时间块上残差接近 0、运动向量接近 0，对应 token 被丢掉；狗附近和它扫过的轨迹块留下。VAE 仍按完整网格编码，但送进 DiT 的序列短了一截，RoPE 坐标还指向原来的位置，模型知道“缺的是哪一块”而不是“世界被挤紧了”。若完全不做蒸馏，模型可能把被剪掉的静区理解成“这里没有物体约束”，开始改背景。教师在同样的噪声状态下仍能看见那些静区 token，于是把“背景应当保持”的速度场教给学生。图 5 还显示：稀疏条件（轨迹、框）可以免费丢掉 80–94%，稠密条件只有 26–71%——客厅里的轨迹几乎整段可压，深度图则要保守得多。

9. Baselines

  • Teacher：稠密条件、不剪 token，是质量和速度的参照。
  • Random：每个条件按同样比例均匀随机丢，用于说明“只减预算”不够。
  • Reduced Resolution：把条件按更低分辨率编码，这是可控生成里常见的减 token 方法。
  • DINO attention：保留 DINOv3 CLS 最关注的 token，代表语义重要性。
  • Saliency（DeepGaze）：保留预测人类注视密度最高的 token。
  • 上述方法的 SFT 版，以及 SFT+Codec：同样步数、同样平均丢弃率下，用流匹配在真值上继续训，用来对比 on-policy 蒸馏。

表 1 要求各方法平均丢弃率同为约 66%。扩展实验另与 Training-Free Codec（发布权重直接吃剪过的 token）和少步模型叠加比较。

10. 实验设置

主试验台是作者的多条件视频模型：从预训练 22B 文图到视频 DiT 出发，不加载 6B 音频分支，实际加载约 16B。条件 token 不关注噪声 token，故支持 KV cache。第一阶段用文本与 16 种条件（分割、框、身份、素描、边缘、深度、法向、人体姿态、稀疏 / 稠密跟踪、模糊、灰度、首末帧插值、续写、修复、外绘）的混合做稠密 LoRA（rank 320，约 20 亿参数，50,000 步，48 GPU，全局 batch 48）。每个样本使用 1 到 5 种条件。第二阶段各微调方法从该稠密模型出发，再训 2K 步（16 张 H200，训练分辨率 49 帧、480×640，全局 batch 16）。CodecOPSD 用 AdamW，学习率 10−4；学生 rollout 与教师目标都不使用 CFG。主评测采样 30 步，训练时监督前 8 步。图 1、图 4 与部分附录改用该模型的 8 步蒸馏版：稠密 LoRA 可直接当教师，学生再 CodecOPSD 2K 步并监督全部 8 步。

测试片段从 VidGen-1M 的 2,000 条池中随机抽，带真值并离线准备条件。主推理 512×768、81 帧；图 4 的计时是 512×896、121 帧、8 步、单张 H200。表 1 与表 3 各 400 条（1–4 种条件），图 4 为 200 条（1–5 种），表 2 为 100 条，图 5 为每条件 50 条。Codec 选择在 Intel Xeon Platinum 8275CL 的 6 核 CPU 上计时，可与 VAE、文本编码器并行。扩展实验改到各域基准，详见第 4.5 节。

FID / FVD / LPIPS：相对真值的质量与保真，越低越好。它们不直接测量“有没有听条件”。

VBench：无真值时的感知维度；表 2 用了成像、美学、运动平滑、闪烁、背景一致、整体一致。

14. Ablation

表 3 是最干净的机制消融：间隙过大或过小都不如 codec 给出的默认间隙，支持“特权信息要可推断且大小合适”。表 1 则消融了选择器与训练目标：同样 2K 步，SFT 加任何选择器都不如 CodecOPSD，说明缺口主要来自训练方式，而不只是选了哪些 token。附录还比较特权教师、监督 1 个状态对 8 个状态等，正文把结论收在默认设定。扩展实验里，Training-Free Codec 在 Ref2VA 上丢掉 82–92% 后会出现转向、动作重开、脸偏离姿态等失败，而 CodecOPSD 在同一批留下的 token 上贴近教师——这是“必须训练”的定性消融。少步模型与第三方 LoRA 可在不额外训练的情况下叠加，但那是兼容性演示，不是表 1 的受控对比。

15. Claim vs Evidence

站得住的：在作者的 16 条件模型上，66% 平均丢弃率有表 S5 的行列和；CodecOPSD 在多数质量与跟随指标上贴近或略优于教师，并明显好于随机、降分辨率和 SFT+Codec。速度方面，图 4 给出随条件数变化的区间，73% 的缓存缩减是该曲线的上端。移植到 MiniMax-H3 与 Cosmos3 时，质量大体落在教师附近或种子噪声带内，加速随分辨率、帧数、参考数增加。

需要收窄的：“几乎不掉质”不是所有格子都为零差。深度 si-RMSE 从教师的 0.647 到 0.706，法向角从 4.72 到 5.44，轨迹误差从 13.54 到 7.80（此项更好），分割从 0.888 到 0.883。人评是“同等或更好”，没有单独报“更好”的比例，也存在偏好平局的可能。主试验台是内部 22B 模型，外部无法直接复现表 1。图 1 的 89%、3.1× 与 8.4× 和正文平均 66%、约 2×、图 6 的 3.72× 不是同一设置。图 4 用 8 步蒸馏模型计时，表 1 的质量是 30 步设定，不宜把质量和 2.30× 当成同一推理配置的成对数字。

未报或未独立核验：主表多种子标准差（Cosmos 表 6 对教师有 ±2σ，学生多为单点）；项目页视频为定性展示；内部数据池细节不完整。

16. 贡献

  • 把标准 H.264 的运动向量和残差映射为 VAE token 掩码，并给出阈值与优先级两种剪枝。
  • 提出 CodecOPSD：教师把被剪 token 当作特权信息，在学生自己的去噪轨迹上做自蒸馏。
  • 在 16 种条件的内部视频模型上验证，并扩展到 MiniMax-H3 Ref2VA、MiniMax-H3-Image 与 Cosmos3 的多任务生成。
  • 在相同平均丢弃率下对照多种 token 剪枝与 SFT，并提供率失真、间隙消融和 KV cache 收益。

17. 局限

附录 J 写了几条很具体的限制。运动轨迹上，一个点在首次出现后若保持静止，其后续 token 可能被丢掉，剩下的证据会让模型分不清“静止”和“被遮挡 / 被抹掉”。框、轨迹、模糊等细节模态需要改 codec 设定（表 S2），不是完全无调参。方法依赖可渲染成图像 / 视频的条件；纯文本或非视觉控制不在范围内。主模型与部分训练数据内部，外部复现重心应放在开源的 MiniMax / Cosmos 扩展。与少步蒸馏、稀疏注意力正交，但本文没有在主表上给出与这些方法的完整因子设计。

18. 复现要点

先复现 codec 映射：块级运动 / 残差 → 按 32×32×8 的 token 网格做 max / mean，再使用表 S2 阈值。选择器应与 VAE 并行，并报告 CPU 耗时。训练必须把 LoRA 限制在条件投影，教师冻结且看见丢掉的 token，学生走自己的 sampler 轨迹；监督步数要与推理采样器对齐（30 步里的前 8 步，或蒸馏模型的全部步）。评测要同时报质量、各条件跟随、丢弃率、去噪时间和 KV 大小，并写明分辨率、帧数、步数、是否蒸馏模型。移植到 MiniMax-H3 时，DiT 与 VLM 视觉 token 要用同一套 codec 信号，但丢弃率会不同（表 4：71.6% 对 36.2%）。不要用展示图的 8.4× 代替图 6 或表 4 的配置化数字。

19. 研究价值

它把“条件 token 太贵”从架构问题改写成可以利用几十年压缩研究的选择问题，并且证明选择器本身可以很便宜（CPU、1.13 秒），真正要花计算的是让模型适应残缺条件。On-policy、带特权信息的自蒸馏，为其他“训练免费剪枝看起来不错、微调后仍有缺口”的模态（图像参考、音频条件、机器人观察）提供了一条可搬的训练模板。

20. 可执行迁移

  1. 在多条件视频服务里，先上 codec 剪枝再决定是否蒸馏。用表 S5 的模态差异做预算：轨迹 / 框可按 80%+ 丢，深度 / 灰度更保守。先看 Training-Free 是否已经落在可接受质量带；若出现附录那种转向或动作重开，再按 2K 步 CodecOPSD 适配条件 LoRA。上线要把 codec 预处理与 VAE 并行，并单独报 KV 显存。
  2. 把间隙当成要扫的超参，而不是越大越好。复用表 3 的两个对照：教师也适度剪枝（间隙过小）和学生极端只留 10%（间隙过大）。选使教师仍明显强于学生、但学生从保留 token 能推断被删区域的工作点。不要为了展示加速直接把丢弃率推到 90%。

21. 方向专用分析

相对昨日的 Hindsight Forcing（少步自回归视频扩散里用潜空间直通桥回传跨 chunk 信用），CodecOPSD 不改采样器的时间信用，而改条件序列长度。它与少步蒸馏是乘法关系：附录 G.3 在 768×1344 的例子上，codec 再给 FastH3-Omni / Pika H3 Flex / SolarRenderer 提供 1.50× / 1.46× / 1.79×，相对 50 步发布模型则变成 9.19× / 11.20× / 约 21.9×。对视频加速路线，这意味着“减步数”和“减条件 token”应一起记账，但分母必须写清。对 all-in-one 可控生成，条件不关注噪声、从而可 KV cache，是收益能落到显存上的架构前提；若未来模型改回全双向注意，加速曲线会更接近图 4 左侧，而不是有 cache 的右侧。

22. Attack / Verification

验证应分开“选择器是否选对”和“蒸馏是否只是记忆教师”。负对照包括：打乱运动 / 残差、用随机丢弃但保持相同预算（表 1 已做）、以及把阈值推过图 5 的免费带，质量应进入有损区。轨迹模态的静点 / 遮挡混淆是已承认的失败模式，应用含长时间静止后突然移动的序列做压力测试。展示图里的 89% 与 8.4× 必须能回溯到具体分辨率、帧数、步数和是否叠加少步模型；否则视为未充分规格化的主张。人评要报告打破平局后的偏好，而不仅是“同等或更好”。若条件图本身被对抗性扰动（在残差上添加人眼不可见但能改变保留集的图案），剪枝可能系统性地丢掉身份或姿态关键块——本文未做此类鲁棒性评估。

23. 记忆总结

  • CodecOPSD = H.264 信号剪条件 token + 教师看见被剪 token 的 on-policy 自蒸馏。
  • 分数是每 token 的最大运动和最大帧均残差；阈值保动态平衡，优先级保固定预算。
  • 16 种条件、平均丢掉 66%（5858/8853）；轨迹可丢 95%，灰度大约 41%。
  • 表 1 上 CodecOPSD 多数指标贴近教师，并明显优于随机、降分辨率和 SFT+Codec。
  • 图 4：无 cache 加速 1.54–2.30×，有 cache 1.15–1.37×，KV 最多减 73%。
  • 人评 92% / 88% 认为跟随与画质同等或更好；VBench 变化不超过 1.0 点。
  • 间隙过大或过小都更差，codec 默认间隙是工作点，不是越狠越好。
  • 可转到 MiniMax-H3 与 Cosmos3；主文最高配置化加速是 Ref2VA 3.72×、图像 2048² 的 3.06×、音频 2.30×。
  • 图 1 的 89%、3.1×、8.4× 与上述平均 / 主表不是同一设置，引用时要分开。
  • 与少步蒸馏正交且可叠加；静点轨迹和部分模态的 codec 设定仍是已知短板。
