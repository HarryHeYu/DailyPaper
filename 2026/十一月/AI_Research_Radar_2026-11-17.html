人话版：这篇论文到底干了什么？

智能体强化学习里，模型外面总有一套脚手架（harness）：它决定历史怎么被写进上下文、模型走偏时要不要给一句提醒。常见做法是人手写好这套脚手架，然后在整个训练过程中原封不动。作者认为这不合理：好的脚手架依赖于环境、数据和当前策略，而且策略一变，它也该变。

ModHarness-RL 把脚手架写成作用在结构化 State 上的两个确定性程序。Compression 读取完整交互记录，按规则重渲染历史，把不再需要的片段卸掉，从而在有限预算里保住关键证据；它在训练开始前对基策略拟合一次，之后固定，以免上下文在策略学习中不停改写法。Steering 是一组触发器，每个触发器检测一种可验证的失败模式（例如重复调用同一工具），只在触发时追加短指导；它每隔 10 个训练步更新一轮，并且先用全部历史轨迹做零成本回放，看这种失败是在自行消失，还是稳定存在，再决定安装、观察或放弃。策略本身仍用标准 GRPO。CodeSearch 上，相对固定的手写脚手架，四个设置平均约高 19%；Qwen3-8B 在上下文受限时 Overall F1 从 0.333 到 0.412（+24%），并且超过写这些程序的 GPT-5-mini 零样本。消融表明：先训策略再改脚手架、或让 Compression 随策略一起演变，都会掉点。

背景与研究缺口

长程工具智能体的轨迹会迅速堆满重复的检索结果、失败的命令输出和已经过时的计划。上下文一满，就只能丢弃早期回合，或叫另一个模型做摘要。与此同时，模型会反复犯同一类错：再查一次已经查过的文件、用错工具参数、在该提交时继续探索。已有工作分别从记忆、技能库、提示词或整套脚手架编辑去补这块，但它们大多仍把“模型看见什么、何时被提醒”当成训练外围的文本产物，而不是可以在轨迹上执行、检查、回放的程序。

缺口有两层。第一，若压缩历史靠在线调用教师模型，代价会随训练轨迹数线性增长，而且每次改写都可能打断前缀缓存。第二，若把指导当成固定提示，它无法区分“策略再训几步自己就会改掉的偶发错误”和“训练怎样都不会自己消掉的稳定失败”；把偶发错误写成永久提醒，等于在策略还在学的时候塞进多余监督。作者要的是一种脚手架：不调用模型就能在每一步运行，能在旧轨迹上事后检验，并且只在闸门确认它提高了留出训练任务的分数之后才安装。

核心洞察

脚手架不应当是一段越写越长的提示，而应当是两个作用在同一份完整 State 上的程序：一个决定“这一回合该看见怎样的历史”，一个决定“这一回合要不要插入一句针对已知失败的提醒”。因为它们是程序，所以可以在历史轨迹上免费回放，画出某种失败是在下降、走平还是上升；只有走平或上升的失败才值得干预。Compression 适合一次拟合后锁住，因为它改变的是上下文的写法，写法不稳会破坏策略学习；Steering 则必须与策略共演化，因为失败模式会随策略改变。把两者的安装都放到留出训练集上的闸门后面，才能避免把教师模型的文风蒸馏进策略，也避免在评测集上挑程序。

方法深挖

Agent 架构与 State。 策略 πθ 在任务 q~𝒟 上与工具集 𝒯 多回合交互。第 t 步读取上下文 ct，采样动作 at~πθ(·∣ct)（本回合完整回复，以一次工具调用结束），观察 ot=𝒯(at)，直到终止步 T。轨迹为 τ=(q,a0,o0,…,aT)。作者把 State 写成带类型的记录 st=(q,u0,…,ut−1)，其中 ui=(ai,oi)，每回合含 `.thought`、工具名与参数、执行输出或带元数据的检索文档，以及该回合展示过的指导。最朴素的脚手架是把记录直接拼成不断变长的抄本 ctflat。ModHarness 则学习 ℋ=(compress,steer)，在每一步用完整 st 重新渲染上下文：compress 给出压缩后的历史视图，steer 仅在触发时于其后追加指导。执行 ℋ 不调用模型、不计模型 token，因此可以在每条轨迹的每一步运行。

RL Formulation。 目标是 maxθ𝔼q~𝒟,τ~πθ[r(τ)]。优化器用 GRPO（在 verl 中实现，vLLM 做 rollout）。对每个任务采样一组 G 条轨迹，组内标准化奖励得到优势

A^i=Ri−mean({Rj}j=1G)std({Rj}j=1G)

再最小化论文给出的裁剪目标（含 KL 项）

ℒGRPO(θ)=1G∑i=1G1|τi|∑t=1|τi|min(ρi,tA^i,clip(ρi,t,1−ϵ,1+ϵ)A^i)−β𝔻KL[πθ‖πref]

其中 ρi,t 是 token 级重要性比，πref 为固定参考策略。奖励因环境而异，都是轨迹级、可验证的结果奖励，没有逐步人工标注：CodeSearch 是文件/模块/实体三个 F1 之和（报表示三个 F1 的均值，落在 [0,1]）；ALFWorld 是通关 1、否则 0；BIRD SQL 是最终查询与金标准结果一致为 1，否则 0。信用分配因此仍是组内标准化的轨迹优势，广播到该轨迹的所有 token；脚手架并不改写奖励，它只改变 ct，从而改变哪些 token 会在何种上下文中被采样。KL 系数在 CodeSearch 为 0.001、ALFWorld 为 0.01、BIRD 为 0；熵奖励仅 ALFWorld 使用 0.001。所有方法训练 200 步，每环境内优化设置相同，差别只在模型周围的脚手架。

Compression：一次拟合，然后锁住。 先用基策略 π0 在 𝒟train 上以追加式上下文做 rollout，得到水库 ℛ0。LLM 创建者（GPT-5-mini）阅读这些轨迹和上下文被填满的方式，写出若干候选压缩程序；每个候选编译、修复直到能跑，再在 ℛ0 的存档回合上测量它是否不忠（删掉了任务相关信息）或无效（上下文几乎没变），不合适就改写。候选集 𝒫 在留出训练任务 𝒟trainhold 上、用冻结的 π0 各跑一次，得分最高者成为 ℋ0 并在此后固定。作者也试过让 compress 随策略每 10 步重拟合，Table 3 显示全面落后，说明上下文写法需要稳定。

Steering：与策略共演化，先回放再安装。 每轮先在现任 ℋk−1 下用 GRPO 更新策略，得到 πk 与新轨迹 ℛk。创建者从“同一任务有的轨迹成功、有的失败”的混合组提出失败假说：每个假说是一个作用在 st 上的触发器，加上指导文本的要点。关键步骤是 Replay：把每个候选触发器在全部历史轨迹 ℛ0:k 上执行，统计该失败在各训练步出现的频率，得到曲线 ℰ。这一步无需模型调用。判定者阅读曲线与已安装集合，给出三种裁决：失败走平或上升则 intervene（安装触发器与指导）；看起来真实但尚未稳定则 monitor（留下观察，暂不展示指导）；持续下降则 continue（不装）。被接纳的触发器还要作为一组一起过闸门：只有在 πk 下、在 𝒟trainhold 上严格超过 ℋk−1 才成为 ℋk。默认 K=20 轮，每 10 个训练步一次，与训练并行，训练器不必等待。一个玩具例子：若触发器是“连续两回合调用了参数相同的同一 shell 命令”，回放会告诉你这种重复是在随训练消失，还是在后期仍然成批出现；只有后者才会把“不要重复同一查询，改检查已有输出”写进下一回合的 ct。

长程与失败传播。 两个程序每一步都读完整 st，因此某一步被卸掉的内容仍可在后续步骤按需重新出现，这是对“压缩等于永久遗忘”的显式否定。失败若不被写成可执行的触发器，就只能通过轨迹级奖励间接影响后续回合；Steering 把可检测失败从隐式信用改成定点干预。它也因此受边界约束：只能捕捉“可用显式规则在记录上检测”的模式，对开放对话里语义层面的偏离帮助有限。

实验设置与结果

设置。 三个环境共用同一套对比逻辑，只改脚手架。CodeSearch 跟随 CodeScout：在修复前的仓库里定位应改的文件、模块与实体，训练用 SWE-Smith，评测 288 题（SWE-Bench Lite 100、Verified 100、Pro 88），模型为 Qwen3-4B / 8B，每步 8 个任务、每任务 8 条轨迹，学习率 10−6，温度 1.0，每回合最多 1024 token、最多 10 回合、每回合一次 shell（30 秒、最多 10,000 字节输出）。ALFWorld 跟随 GiGPO：274 个评测游戏（seen 140、unseen 134），Qwen2.5-1.5B-Instruct / 7B-Instruct；1.5B 在 RL 前用规则专家的 288 个成功局做 9 步 SFT，否则 GRPO 组内优势全为零。与 GiGPO 只展示最近两回合不同，本文保留完整历史直至触达预算。BIRD SQL 跟随 MTIR-SQL：训练集去掉题面已超 6144 token 的 663 题后剩 7726，评测 dev 1534 题，Qwen3.5-2B / 4B，每步 64 题、每题 5 条轨迹，最多 6 回合。所有方法训练 200 步，在 8×H100 单节点上，用最终检查点评估；凡是要从轨迹学习文本产物的方法，创建者都是 GPT-5-mini。上下文分两档：受限默认 1024 历史 token（会在典型回合中途用尽），充足默认 8192（ALFWorld 提到 12288，因 8192 仍不够长）。𝒟trainhold 在 CodeSearch 与 ALFWorld 为 128 个任务，与评测集不相交。基线包括：固定手写 Base harness；只加其中一个程序的 +Compression / +Steering；EvolveR（记忆）、SkillRL（技能库）、INSPO（提示共演化）、HarnessForge（编辑脚手架模块）、DeepAgents（带规划清单、草稿本和子智能体的复杂手写脚手架），以及 GPT-5-mini 零样本。

主张与证据、贡献与局限

主主张是：把脚手架写成可执行程序，并让 Compression 锁住、Steering 与 GRPO 策略共演化，能够在多种环境与两种上下文预算下超过固定手写脚手架，且收益不是教师蒸馏。Table 1 加上 GPT-5-mini 零样本对照，是主张的主证据；Table 3 把共演化、判定和“压缩不宜随策略改写法”写成可证伪的消融；Table 2 说明程序化压缩相对在线摘要的代价优势。相对弱的证据是 ALFWorld / BIRD 主要靠单程序曲线和正文百分数，没有像 Table 1 那样的完整第三方表，因此“跨环境普遍成立”应读作定向验证，而不是同等强度的排行。局限还包括：闸门样本量有限；创建者与判定者都是 GPT-5-mini；比较范围在 CodeSearch 最完整；确定性程序不适合开放对话。贡献是把 agent RL 里“模型看见什么、何时被提醒”从提示工程对象改成可回放、可闸门的程序对象，并给出一套可操作的更新节奏（20 轮、每 10 步、与训练并行）。研究价值在于：它和近期把经验写成 playbook、步骤分数或技能库的工作可以对照——这里经验被编译成对 State 的规则，而不是再喂回模型当文本记忆。

最小可执行迁移

若要在自己的工具智能体 GRPO 训练里试验这件事，不必一开始就同时上两个程序。最小路径是：把交互记录成带类型的 State（思考、工具名、参数、输出），先保持现有奖励与 GRPO 超参不变。第一步只做 Compression：用基策略在训练集上 rollout，让一个能写代码的模型提出若干“按规则重渲染历史”的程序，在留出训练题上挑选能跑、且不降低分数的一个，然后锁定，再开 RL。对照必须是同一预算下的追加式 Base harness，以及用同一个写手做在线摘要的 compaction，同时记录 prefill token 与前缀缓存命中，而不是只看结局分数。第二步再加 Steering：每 10 个训练步，从混合成功/失败组提出触发器，在历史轨迹上免费回放，只把走平或上升的失败送进闸门；闸门必须用留出训练题，绝不能用测试集。环境建议先选工具输出结构化、奖励可自动计算的一种，例如代码定位或 SQL，而不是开放对话。风险是：创建者若换成弱模型，提案质量会下降；若让 compress 跟着策略改，上下文不稳可能直接伤性能；触发器写得过宽，会把偶发错误当成永久指导。成功标准很具体：相对 Base 的结局分数上升，且 Table 2 那种“教师调用次数少一个数量级以上”的代价差被保持。若资源只够改一个旋钮，优先锁住 Compression、不要让历史写法随策略漂移；Steering 可以后加，但必须保留回放曲线，否则就会把仍在自行下降的失败写成永久提醒。评测时用最终 200 步检查点，并同时报告受限与充足两档，避免只在某一档上挑选好看的数字。

五句总结

智能体 RL 的脚手架不该在整个训练里保持手写不变，因为它依赖当前策略。把历史压缩和失败指导写成作用在完整 State 上的程序，就可以免费回放、用留出集闸门，而不必每一步请教师改写。Compression 应一次拟合后锁住，Steering 应与策略交错更新，顺序颠倒或让压缩跟着变都会掉点。CodeSearch 上四个设置平均约 +19%，且超过写程序的 GPT-5-mini 零样本。这一套仍然吃轨迹级奖励，并不发明新的逐步奖励；它改变的是策略在每一步看见什么、以及何时被提醒。

人话版：这篇论文到底干了什么？

投机解码让一个更轻的草稿模型先提出一串 token，再由目标模型一次性并行验证，从而缩短自回归生成的墙钟时间。DFlash 这类扩散式草稿器能在一次前向里填完整块，文本上已经很快；但换成视觉-语言模型后，真正“看图才能写对”的 token 往往最先把整块截断。作者用目标模型自己、在有图和无图两种条件下的下一词分布 KL 散度来定义 token 级视觉依赖，并发现接受率从最低依赖四分位的 46% 降到最高依赖四分位的 22%，截断点有 44% 落在最高依赖四分位；即使用约 90 万条多模态样本按官方配方再训一遍，这个缺口也合不上。

MMFlash 的做法不是再堆一个更复杂的草稿结构，而是把上述诊断直接写进训练权重：离线算好视觉依赖分，再用目标置信度（有图分布的熵）和草稿模型当前会不会写对，去放大那些“图像既改变了预测、目标又已经想清楚、草稿却还没学会”的位置；同时用草稿自信度估计整块前缀能否活过验证，避免把梯度浪费在验证根本走不到的后段。对平均约 4 万 token 的长视频，他们还观察到草稿注意力一半堆在最近 256 个位置，于是在训练和推理用同一套稀疏模式：保留前 4 个 sink、步长 32 采样的视觉 token、全部文本和一个 256 的局部窗。主结果是墙钟加速而不是纸面 FLOPs：Qwen3.5-4B / 9B 在七个图像基准、贪心解码下平均加速 3.00× / 3.05×，高于同数据训练的 DFlash（2.72× / 2.75×）；视频上再轻量微调后平均加速约 2.33–2.71×。

背景与研究缺口

投机解码的速度取决于草稿有多常被目标模型原样接受。自回归草稿器要逐步写完一整块，草稿步数和草稿长度绑在一起；DFlash 把一块 B 个位置里的锚点之后 B−1 个 mask 并行填满，于是可以把省下来的串行步数换成更深的草稿器。它的训练损失是对目标自身选择的交叉熵，但位置权重只按块内下标指数衰减，因为验证只接受前缀：第 k 个位置被拒，后面全部作废。

这个设计在文本上合理，迁到 VLM 时却留下一个盲区。图像或视频里，有的 token 只是在把句子写完，有的必须读图表里的数字、坐标或某一帧的事件。两者在块内的位置可能相同，对接受长度的贡献却完全不同。已有工作要么把文本草稿器直接套到多模态目标上，要么只用多模态数据再做一次同样的位置加权训练，默认“看过图就会写图像 token”。缺口在于：没有一个只依赖目标模型、因而可以离线预计算的 token 级量，来指出草稿到底在哪些位置系统性失败；也就没有理由修改损失，把容量用在那些位置上。长视频还叠加了另一层问题：上下文从图像基准平均 477 个 token 涨到约 4 万，草稿器是否还要在每一步对全部视觉 token 做全注意力，同样缺少依据。

核心洞察

真正决定一块草稿能走多远的，不是“这个位置靠不靠前”，而是“目标写这个词时到底有没有在看图、看完有没有想清楚、草稿现在会不会写对、以及验证会不会走到这里”。视觉依赖可以用目标模型自己来量：同一前缀下，把图像拿掉前后的下一词分布做 KL；这个量与草稿器无关，只需离线算一次。若再乘上有图分布的置信度，就能把“图在说话但目标自己还在几种答案间摇摆”的位置排除出去——那些位置再加权也学不成稳定模仿。训练时把这套分数与“块前缀能否存活”和“草稿是否仍会写错”相乘，额外梯度就会自动从已学会的视觉 token 撤走，避免伤害文本 token。长视频上，小草稿器的注意力本就集中在问题、已写答案和最近窗口，对远帧是摊薄的；与其维持全上下文注意力，不如在训练和推理用同一套稀疏模式，既省计算，又不制造训练-推理不一致。

方法深挖

输入到输出。 训练阶段，先用冻结的目标 VLM 在其自己生成的回答上，为每个位置离线计算视觉依赖与有图熵，存进数据，之后不再产生额外训练开销。每个训练块以一个锚点 token（推理时对应上一步验证给出的 bonus token）开头，后面跟 B−1 个 mask；草稿器读取目标模型若干层的隐状态，一次前向填完这些 mask，得到每个位置上目标所选 token zk⋆ 的概率 qk。损失是带新权重的交叉熵。推理时，草稿器提出长度 B 的块，目标模型并行验证，接受一个前缀并给出下一个 bonus token，再开启下一块。视频基准上，训练和推理使用同一套稀疏注意力，而不是先全注意力训练再在测试时窗口化。

视觉依赖与置信度门控。 对前缀 x<t 与图像 I，定义

dt=KL(p(·∣x<t,I)\|p(·∣x<t))

其中 p 是目标模型的下一词分布。原始 KL 无界且重尾，故在整个训练集 𝒟 上按秩映射到分位数 g~t∈[0,1]。再按有图分布的熵 Ht=H(p(·∣x<t,I)) 缩放

gt=g~t·exp(−Ht)

于是 gt 高，当且仅当图像既改变了预测，目标又已经把质量集中在少数选项上。这正是“再花力气可能换来接受”的位置。一个直观的玩具例子是：写“The chart shows that sales reached”之后的数字，拿掉图以后下一词分布会明显摊开，dt 高、熵低，gt 接近 1；而写冠词或介词时，有图无图几乎同分布，gt 接近 0。DFlash 的位置权重对这两个 token 一视同仁，MMFlash 则只给前者加码。

三项相乘的块内权重。 MMFlash 保留 DFlash 的交叉熵拟合，但把原来只依赖下标的 wk=exp(−(k−1)/γ) 换成

wk=bk(1+αgk(1−sg(qk))),ℒMMFlash=∑k=1B−1wk(−logqk)

其中 sg(·) 是停止梯度。bk 是验证感知的前缀存活估计：

bk=∏i=1kq¯i,q¯i=(1−λ)sg(qi)+λ

平滑 λ 保证每一项至少为 λ，单个提前错误会削弱后续位置，但不会把整段后半的梯度封死。(1−sg(qk)) 则是动态项：草稿已经会写的视觉 token，加成自行消退，避免过拟合图像位置、牺牲文本位置。默认 λ=0.5、α=1，块长 B=16。

视频长度下的稀疏注意力。 七个图像基准的平均输入约 477 个 token，三个视频基准则约 41,218。对训练好的 MMFlash 草稿器做注意力分析：最近 256 个位置只占上下文的 0.8%，却拿走 50.1% 的注意力；远帧占上下文 96% 以上，合计仍吸走约 46%，但单 token 贡献很低，说明全上下文起草有大量冗余。简单窗口能提高视频接受长度，但会丢掉窗外的视觉证据。作者因此采用固定稀疏模式：保留前 4 个 sink token、按步长 32 采样的视觉 token、全部文本 token，以及 256 的局部窗；训练与推理共用，以保证上下文可见范围一致。

推理时的接受规则与 τ。 目标模型一次读完草稿块，从左到右核对；第一个与目标解码策略所选 token 不一致的位置成为截断点，该位置之后全部丢弃，再由目标给出 bonus token 作为下一块锚点。平均接受长度 τ 是每次起草后实际留下的 token 数（含 bonus 的计数方式与原文一致）。停止梯度是必要的：若 qk 同时出现在权重和交叉熵里，模型可以通过故意压低自信度来抬权重，损失信号会失真。把 qk 从权重图中切开，权重只作为对“现在还不会的视觉 token、且验证还走得到”的调度系数，学习本身仍是拟合目标选择。

与基线目标的差别。 MTP 是 Qwen3.5 自带的多 token 预测头，草稿步数与深度绑在一起；EAGLE-3 是自回归树状投机解码的强基线，本文用与 MMFlash 相同的数据训练；DFlash-z 是官方发布、在纯文本上训练的 6 层草稿器，读取目标 8 层隐状态；DFlash 则按官方设定、在与 MMFlash 相同的约 90 万多模态样本上训练，5 层、读取 5 层隐状态。MMFlash 与最后这一支的唯一系统性差别，就是损失权重以及视频上的稀疏注意力，而不是换成另一种起草结构。这使主表上的加速差可以直接读成“视觉感知重加权是否值回票价”。

实验设置与结果

设置。 目标模型为 Qwen3.5-4B 与 9B。训练数据取自 LLaVA-OV-1.5-Instruct-Data 约 100 万条，用目标模型按官方解码设置（温度 0、top-p=0.95、top-k=20、最长 4096）重写回答；为提高训练效率，部分限制为单词或选项字母的提示被改成逐步推理，Qwen3.5-4B 上有 37.0% 的提示被改写，改写后中位回答长度从 3 提到 130，不超过 8 个 token 的比例从 12.5% 降到 1.0%。丢弃总长超过 4096 的样本后约剩 90 万条。块长 16、每条最多 512 个锚点、batch size 2、6 个 epoch，学习率 6.0×10−4，余弦退火，前 4% 线性 warmup，8 张 H100。因离线缓存隐状态可达数十 TB，作者采用在线训练，每步同时跑目标模型。主推理在单张 H200 上用 SGLang，关闭 thinking，并发为 1，温度 0 与 1 各评一次。图像评测覆盖 ChartQA、CharXiv、MMStar、MMBench、DynaMath、MathVista、MathVerse，每个基准固定 200 个随机样本、零样本、LMMs-Eval。视频评测为 LongVideoBench、MVBench、Video-MME（平均上下文约 41.6K / 42.3K / 39.8K token），在 LLaVA-Video-178K 的 2K 样本上用稀疏模式再微调 3 个 epoch。指标是平均接受长度 τ 和相对无草稿基线的墙钟加速（token/s），不是理论 FLOPs。

主张与证据、贡献与局限

论文的主主张是：VLM 投机解码的接受损失集中在视觉依赖 token 上，把这一诊断写进损失、并在长视频上配上训练-推理一致的稀疏注意力，就能在不改目标模型的前提下提高墙钟加速。Table 1 与同数据 DFlash 的对比是最硬的证据；Figure 3 的 46% 对 22%、截断点 44% 落在 Q4，说明问题不是“没见过图”，而是目标函数看不见图。Table 2 把稀疏注意力和微调拆开，避免把视频收益全部算到重加权头上。相对弱的部分是：主表样本只有每基准 200 条；提示改写改变了训练回答长度，虽对所有自训基线一视同仁，但仍使“官方数据配方”不再完全可比；DFlash-z 的完整训练配方并未公开；显存和 FLOPs 缺席，因此不能把它读成理论计算最优，只能读成 H200 / H100 上的墙钟结果。

贡献有三：给出可离线预计算的 token 级视觉依赖量；把验证存活、未学会程度和视觉接地三项乘进同一权重；为视频上下文提供简单可复现的稀疏起草模式，并在 Qwen 与 Gemma、4B 到 27B 上给出系统加速数字。局限同样明确：方法针对“视觉输入、文本输出”的 VLM，不是 omni 或语音生成；视频草稿器仍是在图像草稿器上做启发式稀疏与轻量微调；高并发下加速会回落；思考模式关闭。研究价值在于，它把“多模态投机解码为什么变慢”从系统调参问题改写成一个可测量、可加权的 token 属性，后续工作可以在此之上做按问题选帧、帧级依赖，或把同一想法迁到音频-视觉交错上下文。

最小可执行迁移

若要把 MMFlash 接到自己的 VLM 服务，不必先改草稿结构。最小实验可以是：冻结一个已有 DFlash 或同构扩散草稿器，用目标模型对其训练回答离线计算 dt 与 Ht，按分位数得到 gt，然后只把 DFlash 损失里的 wk 换成本文的三项乘积，λ=0.5，α=1，B=16。数据必须用目标自己生成的回答，先从十几万到几十万条看趋势；不要用与目标解码不一致的开放答案，否则草稿在拟合一个推理时根本不会选的分布。基线必须包括“同数据、同块长、旧位置权重”的 DFlash，否则说不清是数据还是权重在起作用；EAGLE-3 或 MTP 可以并列，但它们不是解释本文机制的对照。指标看 τ 和单卡墙钟 tok/s，并按视觉依赖四分位拆接受率，确认 Q4 是否被抬起来、文本位置的接受率有没有掉。若目标是长视频，第二步再把注意力改成 4 sink + stride 32 + 局部 256，训练和推理必须同构，并单独报告“只加稀疏、不微调”这一行，避免把稀疏与重加权混成一笔。硬件上，与主表完全对读需要 8×H100 训练和 1×H200 服务；资源不够时，可先在 4B、单一文档基准（CharXiv 或 ChartQA）上跑通权重替换，再决定是否做视频微调。风险有三：提示改写会改变回答长度，复现必须记录改写比例；并发升高后加速会收窄，结论不要只写并发 1 的峰值；思考模式若开启，接受长度与主表不可直接比较。若要对外声称服务加速，还应补一张与 Table 3 同结构的并发曲线，并写明框架是 SGLang 还是 vLLM，因为两者对基线吞吐的提升并不对称。

五句总结

DFlash 在 VLM 上的失败不是“没看过图”，而是位置权重看不见哪些 token 在依赖图像。用目标模型自己的有图/无图 KL 加上熵门控，可以把训练信号对准“图既改了预测、目标又已经想清楚”的位置。再乘上前缀存活估计和“草稿是否仍写错”，额外梯度会随学习自动撤走，避免伤害文本 token。长视频上应把稀疏注意力写进训练，而不是只在测试时加窗。同数据对比下，Qwen3.5-4B / 9B 图像贪心平均加速 3.00× / 3.05×，视频微调后约 2.33–2.71×，这是墙钟数字，不是 FLOPs 最优声明。

人话版：这篇论文到底干了什么？

长程工具智能体的历史会迅速超出窗口。摘要可能丢掉稍后真正要用的精确字段，整段保留又会把大量无关回合继续送给模型。CarryOn 把上下文拆成两块：一份紧凑的执行状态，加上带来源链接的细粒度证据。一个学来的选择器和自适应保留策略决定留下什么，管理上下文时不再额外调用 LLM。作者在 AppWorld、OfficeBench 和 Tau2 Telecom 上用 Claude Sonnet 5、Qwen3.8-27B、Gemma-4-31B 三个 Actor 评测，宏观平均任务成功率为 75.7%，比最强基线高 6.7 个百分点，并在 S0.8（成功优先、同时计入资源）和成功单位成本 NCS 上总体最好。

方法与智能体结构

Agent Architecture / State。 Actor 仍负责调用工具、推进任务；CarryOn 是外挂的上下文管理器。历史被切成证据单元，并维护一份可读写的执行状态（控制状态）。选择器给证据打分，自适应保留决定当前步把哪些证据和状态一起写入 ct。选择器的监督来自离线标注的状态与证据有用性，而不是在线让 Actor 自学“什么该忘”；论文还给出面向本地部署的 CarryOn-E 变体，用教师上下文蒸馏，使较小的本地模型也能做类似的保留决策。管理器本身不再为“该不该删这句话”再叫一次 LLM，所以每步的额外成本主要是选择器前向，而不是又一轮生成。Long-Horizon 问题被说得很清楚：后段动作常常依赖很早出现的精确值（账号、余额、议程时间），摘要一旦把数字写含糊，失败会在后续工具调用中爆发，而不是在被删的那一步立刻显现。这就是失败传播的路径：早期证据丢失，中期状态看起来还正常，末期才在付款或写表时出错。

评测不用单一成功率。Sα 把成功放在前面，同时惩罚资源；NCS 是归一化的“每次成功花掉的资源”，Full History 被标成 1。这个设计很重要：FIFO 或检索有时看起来省了上下文，却会用更多步数把任务做砸，NCS 会把它揭出来。

结果与消融

Table 1 是主证据。AppWorld 上，Claude 的成功率从 Full History 的 43.5% 升到 CarryOn 的 79.8%，略高于最强基线 SWE-Pruner 的 79.2%，NCS 从 1.000 降到 0.556；Qwen 从 65.5% 到 84.5%（SWE-Pruner 68.5%），Gemma 从 53.6% 到 72.0%。OfficeBench 上三个 Actor 分别为 69.5 / 66.3 / 66.3，Claude 与 Qwen 至少持平或超过 Full History，NCS 明显下降（Qwen 0.476，Gemma 0.338）。Tau2 上 Qwen 90.0%、Gemma 77.5%，Claude 为 75.0%，与 Full History 持平但 NCS 为 1.121，是少数没有同时赢下成本和成功率的格子。检索基线在 AppWorld 上对 Claude 只有 11.9%，说明“按相似度找回历史”在应用型长程任务里可以非常差。

Table 2 在 AppWorld + Claude 上拆组件：去掉 MEMORY 掉到 66.1%；只做排序是 76.8%；细粒度训练 73.2%；按新近度打包 76.2%；完整 CarryOn 79.8%，NCS 0.556 也最好。Table 3 显示 MEMORY 容量 128 个代理 token 时成功率最高（79.8%），64 时截断多达 284 次，256 时成功率 78.0%、截断只剩 8 次，并不是越大越好。主张“更短的上下文也可以更好做决定”总体上成立，但 Tau2 + Claude 提醒：在已经很短、对话型的流程里，管理器可能带来轻微成本回升。局限是没有公开已核验代码，Actor 是专有或大模型 API，选择器训练细节主要在附录；迁移时至少要保留“状态 + 带出处证据”的拆分，并用 NCS 而不是只看成功率。

把这些数字放到长程智能体的设计里，有三点值得单独写。第一，最强的“短历史”基线并不是 FIFO 或检索，而是 SWE-Pruner 和 ACON 这类专门为智能体历史设计的方法：在 AppWorld + Claude 上，SWE-Pruner 已经把 43.5% 拉到 79.2%，CarryOn 只再多 0.6 个点，但 NCS 从 0.652 降到 0.556，说明它的主要附加值常常是更省、而不只是更高。Qwen 上则相反，84.5% 对 68.5% 是大幅度的成功率优势，SWE-Pruner 在这个 Actor 上甚至只比 Full History 好 3 个点，跨模型并不稳定。第二，OfficeBench 的 Full History 已经不差（63.2 / 66.3 / 51.6），CarryOn 的胜利更多体现在 NCS：Gemma 的 0.338 意味着同样一次成功大约只花 Full History 三分之一的资源。第三，Tau2 + Claude 的 75.0% 与 Full History 持平、NCS 1.121，是必须写进局限的格子——上下文管理不是免费午餐，在轨迹本来就不长的客服诊断里，选择器和证据槽位可能成为额外开销。Appendix 的案例也表明，证据会被再次选中而不是写进摘要后丢掉，这与“压缩等于遗忘”相反，却依赖于出处链接仍然可用。

若要迁移，最小实验不必重训 Actor。先把轨迹记成“控制状态 + 带来源的证据片段”，用一个小选择器在离线标注上学习保留策略，对照 FIFO、检索和一种现成的摘要/剪枝器，同时报成功率和 NCS。数据可选 AppWorld 或自己的多应用工具日志。不要只用成功率宣布胜利，也不要在 Claude 的 AppWorld 上看着 79.8% 对 79.2% 就声称全面超越 SWE-Pruner。风险是选择器过拟合某一种应用的字段（余额、日期），换到新工具模式会失效；以及 MEMORY 容量并不是越大越好，需要像 Table 3 那样扫 64 / 128 / 256。

人话版：这篇论文到底干了什么？

同步、同机部署的 LLM on-policy 强化学习有一个很具体的浪费：一个 batch 里总有几条特别长的 rollout，推理引擎要么空等长尾，要么以很小的 batch 低效解码。TIDE 不改梯度公式，而是在保持 on-policy 语义的前提下做两件事：长尾还没结束时，把已经空出来的 rollout GPU 临时改去跑训练；以及把未完成的 rollout 在推理引擎之间迁移，把解码 batch 重新做满。迁移时机由自适应策略决定，不必为每种应用手调。评估覆盖 DAPO Math、R1-Distill-8B、Text2SQL 和 Qwen2.5-Coder-7B，以及 H200 / H100 / L40S 三种拓扑。相对同机基线，端到端最高约 1.36×，并把“占最优吞吐的比例”从例如 R1-Distill-8B 的 83.2% 提到 97.4%。

方法：在哪里省时间，又不破坏 on-policy

RL 训练效率，而不是新的目标函数。 状态、动作、奖励和优势仍由上层算法（如 DAPO）定义；TIDE 是训练系统。On-policy 约束的含义是：用于更新的轨迹必须来自当前策略，不能为了填满 GPU 就提前拿旧策略的样本来凑。因此系统不能用经典的异步离策略缓冲来消灭长尾，只能在“同一批 rollout 尚未完成”的窗口里做文章。作者把同机执行的浪费拆成三类（Table 1）：空等长尾的 Idle loss、小 batch 解码的 Ineff. loss，以及引擎与训练器状态换进换出的 Misc. idle。四套应用里，Text2SQL 在 8×H200 上只有 56.6% 的最优吞吐，Idle loss 高达 30.0%；R1-Distill-8B 已经比较好，仍只有 83.2%。

两个机制对应两类损失。Repurposing：部分引擎已经完成自己的 rollout 时，不要让这些 GPU 空转，把它们切到训练侧，与仍在生成的长尾重叠。Migration：把卡住的请求搬到更空的引擎，恢复解码 batch。自适应迁移策略决定何时搬、搬哪些；KV veto 用来避免得不偿失的迁移（Table 3 里，8×H200 上加上 KV veto 后步进时间从 572.5 秒微升到 576.9，但 4×H100 上从 1052.4 降到 1002.9）。挑战在于切换开销、KV 缓存迁移成本和不要改变“这批数据来自当前策略”的语义。

结果与消融

Table 2 给出相对最优吞吐的比例：DAPO Math 8×H200 从 75.1% 到 87.0%；R1-Distill-8B 4×H100 从 83.2% 到 97.4%；Text2SQL 8×H200 从 56.6% 到 77.2%；Qwen2.5-Coder-7B 4×L40S 从 78.4% 到 95.1%。也就是说，原先越“不饱满”的应用，绝对提升越大，但没有任何一档宣称超过最优上界。Table 3 在 DAPO Math 上逐项叠加：同机 689.1 秒（1.00×）→ 加 Repurposing 666.8（1.03×）→ 加负载均衡 617.9（1.12×）→ 加 Migration 572.5（1.20×）→ 加 KV veto 576.9（1.19×，在这块 H200 上几乎持平）。4×H100（TIDE-FSDP）上没有负载均衡这一档，完整系统为 1.14×。正文还给出跨配置 1.16–1.36× 的总区间，1.36× 出现在 H200 测试床。最强基线就是同机同步系统，而不是已经拆分部署的 off-policy 流水线；若有人把 TIDE 和异步 RL 比速度，就比较了两种不同的语义。局限是：应用与硬件组合有限，Table 3 并非在所有拓扑上都单调变好，系统实现绑定具体训练栈。迁移价值很直接：任何做 on-policy LLM RL 的团队，如果 step time 曲线被长尾拉开，应先量 Idle / Ineff. / Misc. 三类损失，再决定是迁请求还是把空 GPU 切去训练，而不是先改算法。

读这些表时有一个容易误读的地方：97.4% 并不是“算法收敛到最优策略”，而是“这一步的 GPU 时间已经接近一个没有长尾、没有小 batch、没有切换开销的上界”。Text2SQL 即使上了 TIDE 也只有 77.2%，说明长尾特别重的应用，单靠迁移和改用途仍拿不回全部空隙，可能还要在数据侧截断或分组。Table 3 的非单调性同样重要：在 8×H200 上，Migration 已经把步进时间降到 572.5 秒，再加 KV veto 反而到 576.9 秒，但同一否决在 4×H100 上是净收益。所以 KV veto 不是无条件的加速器，而是对“这次搬迁会不会把 KV 白搬一次”的保险。作者强调自适应策略使配置不必为每个应用重写，这一点只能部分被 Table 2 的跨应用数字支持——我们没有看到策略在失败时的回退曲线。和今天的 ModHarness-RL、MMFlash 放在一起，TIDE 提醒的是另一层：即使目标函数不变，on-policy 的墙钟效率已经足够成为独立问题。最小迁移是：在现有同步训练栈上先打点三类损失占比，若 Idle loss 超过百分之十，再尝试在长尾窗口里把空闲推理 GPU 切去跑训练；迁移请求作为第二步，并务必带上类似 KV veto 的成本开关。不要为了填满 GPU 就把上一策略的样本混进当前 batch，那已经离开本文坚持的 on-policy 语义。若你的栈已经是分离式的推理集群加训练集群，TIDE 的同机假设不一定成立，此时更该先问调度层能否在长尾窗口做等价的改用途，而不是直接搬论文里的实现细节。报告结果时也应同时给出 step time 和“占最优吞吐的比例”，只报加速倍数会掩盖 Text2SQL 那种即使加速后仍远离上界的情况。

人话版：这篇论文到底干了什么？

屏幕历史可以成为人或计算机使用智能体的可视记忆，但它必须在每张截图到达时就被编码进索引，不能等离线再跑。OCR 索引快，却丢掉版式和图像；完整视觉编码在他们的测量里超过两秒，跟不上两秒一张的屏幕流。关键观察是：连续屏幕高度冗余，多数像素在邻块之间、在相邻截图之间是重复的。StreamEmbed 只根据像素差，做两件事：空间 token 剪枝，跳过与邻居重复的块；时间上复用未改变块的 KV。再用一个小的一致性适配器，把剪枝和复用后的表示拉回完整编码。他们发布 ScreenMemEval：两个人和一个计算机使用智能体共 184 小时、10,426 道题。在 M2 Pro 上，相对完整截图编码最快约 3.7×，并在匹配延迟下比 OCR 索引最多高 6.3 个 Recall@10 点。

方法与效率机制

输入是按时间到达的截图流，输出是可检索的嵌入索引。空间剪枝在 ViT 网格上跳过与邻居几乎相同的块，并保留一定的网格结构（消融里去掉 grid keep 会在 SME-Agent 上从 57.1 降到 55.2 R@10）。时间 KV 复用则在跨截图仍未改变的块上，直接重用缓存的键和值，避免 ViT 与后续语言模型部分的重复计算。一致性适配器是唯一需要学习的小模块，用来补偿剪枝和复用带来的分布偏移，目标是贴近完整截图嵌入，而不是另训一个检索模型。指引信号只有像素差，没有OCR 或额外的语言模型判断，这使它可以跟在截图后面实时跑。

许多多智能体论文把“几个会通信的模型”去和“一次贪心单次解码”比，然后宣布协调有用。这篇综合研究指出，这样比把样本数和推理计算都算进了协调的功劳。作者整理了 9 项主要实证、516 种多智能体配置，用六维资源向量和四档基线梯子重新对齐比较。相对贪心单次（Category A），总体差异为负，去掉贡献最大的那项研究后接近零；相对样本数对齐（B）或资源预算对齐（C）的基线，多智能体平均准确率差为 −0.042，74% 的可比对照中多智能体不高于基线。所谓约 45% 能力阈值，在抽出的数据里也站不稳。

分析

概念框架把常见混淆写成可检验的来源：上下文拥挤、token 被脚手架稀释、以及“看起来像协调、其实只是多采了几次样”。四档基线是这篇工作最可迁移的工具：A 是一次贪心；B 对齐样本数（例如多数投票、重复采样）；C 对齐总资源预算；D 则更接近真正控制通信本身。PACE 协议要求报告资源向量，而不是只报准确率。综合结果的方向很一致：一旦把样本和预算对齐，通信架构的平均优势消失，甚至为负；多层次随机效应在对数几率尺度上的估计同样为负，并对敏感性检查保持符号。实践含义不是“不要做多智能体”，而是：若你的对照还停留在贪心单次，就还没有证明协调的价值。最小的下一步，是把已有多智能体系统放到 Category B/C 对照下重评，看优势是否还在。局限也很明显：这是对已发表对照的再综合，不是一组在统一代码库里重跑的新实验；研究间任务结构差异大，负平均不能排除在特定分工或工具协议上存在正收益。作者在附录里也列出了尚未被这些对照检验的正收益假说，那些才是还值得做新实验的地方。对今天的正式论文来说，这篇综合像一条方法学警戒线：ModHarness-RL 比较的是同一预算下的不同脚手架，对照是干净的；但若有人把“多智能体加通信”只拿去打一次贪心解码，PACE 会把它记成 Category A 的表观收益。审稿清单和配套代码降低了复现门槛，值得作为评估工具保存，而不必把它的负平均读成多智能体研究的终审判决。

B ReDiverse：蒸馏后的少步图像/视频生成并不缺方差，缺的是方向（Video Generation Quality after Distillation）

B Restoring Diversity in Distilled Image and Video Generators by Probing Activations

  • Affiliation: University of Illinois at Urbana-Champaign（Horoz, Kara, Rehg）；fal（Oktay, Akan, Atakan Kara）；Johns Hopkins University（Bhattad）。Bhattad 与 Rehg 为通讯作者。
  • Date / Venue / Status: arXiv 2611.18550v1，submitted 2026-11-13，周一 2026-11-16 公告（cs.CV）。非正式发表。
  • Links: arXiv:2611.18550 · PDF · Code: github.com/H-furkan/rediverse · Models: huggingface.co/ReDiverse

人话版：这篇论文到底干了什么？

把扩散模型蒸馏成少步学生，采样会快很多，但不同随机种子生成的样本往往几乎一个模样。作者探测学生相对教师的内部激活，发现学生的总激活方差并不明显更小，而是把方差集中进了少得多的方向；这种方向坍缩可以定位到初始去噪步的某个中间块。因此多样性崩溃被解释成方差分配错误，而不是生成能力被蒸馏掉了。ReDiverse-FT 用轻量适配器在这些丢失方向上做对齐；ReDiverse-TF 则是训练免费的随机转向。两者可组合。图像和视频（包括 Wan 2.1）上都给出了多样性指标和相对学生的成对胜率。

分析

对视频加速这条线，这篇工作的位置很清楚：它不减少步数，而是修补“已经减少步数之后”的质量。若多样性崩溃来自某一个可识别的块，那么修复不必重训整个学生。Table 7 列出了各骨干上坍缩的块与教师回归步，例如 Wan 2.1-T2V-14B 的学生是 lightx2v，坍缩块为 block 28，教师回归步为 8。成对比较（Table 16）上，ReDiverse 在 SDXL 的 DINO / TPIPS 多样性上相对学生分别以 95% / 97% 的提示赢过，但 CLIPScore 只有 38% 更高，说明多样性和对齐之间仍有折中；SD3 上 DINO / TPIPS 为 100% / 99%，CLIPScore 31%。视频表给出教师、FastVideo 与 Turbo 的 DINO、V-JEPA2、TPIPS、ViCLIP 等参考，Turbo 的多样性掉得更厉害（DINO 35.8 对教师 55.3）。主张的强处是机制定位清楚，并同时提供训练与免训练两条修复；弱处是主表数字在图像上更完整，视频对比需要结合附录阅读，且转向可能轻度牺牲对齐。它与“少步蒸馏加速”是互补问题：加速若以模式坍缩为代价，墙钟收益会在应用侧被抵消。最小实验是：在一个已有的少步视频学生上，按论文协议找出初始步方差最集中的块，先试 ReDiverse-TF，用 DINO / TPIPS / ViCLIP-S 同时看多样性与对齐，不要只报看起来更花的样本。和 MMFlash、TIDE 不同，ReDiverse 不声称墙钟更快，它问的是加速之后还剩多少可分的样本模式。若你的少步视频管线已经在线上，这是比再追 0.2× 加速更可能改变用户体验的修补。局限是探测协议依赖教师可访问，闭源学生若拿不到对应教师激活，训练免费转向也需要对准的方向估计来源。附录还比较了注入教师方向、学生方向或随机方向，主方法选择对准教师中丢失的那些方向，而不是加噪声式地“把方差打散”。

Idea Mining

以下四条都来自今日正式论文的交叉，而不是关键词拼接。每条都可以在一周到数周的预算里做最小实验。

Idea 1（最佳）：把 Steering 触发器编译到 CarryOn 的带出处证据上

  • Inspiration: ModHarness-RL 的可回放 steer 程序；CarryOn 的控制状态 + 源链接证据。
  • Gap: CarryOn 的选择器学习“留下什么”，但不检测可验证失败，也不会在失败走平时才插入指导；ModHarness 的触发器作用在工具轨迹记录上，没有把“精确字段的出处”当成一等对象。
  • Hypothesis: 在 AppWorld 一类多应用任务上，用确定性程序检查证据槽位（例如余额被覆盖、同一订单 ID 出现冲突）并按回放曲线闸门安装指导，会同时提高成功率并降低 NCS，且优于只做 CarryOn 选择器或只在扁平抄本上做 Steering。
  • Method: 保持 Actor 与奖励不变；上下文一律写成状态 + 证据单元；Steering 只读这些单元，不另请 LLM 改写历史；Compression 若使用则锁定。
  • Minimum Viable Experiment: AppWorld 训练/测试拆分，Qwen3 或同等 7–8B Actor，GRPO 或冻结 Actor 的推理期对比均可先做推理期版本以降低成本。
  • Model / Dataset / Baseline / Metric: Qwen3-8B 或 Claude 之一；AppWorld；Full History、CarryOn、扁平 Steering、本文组合；成功率、S0.8、NCS、指定失败模式的频率曲线。
  • Expected Contribution: 证明“证据选择”和“失败干预”可以共享同一份可审计 State，而不必再训练一个摘要模型。
  • Novelty ★★★★☆ / Feasibility ★★★★☆ / Compute ★★☆☆☆（推理期版本成本更低；若上 GRPO 则升到 ★★★）。
  • Risk: 触发器在应用字段上过拟合；闸门样本过小。
  • Collision Risk: 中等，见下文与 HyperSkill / Experience-Handoff 的差别。
  • Best Venue: ACL / ICLR / 智能体专项Workshop 之后的正式会议。

Idea 2：把 TIDE 的长尾改用途接到智能体 GRPO

  • Inspiration: TIDE 的 Idle / Ineff. 分解；ModHarness 在 ALFWorld 上最多 50 回合、CodeSearch 上工具输出很长。
  • Gap: TIDE 评估的是数学、蒸馏和 Text2SQL 等相对短的生成，没有报告家庭任务或仓库定位这类超长尾智能体 rollout。
  • Hypothesis: 智能体轨迹的 Idle loss 将高于 DAPO Math 的 15.2%，仅 repurposing 一项的相对收益就会超过 Table 3 里的 1.03×。
  • Minimum Viable Experiment: 在 8 GPU 同步 GRPO 栈上跑 ALFWorld 或 CodeSearch，先打点三类损失，再打开“长尾未结束时把空推理 GPU 切去训练”，保持 on-policy 批次语义。
  • Model / Dataset / Baseline / Metric: Qwen2.5-7B 或 Qwen3-8B；ALFWorld 或 SWE-Smith；同机同步系统；step time、占最优吞吐比例、最终任务分数（须验证不掉点）。
  • Expected Contribution: 给 agent RL 提供一张可公开的利用率分解，而不是只报算法分数。
  • Novelty ★★★☆☆ / Feasibility ★★★☆☆ / Compute ★★★☆☆
  • Risk: 切换开销吃掉收益；实现绑定训练栈。
  • Collision Risk: 低到中，是 TIDE 在新负载上的迁移，需明确新负载特征。
  • Best Venue: MLSys / EuroSys / ICLR 系统与学习交叉。

Idea 3：用像素差候选帧，再计算帧级视觉依赖，为视频投机解码选上下文

  • Inspiration: MMFlash 把 token 级 KL 当训练信号，并承认视频仍用启发式稀疏；StreamEmbed 只用像素差决定复用。
  • Gap: MMFlash 的 stride-32 不看问题，对所有远帧一视同仁；若对每一帧都跑两次目标模型算 KL，离线成本会爆。
  • Hypothesis: 先用像素差（或时间 KV 是否可复用）筛出“看起来在变”的帧，只在这些帧上计算有图/无图或有帧/无帧的依赖分，再让草稿器优先保留高依赖帧，将在 LongVideoBench 上以接近稠密的 τ 达到不低于 MMFlash 稀疏模式的加速。
  • Minimum Viable Experiment: 冻结已有 MMFlash 或 DFlash 草稿器，不改损失，只改可见视觉上下文的选择；对比固定 stride-32、随机采样、像素差筛选 + 依赖打分。
  • Model / Dataset / Baseline / Metric: Qwen3.5-4B；LongVideoBench / Video-MME；MMFlash 稀疏模式；τ、墙钟加速、按问题类型拆分。
  • Expected Contribution: 把“问题相关的视觉上下文”做成可离线预计算的选帧规则，而不是再训一个重的视频草稿器。
  • Novelty ★★★★☆ / Feasibility ★★★☆☆ / Compute ★★★☆☆
  • Risk: 像素差在镜头运动上会全选中，退回近似稠密；依赖分定义在帧级可能不稳定。
  • Collision Risk: 中，与 MMFlash 自己的未来工作陈述相邻，必须强调像素差预筛和“不改损失、只改可见上下文”的差分。
  • Best Venue: CVPR / ECCV / NeurIPS 效率轨。

Idea 4：用 PACE 的 Category C 预算，重评可学习脚手架对“更多智能体”的优势

  • Inspiration: PACE 的负平均；ModHarness 在单策略、同训练步数下的正收益。
  • Gap: 两者都还没有回答：若把 ModHarness 多出来的训练时教师调用，拿去加采样或加一个通信同伴，谁会赢。
  • Hypothesis: 在 Category C 对齐后，单策略 + 程序脚手架仍优于同样 token 预算的双智能体通信，至少在 CodeSearch 定位任务上如此。
  • Minimum Viable Experiment: 固定总生成 token 或总教师调用，比较 Base、ModHarness-RL、以及样本对齐的单智能体 self-consistency。
  • Metric: Overall F1、每成功样本的 token、PACE 资源向量。
  • Novelty ★★★☆☆ / Feasibility ★★★★☆ / Compute ★★★☆☆
  • Collision Risk: 低，属于评价协议落地。
  • Best Venue: 评价与智能体研讨会，随后 ICLR/ACL。

Collision Detection

⚠️ Collision Warning：Yes（有条件撞题，不是题目已被关闭）。

ReDiverse vs eDMD（Nov 14 Tier A，arXiv:2611.17194）。 两者都处理少步蒸馏生成。eDMD 从端点分布匹配入手改善少步扩散蒸馏；ReDiverse 从学生激活方向坍缩入手恢复多样性。已解决的部分是“少步学生会塌”，但塌的机制和修复对象不同。剩余缺口：把方向修补接到 eDMD 类蒸馏目标里，是否还能在 Wan 2.1 上同时保住多样性和对齐。仍值得做，但必须把 eDMD 列为对照，而不是只对学生本身比。

ModHarness-RL vs Experience-Handoff / HyperSkill（近七日正式论文）。 都在回答“哪些经验应该留下来影响以后的策略”。Experience-Handoff 把经验写成按再执行奖励记账的 playbook；HyperSkill 写成冻结骨干上的超图技能库；ModHarness 把经验编译成对 State 的确定性程序，并用回放曲线决定何时干预。重合在“经验外置”，差分在“可执行、可回放、闸门安装、压缩锁住”。仍值得做 Idea 1，但相关工作必须点名这三篇。

MMFlash vs ForeSpark（Nov 13 Tier A）。 同属投机解码的预算与调度；ForeSpark 关心并行投机里草稿与验证的预算，MMFlash 关心多模态 token 的视觉依赖重加权。重合是系统层加速，机制几乎不重叠。Idea 3 需避免写成 ForeSpark 的多模态换皮。

CarryOn / StreamEmbed vs 近七日记忆工作（MemInStream、Cleaning History、When Should Agents Remember）。 都谈记忆与遗忘，但 MemInStream 是流视频记忆评测，Cleaning History 给出“世界里错误还在时改写历史会伤害恢复”的反例，CarryOn / StreamEmbed 分别是应用轨迹上下文与屏幕像素索引。没有关闭题目，只是任何“改写历史”的设计都必须把 Cleaning History 当作失败边界。
