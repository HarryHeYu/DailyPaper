5.2 一句话定位

这篇论文指出 unlearning 的根本问题之一不是 loss，而是 forget set 与模型真实 memorized knowledge 不一致；CONFS 在不访问训练数据的前提下，从模型自身输出构造更对齐的 forget set。

5.3 人话版

绝大多数 unlearning 工作默认用户能够精确给出模型需要忘掉的知识，然后研究 GA、GD、NPO、RT 等 objective。但现实中用户通常不知道模型究竟记住了哪些细节。作者把这种错位分成两类：Under Unlearning——模型真正记住的知识有一部分没被请求覆盖，留下 privacy leakage；Out-of-Knowledge Unlearning——请求包含模型从未学过的事实，优化器仍强行压低这些答案，从而造成一般能力损伤。作者先用受控 TOFU 与 gradient inner product 说明两类 failure 的机制，再提出 CONFS：只给模型目标实体名，让它“confess”自己知道的事实；把自然语言 claim 拆成 Subject-Relation-Object triplets；递归 reconfession 补充属性级细节；生成 atomic competency questions；最后通过多次目标模型采样 + DeBERTa-v3-large NLI 过滤 hallucinated/unreliable facts。TOFU、CLEAR、RWKU 上，CONFS 在完全 data-blind 的条件下比 FreeRecall-QA 和 RWKU-style 更接近 Gold-standard，并更好保护 retain utility。

5.4 Background & Research Gap

TOFU、CLEAR、MLLMU 等 benchmark 为可控评测，通常先注入 synthetic persona，再把同一批注入知识作为 forget set，因此“模型知道什么”与“用户要求删什么”天然一致。现实 privacy request 并没有这种 oracle。用户可能要求删除教育经历、职业与家庭信息，但模型也许只记得前两者，并额外记得一个用户自己没写出的奖项。

直接使用用户 request 会同时造成漏删与错删：漏掉的奖项继续可恢复；模型没记住的家庭事实却会被 unlearning objective 强行压低。本文真正填的 gap 是：在训练数据不可见时，先近似恢复 model knowledge boundary，再执行 unlearning。

5.5 Core Insight

第一，Under Unlearning 不会自动按“实体”泛化：显式 requested facts 会先下降，同一实体未请求事实仍保持很高概率。第二，对模型从未学过的 facts 做 unlearning，其梯度与 retain gradient 的 overlap 更高，因此 utility damage 更大。第三，一次 free recall 不足以覆盖模型知识，还必须将 claims 原子化、递归 probing，并过滤模型自身无法稳定支持的 facts。

5.6 Method Deep Dive

Target entity E → Confession using only entity name → raw claims → SRO triplet extraction → subtriplet decomposition → reconfession decision → selective attribute probing → atomic leaf knowledge units → competency question generation → target-model sampling N=5 → DeBERTa-v3-large contradiction filtering, τ=0.7 → model-aligned forget set F_CONFS → GA / GD / NPO / RT → Forget + Retain + Real-world + MIA evaluation

Confession：只输入实体名，避免把外部新知识注入 forget set。

SRO：长 claim 可能混有多条事实，因此先拆成可独立验证/删除的原子事实。

Reconfession：已有 leaf 作为 cue，继续询问更细属性，主要减少 Under Unlearning。

Competency Questions：每个 leaf 变成一个或多个直接 QA，答案只来自 leaf，不允许引入额外事实。

Hallucination Verification：目标模型对 CQ 随机采样 5 次，NLI contradiction 过高则丢弃，主要减少 Out-of-Knowledge。

5.7 核心公式与数学直觉

L(q,a;θ) = -Σ_t log p_θ(a_t | q,a_

真正 memorized target 的 g_(L+) 更像定向删除；never-seen target 的 g_(N+) 没有对应的已学知识盆地，因此实测更容易与 retain gradient 重叠。也就是说，错把“模型不知道的内容”放进 forget set，会让优化器为了压低一个本就不稳定的答案而做更广泛参数更新。

关键超参：τ=0.7 与 reconfession depth。τ 太宽会引入 hallucination；太严会漏低置信但真实 memorized facts。GD/NPO 能缓解 utility loss，但如果 F 本身错了，objective 无法从根本修复。

5.8 Toy Example

模型关于虚构作者 Lina 真正记住 MIT、小说 A、Boston。用户只请求删除 MIT、小说 A，并错误加入 Nobel Prize。普通 F 会漏掉 Boston，同时对 never-seen Nobel 强行 unlearn。CONFS 让模型自述 Lina，得到 MIT/小说A/Boston；拆成 SRO；reconfession 发现 MIT→degree=CS；生成 CQs；Nobel 因目标模型无法稳定支持而被过滤。最终 F_CONFS 更接近真正 memory boundary。

5.10 Experiment Setup Deep Dive

Controlled analysis：TOFU 200 fictitious entities，取20个目标；每target选15个QA，平均分为 D_L+（memorized+requested）、D_L-（memorized+not requested）、D_N+（not memorized+requested）。

Main datasets：TOFU、CLEAR、RWKU。Models：LLaMA-2-7B-Chat；CLEAR 为 LLaVA-1.5-7B。Objectives：GA、GD、NPO、RT。

Training：TOFU/RWKU full-parameter，effective batch16，LR=1e-5；CLEAR LoRA rank8、alpha16、dropout0，effective batch8，LR=1e-5。

Compute：单 H200 141GB；7B sampling peak约20GB；单实体 CONFS 构造约4.1min；单次 unlearning run约10min。

Research Questions：misalignment 是否造成两类 failure？gradient overlap 是否解释 utility degradation？CONFS 是否逼近 Gold-standard？reconfession/filter 各承担什么？是否跨 text/multimodal/real-world成立？

5.11 Metrics 教学式解释

Probability↓ on Forget / ↑ on Retain：teacher-forced ground-truth likelihood。ROUGE-L↓ on Forget / ↑ on Retain：测生成表面相似，但对同义改写敏感。Truth Ratio：正确答案相对错误候选的偏好。MIA：检查成员特征，但不能单独证明真正删除。D_N+ share、cos(g_N+,g_retain)、retain ΔL、E_tf/E_eg：本文最重要的 misalignment diagnostics，直接测 target quality 与 gradient interference。

5.14 Ablation / Mechanistic Analysis

去 Reconfession：coverage下降，Under Unlearning加重。去 Hallucination Verification：更多不稳定 facts 进入 F，Out-of-Knowledge增加。τ：控制 precision-recall trade-off。Forget-set size：Appendix 表明性能差异不能仅由集合更大解释，target quality才是关键。Gradient 分析属于局部一阶机制，不等于 representation-level causal tracing。

5.15 Claim vs Evidence

Authors Claim：可靠 unlearning 依赖 forget set 与 model memory 对齐；CONFS 可在 data-blind 下逼近 Gold-standard。
Experiments Actually Show：受控 misalignment + gradient overlap + 三 benchmark 多 objective 结果支持这一点。
What Is Not Yet Proven：模型能 confess 出来的知识不等于全部 memorized knowledge；稳定回答也不等于训练记忆；没有 adaptive recovery attack 测 silent memory。

5.2 一句话定位

PlanFence 指出 distributed agents 即使已读到最新共享事实，也可能继续执行由旧事实生成的 plan；它用 exact derivation lineage + dependency-scoped action-time validation 保证外部 action 仍由当前 authoritative state 授权。

5.3 人话版

多 Agent 系统常把共享状态复制给不同角色。直觉上，executor 在工具调用前读取最新 requirement 就安全了，但作者发现不是：planner 早先基于 r3 生成 plan p3，之后另一个 Agent 更新为 r4；executor 虽然已经收到 r4，却仍可能拿 p3 的参数去订票、发货或部署。这个 failure 叫 stale-plan execution。PlanFence 让每个 derived plan 记录精确 parent record IDs，并由 tool wrapper 声明 action 真正依赖的 keys D(a)。执行前，系统沿 plan lineage 得到 frontier F_a(x)，再向 authoritative owner 查询当前 head H(x)。全部相等才授权；若不等，抓取新版本、允许一次 replan，再检查；任何缺失、冲突或二次变化都 fail closed。30个 live workflows 中 freshness-only 每次都执行旧 action，而 PlanFence 全部修复；controlled replay 中高 churn 下它比其他 safe policy 更省 stall/traffic，且 keyspace 扩到128时 traffic 仍约8.1KiB/action。

5.4 Background & Research Gap

Agent memory研究经常讨论 retrieval、replication、consistency、CRDT、provenance和shared memory。一个常见但错误的假设是“只要 executor 有最新 state，就不会执行旧决策”。事实上 derived plan 可能跨 role call、replica 和 memory refresh 长时间存活。

例如 planner 根据“部署 build A”生成 plan p3，之后 requirement 改成“部署 build B”。executor 本地已看到新 requirement，但 p3 不会自动被重写。本文把数据库里的 read-set validation 思想迁到 Agent：不是确认当前数据 fresh，而是确认这个 derived artifact 当初读的版本仍是 current。

5.5 Core Insight

State freshness ≠ plan authorization validity。 H(x)回答“现在权威版本是什么”；F_a(x)回答“这个 plan 到底基于哪个版本”。真正需要验证的是 F=H。第二，validation scope 应由 tool contract 定义，而不是 LLM 自由描述。第三，coordination placement 存在 regime boundary：低 churn proactive sync 更便宜，高 churn/大无关 keyspace 下 action-time dependency validation 更便宜。

5.6 Method Deep Dive

Versioned public state → semantic key x has owner o(x) and head H(x) → planner creates plan root L(a) → every derived public record stores exact parent IDs → tool wrapper declares D(a) → before external action: traverse exact lineage compute F_a(x), x in D(a) → query owners concurrently for H(x) → if all F_a(x)=H(x): authorize → if mismatch: fetch changed records one fresh replan validate again → second mismatch / missing lineage / malformed response: fail closed → log validation point + outcome

Immutable records：semantic key 标识逻辑对象，record ID 标识具体版本；owner sequence 单调。

Exact parents：plan必须记录实际输入版本，不能只写“使用了最新 requirement”。

D(a)：由应用 tool wrapper 声明会影响 action 的 public keys。

Frontier：从 plan root 沿 parents 到 dependency boundary，得到 plan 实际使用版本。

One-replan：不匹配时只允许一次修复；第二次变化直接 block，避免无限 replan loop。

5.7 核心公式与数学直觉

A = {a_1,...,a_N} x ∈ X o(x): authoritative owner H(x): current authoritative record ID D(a) ⊆ X: declared action dependencies F_a(x): record ID actually used by plan lineage Valid(a) ⇔ F_a(x) = H(x), ∀ x ∈ D(a)

这个 invariant 把“当前状态”和“当前计划的推导来源”绑定。若 protected actions 间有 R 次 dirty updates、N agents、d=|D(a)|，per-update metadata sync 提前传播 O(RN) heads；all-key validation 每次处理 |X|；PlanFence 只处理 d 个真正依赖。

关键变量不是学习率，而是 D(a) 的 completeness。 漏一个真实依赖，系统会错误授权；D(a) 过大则退化为 all-key validation。

5.8 Toy Example

五个 Agent 做机票预订。Planner 读 r3“上海，9月10日”生成 p3；之后 owner 更新 r4“北京，9月11日”。Executor 已同步 r4，所以 freshness check 通过，但 p3 parent 仍是 r3。tool 声明 D(book)={destination/date, policy}。PlanFence 得到 F(destination)=id_r3，而 owner 返回 H(destination)=id_r4，因此拒绝直接订票并 replan；新 p4 基于 r4 后 F=H，才允许执行。若 replan 后又变成 r5，则 block。

Research Questions：最新 state 是否仍能执行旧 plan？何时 proactive sync 更优、何时 action-time validation 更优？keyspace增大时 dependency scope 能省多少？

5.11 Metrics 教学式解释

Invalid/issued↓：已发出 action 中 lineage 未覆盖 current declared inputs 的比例，是最直接安全指标。Available/scheduled↑：防止通过“全部 block”伪装安全。Stall↓：同步/验证引入的 critical-path 等待。Traffic↓：跨 replica/central service bytes。Task completion↑：live workflow是否完成；不能把 controlled replay 直接解释成一般任务准确率。

5.12 Results Deep Dive

  1. 30个 live workflows 中 freshness-only 每个任务都发 obsolete action；PlanFence 30/30 修复并完成。
  2. Primary replay：Local replica 330/330 invalid；Owner-head freshness也330/330 invalid。
  3. Centralized、Metadata K=1、Batched all-key、PlanFence 全部0/330 invalid、330/330 available。
  4. 高 churn 成本：PlanFence230.8ms/8.1KiB；Centralized508.6/15.6；Metadata403.4/23.5；Batched258.4/16.4。
  5. Delayed sync K=2/4/8/16 stall333.1→60.7ms，但 invalid42/330→291/330，清楚显示 safety-latency trade-off。
  6. ρ≤1时 proactive sync多半更快；ρ≥4时 PlanFence 在8/8网络×设置 cells领先 runner-up 1.5×–7.1×。
  7. Loopback 128 keys：Batched199.2ms/81.7KiB，PlanFence66.0ms/8.1KiB。
  8. AT&T 128 keys：Batched428.7/81.7，PlanFence345.2/8.1。
  9. d=1时 PlanFence223.6/8.1 vs all-key262.8/16.4；d=8=|X| 时421.7/36.8 vs400.1/34.1，变为 practical tie。
  10. owner outage、missing lineage、malformed head、second version change 四类异常下 fail-closed 全部 block；fail-open 全部错误放行。
Strongest result：freshness-only 在 live 与 replay 中稳定失败，而 exact-lineage policies 为0 invalid，干净隔离了 failure model。
Weakest：低 churn proactive sync 更快；d≈|X| 时 dependency scoping优势消失。
Failure：安全保证依赖 benign owners、exact parents 和完整 D(a)，不覆盖 Byzantine owner 或漏依赖。

5.14 Ablation / Mechanistic Analysis

Freshness only：有最新 head 但无 exact parents → 330/330 invalid，说明 fresh 不是核心机制。K>1 delayed sync：同步越少越快但越不安全。All-key vs dependency scope：相同 replan 规则仅改变 scope，直接验证 D(a) 节省无关工作。Fail-open：四类异常全部错误放行，证明 fail-closed 不是实现细节。Appendix 的 learned selector 在 OOD shift 下没有稳定压过透明规则。

5.15 Claim vs Evidence

Authors Claim：fresh state 不足以保证 pending action正确；exact lineage + dependency-scoped validation 在特定 regime 下兼顾安全与效率。
Experiments Actually Show：3 workflow families、3–8 agents、多个 network traces 中复现 stale-plan，并在高 churn/大 keyspace 下低成本保持安全。
What Is Not Yet Proven：Byzantine owners、owner migration、自动依赖推断、semantic merge、private reasoning lineage、multi-owner atomic snapshot、validation 到 external side effect 的 transaction atomicity。

5.16 Contribution

  • New Failure Mode：stale-plan execution。
  • New Formal Invariant：F_a(x)=H(x)。
  • New System：PlanFence action gate。
  • New Evaluation：safety/availability/stall/traffic matched replay。
  • New Empirical Finding：coordination placement 存在 churn crossover。
  • New Negative Boundary：d≈|X| 时 scope 优势消失。

5.17 Limitation & Failure Modes

Authors：只覆盖3 workflow families、3–8 agents、constructed keyspaces 与少量历史网络 traces；要求 benign owners、exact parents、完整 D(a)。
Additional：手写 D(a) 可能成为新 bug；private context 依赖不可见；validation 后到 external commit 仍有 race；semantic equivalence 不等于 exact ID；高 fan-in actions 重新变贵；summary/compression 可能破坏 parent chain；过度 fail-closed 可能降低开放式 Agent 可用性。

5.20 Migration Analysis

Original Problem →阻止旧共享事实驱动 stale action。

New Research Question →canonical memory 已删后，旧 plan/summary/tool args 是否仍携带被删知识？
Method Modification →derived carrier记录 exact parents；forget时 owner head 更新为 tombstone/new version；protected action前 lineage check；依赖 deleted ancestor则 recompute。

5.21 Attack / Verification Lens

可构造 Stale-Plan-after-Unlearning：先让 Agent 基于敏感 memory 生成 plan/tool args，再删除 memory 并刷新共享 state，最后触发旧 plan。定义 Stale Derivation Leakage Rate (SDLR)：canonical target 已删除后，旧 lineage action 仍泄漏 target 的比例。

  2. stale-plan execution 是 derivation stale，不是 state stale。
  3. plan 必须记录 exact parent IDs。
  4. tool wrapper 必须声明 D(a)。
  5. 安全条件是 F_a(x)=H(x)。

Combined Research Opportunities

Best Migration Direction — Model-Aligned + Lineage-Closed Unlearning

Deletion request → model-aligned discovery → atomic forget facts → unlearn/delete canonical memory → update authoritative versions/tombstones → forward-slice downstream dependency graph → invalidate stale summaries/plans/skills/tool args → action-time lineage validation → black-box recovery + retain audit → closure certificate

Collision / Overlap

Strongest Collision：CONFS 与 TAS 都挑战“forget target已知”假设，但 TAS 是攻击者从 refusal trace 猜 target，CONFS 是 defender 从模型自述构造 F。新工作应比较 Requested Set / Confession Set / Recovery Set，而不是简单把 TAS 换成 CONFS 搜索器。PlanFence 与 MutMem V2/Governed Shared Memory 在 provenance 上邻近；真正差异化应放在“删除后旧 derived plan 仍执行”的行为泄漏，而不是再做签名 receipt。
