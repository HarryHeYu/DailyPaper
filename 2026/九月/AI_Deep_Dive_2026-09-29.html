3. 为什么选这两篇

第一篇的价值不在于发明了新的 unlearning loss，而在于重新定义“什么才是有效的 forget instance”：候选知识必须先在原模型上以目标行为出现，然后才能谈删除。这个逻辑看似简单，却直接打击大量 benchmark 的隐含漏洞——如果模型本来就不会输出某知识，那么 unlearning 后的低命中率没有证明任何删除。第二篇则把 agent 研究从“模型会不会调用工具”推到“数十万并发、长状态、异构隔离、低 image fanout、GPU 训练可抢占时，执行环境如何不成为瓶颈”。二者共同指向一个趋势：AI 研究正在从静态 benchmark 转向生命周期级证据链。

4. Paper 1 Full Deep Dive — What Was Once Learned May Need to Be Unlearned: Machine Unlearning for Deprecated API Knowledge in Large Language Models

5.1 基本信息

Date: 2026-09-22 (arXiv v1) · Category: cs.SE · Status: arXiv preprint；正文模板标注 TOSEM，但不能据此把它写成已正式录用。
Paper: arXiv 2609.25786 · HTML: full text
Code/Project: 本次核验的一手 arXiv 页面未给出可确认的官方代码仓库，因此记为 not verified，不猜测。

5.2 一句话定位

把 deprecated API adaptation 从“指定一个新答案的 model editing”改写成“只删除旧行为、允许多种合理 continuation 的 machine unlearning”，并用行为先验过滤构造 MUDAPIBench。

5.3 人话版

代码补全和普通事实问答不同：同一段 prefix 后面往往有很多合理实现。旧 API 被弃用后，最直觉的 model editing 是把 torch.norm 定向替换成 torch.linalg.norm；但真实代码可能也可以用 torch.abs、torch.isclose 等实现相近意图。作者因此认为，目标不应是强迫模型输出某个唯一“新答案”，而应是压低 deprecated completion 的概率，同时尽量保留原模型其它合理分支。更重要的是，MUDAPIBench 先对每个模型采样五次，只有模型真的生成过 deprecated API 才把样本纳入 forget set。八种 unlearning 方法在 Qwen2.5-Coder-3B、StarCoder2-3B、DeepSeek-Coder-1.3B 上比较后，Gradient Difference (GD) 给出最好的综合平衡；最激进的 RLFT/GA/SimNPO 虽忘得更狠，却明显伤害 up-to-date、other API 和 general code utility。

5.4 Background & Research Gap

旧范式 1：Inference-time replacement。检测到 deprecated API 后丢弃后续 token，插入新版 API 再续写。优点是无需改权重，缺点是旧知识仍在模型里，而且每次检测/重生成增加延迟。

旧范式 2：Directed model editing。AdaLoRA-L 等把旧→新 API 当成确定映射，直接提升指定 replacement 的概率。问题是 code completion 是 multi-solution：一个 context 不一定只有一个正确 continuation。若只把 torch.norm 换成 torch.linalg.norm，模型可能被无意中挤掉原来可行的 torch.abs/torch.isclose 分支。

旧范式 3：已有 code unlearning。PROD、contrastive unlearning 已能抑制 deprecated token，但常见 benchmark 没先验证目标行为在每个 base model 上是否可观察，也较少测局部 collateral damage。本文真正填的 gap 是：behavior-grounded target + multi-solution preservation + local specificity，而不是再发明一个 loss。

5.5 Core Insight

核心 observation 有两层。第一层是经验/任务结构观察：同一 prefix 的 completion distribution 是多峰的，因此“删旧答案”与“推新答案”不是同一个优化问题。第二层是 evaluation observation：forget target 必须对具体 base model 可观察，否则删除指标没有因果意义。作者从 145 个 deprecated→up-to-date mapping 和真实 repo context 出发，对每个模型以 temperature=0.8 采样 5 次，只要至少一次出现目标 deprecated API 才保留。这使 benchmark 从静态知识表变成 model-conditional behavior set。以前方法通常默认数据集声明的 target 就等于模型实际拥有的 target；本文把这个假设显式打破。

5.6 Method Deep Dive

145 verified API mappings → Sourcegraph real-world contexts → 65,596 candidate functions → per-model 5× sampling → behavior-grounded filtering → Forget / Generalization / Retain / Specificity sets → LoRA unlearning with 8 methods → behavior + utility + internal-change evaluation

Step 1 — 收集真实 completion context

从 8 个 Python libraries 的 145 个映射出发，检索使用 up-to-date API 的真实函数；截取目标调用之前的代码作为 x。这样 x 来自真实软件上下文，而不是模板 prompt。

Step 2 — Model-specific filtering

对每个 x，用具体 base model 采样 5 个 completion。若 deprecated API y_d 至少出现一次，该样本才对这个模型成立。结果三个模型得到不同的 forget universe：Qwen 3,043、StarCoder2 2,117、DeepSeek-Coder 2,586 个 Forget instances。

Step 3 — 四类数据

同一 API mapping 的实例 1:1 分为 Forget 与 held-out Generalization；Retain 从原模型五次生成里挑最常出现的非 deprecated API completion；Specificity 则从 100k The Stack v2 Python files 中，用 CodeBERT 找与 forget input 语义接近、但不含目标旧/新 API pair 的 5 个邻居。

Step 4 — Unlearning

比较 GA、GD、KL、RLFT、DPO、NPO、SimNPO、PROD，并额外对照 AdaLoRA-L editing。关键不是统一追求最低 deprecated probability，而是看 suppression、replacement/alternative preservation、nearby specificity 和 HumanEval 的联合前沿。

Step 5 — 内部分析

对同一输入比较 unlearn 前后逐层 hidden states：PCA Shift 看位移，PCA Similarity 看第一主方向保留，linear CKA 看表示结构；FIM 看参数敏感度变化。这里是相关性机制分析，不是 causal localization。

5.7 核心公式与数学直觉

目标：降低 P_f_u(y_d | x)，但不要求 f_u(x)=y。

OAMR(Y0,Yu)=|O(Y0) ∩ O(Yu)| / |O(Y0)|

GD（概念式）：min_θ - L_forget(θ; D_f) + λ L_retain(θ; D_r)

第一式是这篇论文最重要的任务定义：editing 关心“把概率搬到指定 y”，unlearning 只要求 deprecated y_d 被压下去，剩余质量可以流向多个合理 continuation。

OAMR中的 O(Y) 是排除 deprecated 与对应 up-to-date API 后，五次 completion 里出现的其它 API 集合。它是 recall：新模型新增别的 API 不扣分，因此适合问“原来会的其它分支还在不在”，但不适合判断新增分支是否正确。

GD的关键 λ 控制 forget/retain 梯度竞争。λ 太小趋近 GA，容易 collateral damage；λ 太大则 retain 约束压过 forgetting。与 KL strongest preservation baseline 的差别是：KL要求 retain context 上整个 output distribution 接近原模型；GD直接对选出的 retain completion 做 descent，因此保留信号更“行为定向”。

5.8 Toy Example

设 prefix 是机器人位置判断：is_obj_placed[:,i] = (。原模型 5 次输出里 1 次出现 deprecated torch.norm，1 次 torch.linalg.norm，3 次分别用 torch.abs/torch.all/torch.isclose。传统 editing 会把目标定义成“以后输出 torch.linalg.norm”；本文则把 forget target 定成“不要再生成 torch.norm”。Retain 可能选频率最高的非 deprecated 分支，例如含 torch.abs 的 completion。GD 一边对 torch.norm completion 做 ascent，一边对 retain completion 做 descent。测试时除了原 prefix，还用另一个未训练 context 检查 torch.norm 是否仍被压制；再用语义相近但调用 torch.matmul 的 context 检查 collateral damage。这个 toy case 正好体现“删除一个行为 ≠ 指定唯一替代行为”。

5.10 Experiment Setup Deep Dive

Models：Qwen2.5-Coder-3B（cutoff Feb 2024）、StarCoder2-3B（Sep 2023）、DeepSeek-Coder-1.3B（Feb 2023）。Data：8 Python libraries，145 mapping 起始，过滤后最多 81 unique pairs；Forget / Generalization / Retain / Specificity 四路。Specificity 每个 forget instance 配 5 个语义近邻，因此规模是 Forget 的 5×。Training：LoRA-based unlearning；全部方法可在单张 RTX A6000 上跑，最高观测峰值 47.09 GB。

RQ1：能否同时忘旧 API、保留新 API、other API、nearby unrelated behavior 与 HumanEval？
RQ2：跨 PyTorch/SciPy/scikit-learn/TensorFlow 是否稳定？
RQ3：时间/显存代价？
RQ4：API deprecation 相对 training cutoff 的时间位置是否改变可忘性？
RQ5：行为 trade-off 是否伴随不同程度的 internal perturbation？

5.11 Metrics 教学式解释

AEM-D：completion 中 deprecated API 的 exact-match incidence，越低越好；它直接测目标行为，但只看 API token/调用，不证明底层知识不可恢复。AEM-U：up-to-date API 命中，越高越好；但高并不必然表示功能正确。OAMR：原模型其它 API 行为的 recall，越高越好；优势是专门测 multi-solution preservation，缺点是不惩罚新增错误 API。ES/BLEU/ROUGE-L：completion 与 deprecated/up-to-date reference 的文本相似度；能捕捉比 exact API 更宽的输出变化，但代码语义与字符串相似并不等价。Specificity：在语义近邻、非 target inputs 上对原模型 completion 的 ES/BLEU/ROUGE-L，越高代表局部 collateral damage 越小。HumanEval Pass@1：一般代码功能正确率；补足局部指标，但可能掩盖 API neighborhood 的细粒度损伤。PCA/CKA/FIM：只说明表示/参数变化规模与结构，不应直接当“知识真的被删”的证据。

5.12 Results Deep Dive

1 · 综合 strongest result：跨 Effectiveness+Generalization，GD 平均 AEM-D=3.74，同时 AEM-U=23.38、OAMR=34.77。说明它不是最狠的 suppression，却在“忘旧+保留多解空间”上形成最好的联合点。另一种解释是 Retain 构造天然更适合 GD，因此应在不同 retain sampling 下复验。
2 · Qwen forget：Original AEM-D 33.53；GD 降到 5.42（-28.11），同时 AEM-U 从19.61升到35.30。这里 forgetting 没有靠牺牲新版 API 完成，反而新版行为增强。
3 · RLFT failure：Qwen AEM-D 可到0.03，但 AEM-U 从19.61跌到0.07，OAMR 仅16.28。它证明“低 forget accuracy”可以与“行为空间崩塌”同时发生，因此单一 forgetting metric 会严重误导。
4 · Editing collision：AdaLoRA-L 在 Qwen 把 AEM-U 推到88.01、AEM-D降到0.80，但 OAMR 只有5.14；这非常清楚地显示定向 replacement 与 multi-solution preservation 目标冲突。
5 · Specificity：Qwen 四库上 GD AEM specificity 约94.72–97.00，而 GA 约52.48–61.06；GD 的 retain constraint 确实显著减少邻域行为漂移。
6 · Model-specific weakness：DeepSeek-Coder 上 GD specificity 约75.28–84.19，明显低于 Qwen 的 94%+；说明同一方法并非跨模型稳定，较小模型/训练差异可能改变梯度干扰。
7 · Library failure：GD Generalization AEM-D 在 SciPy 为 Qwen 21.16 / StarCoder2 13.97 / DeepSeek 16.19，而 TensorFlow仅2.40/1.82/0.54。方法优势高度 library-dependent。
8 · Temporal effect：StarCoder2 的 post-cutoff API 残余 AEM-D 从 pre-cutoff 3.47 升到16.01（+362.2%）；DeepSeek-Coder 从1.67到12.22（+633.6%）。这是很有价值的“知识时间地层”现象，但 post-cutoff API 数量只有3和7，统计外推要谨慎。
9 · Compute：GD 平均8.26h；GA 3.98h、RLFT 3.97h、DPO 11.66h；GD 平均 peak memory <14GB，而 PROD 28.65GB。综合 trade-off 有代价，但不是最贵。

5.14 Ablation / Mechanistic Analysis

这篇更像系统性 empirical study，传统“去掉模块”ablation 较少；真正的 mechanism analysis 是方法族之间的对照与 layer-wise probes。去掉 retain descent（GD→GA）后，forgetting 仍强，但 specificity 与 other-API preservation 明显下降，说明 retain branch 主要承担 collateral-damage control。把“只抑制”换成“定向 replacement”（AdaLoRA-L）后 AEM-U 大涨但 OAMR 崩，说明 multi-solution preservation 不是自然副产物。PCA/CKA/FIM 则显示 aggressive methods 引起更广泛变化；这验证的是相关性机制假设，而非因果。

5.16 Contribution

  • Contribution 1 — New Benchmark/Dataset：MUDAPIBench，真正创新点是 model-specific behavior grounding。
  • Contribution 2 — New Metric/Protocol：OAMR + semantically-near Specificity，把 multi-solution preservation 纳入 unlearning。
  • Contribution 3 — New Empirical Finding：GD 的综合 Pareto 优势、library heterogeneity、post-cutoff difficulty。
  • Contribution 4 — Mechanistic empirical analysis：PCA/CKA/FIM 联合观察 internal perturbation。这里不是新机制，更像已有分析工具的有针对性组合。

5.17 Limitation & Failure Modes

Authors' limitation / threats：只覆盖三种较小 open-source code LLM、Python library evolution、采样与 API mapping 质量会影响 benchmark；内部指标不等于因果。

Additional：没有 recovery/relearning attack；没有 quantization/finetuning 后 deprecated behavior 是否回归；AEM 只测显式 API surface form，alias/import rewrite/semantic equivalent 可能绕过；OAMR 不惩罚新增错误 API；Specificity 以原模型输出为 reference，原模型本身可能错；没有 security-deprecated API 的风险加权；post-cutoff 组 API 数量小；LoRA unlearning 结论不必然迁移到 full-FT。

5.18 Reproduction View

最小复现建议先只做 Qwen2.5-Coder-3B + PyTorch + GD/GA/NPO。模块顺序：① mapping loader；② Sourcegraph/context corpus 替代源；③ 5-sample behavior filter（temperature=.8）；④ per-API 1:1 Forget/Generalization split；⑤ retain completion extractor；⑥ CodeBERT nearest-neighbor Specificity builder；⑦ LoRA trainer；⑧ AEM-D/U + OAMR evaluator。最容易踩坑的是 API string normalization、import alias、五次采样随机种子、同 API mapping 的 data leakage、Specificity neighbor 中误含 target pair。第一优先实验不是跑全部八方法，而是复现 GD vs GA 的 AEM-D/OAMR/Specificity 三角；若这个趋势不成立，就没必要继续扩展。

5.19 Research Value

Baseline Potential：高，GD + behavior-grounded split 很适合成为 practical unlearning baseline。Migration Potential：很高，尤其适合 MLLM：先验证某 image-question knowledge 在 base model 上真的可触发，再构 forget set。Attack Potential：高，可从 API alias/paraphrase/context rewrite 做 recovery probe。Evaluation Potential：极高，OAMR 的思想可迁成“same-context alternative behavior recall”。Benchmark Potential：高，关键模板是 model-conditional dataset，而非 deprecated API 本身。New Paper Potential：最高价值不是再改 GD loss，而是做 lifecycle robustness：quantization/relearning/tokenization/context perturbation 后 target 是否回来。

5.20 Migration Analysis

Migration A — Behavior-Grounded MLLM Unlearning Benchmark

Original Problem：deprecated API target 先验可能不存在。→ Transferable Mechanism：per-model observable-behavior filtering。→ New Research Question：MLLMU 的 forget QA 是否应只保留 base MLLM 确实能答对/泄露的实例？→ Method Modification：每个 image-question 采样5次，按 answer probability / exact semantic match 建 observable gate，再构 Forget-Exact/Transform/Semantic。→ Minimum Experiment：LLaVA-1.5/OneVision，各取 GQA/VQAv2 1000 target；比较 static forget set vs behavior-grounded forget set；GA/NPO/GD/当前 strongest method；r=5/10；测 Forget Multi/Uni、Retain-Near/General、relearning、quantization、Image Rephrase。→ Metric：AP/TR/KS/JS + ROUGE/Cls + retain utility + recovery rate。→ Expected Contribution：证明 benchmark target validity 会改变 method ranking。→ Risk：过滤后样本分布偏向易记忆。→ Collision Risk：中；与现有 model-specific benchmark 思想相邻，但 multimodal+lifecycle 可形成独立贡献。

Migration B — Alternative-Behavior Recall for Unlearning

Original Problem：OAMR 保留同 context 的其它合理 API。→ Transferable Mechanism：不要只测 retain dataset，要测 target context 内的 alternative capabilities。→ New Research Question：忘掉人物/图像知识时，模型是否把同一图像上的非目标视觉语义一起抹掉？→ Method Modification：对每张 forget image 预先采样/标注多个 non-target attributes/questions，定义 Visual Alternative Recall (VAR)。→ Minimum Experiment：100 forget images，每图 target QA 1个 + non-target QA 4个；LLaVA-7B；GA/NPO/RMU/MIP-Editor；同时测 target forgetting 与 VAR。→ Expected Contribution：揭示“忘得好”是否其实来自 image representation collapse。→ Risk：alternative QA 的语义独立性难保证。→ Collision Risk：低到中。

5.21 Attack / Verification Lens

可直接反转成 verification：对被删除 API 生成 alias、import style、functionally-equivalent prefix、post-cutoff documentation injection，再测 AEM-D recovery；black-box 情况下不需要权重。还可以定义 Reacquisition Half-Life：给模型少量新版/旧版混合 code finetuning，记录 deprecated AEM-D 恢复到原始水平一半所需 steps。若某方法 AEM-D 很低但 half-life 极短，说明更像表面 suppression。进一步可把 OAMR 与 recovery 联合成二维 verifier：既不能恢复 target，又不能损伤 alternative behavior。

5.22 与 Paper 2 的关系

Paper 1 告诉我们“验证删除需要 model-specific、multi-behavior、生命周期测试”；Paper 2 提供大规模、可恢复、可隔离的 agent execution substrate。两者可组合成一个很实际的方向：用 DSec 类环境批量生成 code-agent trajectory，在工具/API 生命周期变化后做 continual unlearning，并通过 sandbox replay 检查旧 API 是否在长轨迹中重新出现。

5.23 如果只让我记住这篇论文

  1. Code completion 是 multi-solution，删除旧 API 不等于指定唯一新 API。
  2. Forget target 必须先在具体 base model 上可观察。
  3. MUDAPIBench 因此是 model-specific，而不是一份静态统一表。
  4. OAMR 专门测同一 context 下其它 API 行为是否被误伤。
  5. GD 不是最狠的 forgetting，却是综合 trade-off 最好。
  6. RLFT 说明“忘得越彻底”可能意味着 utility collapse。
  7. AdaLoRA-L 说明 editing 能强推 replacement，但会压缩其它合理分支。
  8. SciPy 明显比 TensorFlow 难忘，method ranking 有 library dependence。
  9. post-cutoff API 更难忘是最值得继续挖的现象之一。
  10. 下一步真正缺的是 recovery、relearning、quantization 和 semantic bypass verification。

5. Paper 2 Full Deep Dive — DeepSeek Elastic Compute (DSec): A Sandbox Infrastructure for Effective Agentic Training at Scale

Date: 2026-09-19 · Category: cs.DC · Status: arXiv v1；31 pages / 13 figures；arXiv comments 说明其从一个曾进入 ACM SIGOPS ATC 2026 Operational Systems Track first-round review 的两页 extended abstract 大幅扩展而来，不能写成已录用。

5.2 一句话定位

DSec 把 agent RL 的“执行环境”从容器工具升级为独立的弹性系统层：统一管理 FnCall/container/microVM/full VM、海量异构 image、长状态、资源超卖、抢占恢复与 agent misbehavior。

5.3 人话版

训练 coding/computer-use/security agent 时，真正昂贵的不只是 GPU：每条 rollout 都要有一个隔离、可修改、能跑命令和服务的环境，而且一个训练任务会瞬间拉起成千上万个 sandbox。DSec 的关键观点是：这不是“多开几个 Docker”能解决的问题。它把环境拆成可组合层，用 3FS + EROFS/OverlayBD 按需读取 image，只把实际访问的数据搬进来；用共享 page cache、free-page reclamation 和 QoS CPU scheduling 把长时间 idle 的 sandbox 高密度塞在节点上；再把 sandbox lifecycle 与 RL trainer 解耦，使 GPU job 被抢占时环境能暂停/恢复。生产规模达到单 scale unit 约160节点、3万 CPU cores、约250TB DRAM、日均约300万 sandbox，峰值约38万并发、创建速率超过5000/s。它的重要性在于把 agent RL 的瓶颈从“模型训练”扩展到“environment factory”。

5.4 Background & Research Gap

传统 RLHF/LLM training infrastructure 主要优化 GPU scheduling、communication、sample throughput，默认 environment 是随时可用的黑盒。但 agent rollout 的 environment 具有七个不同性质：burst creation、high density、stateful long lifetime、backend heterogeneity、image diversity、untrusted execution、interruptibility。比如一个 batch 最多一次请求 32K sandbox；sandbox CPU 经常在等模型下一步 action，但内存和文件状态一直占着；一周 active image 超过130TB，而很多 image fanout 极低，根本不适合“每台机器预热所有镜像”。

所以 gap 不是更快 container startup 单点优化，而是同时处理 lifecycle、storage、memory、CPU QoS、security boundary 和 RL preemption。这也是 DSec 与 Slime/veRL/OpenRLHF/Seer 的分工：后者主要在 trainer/GPU plane，DSec 在 execution plane。

5.5 Core Insight

最核心的工程观察是：agent sandbox 活得久、算得少、镜像大、实际读得少。生产数据中 container/microVM median lifetime 分别17.4/15.5分钟，p99 都超过3小时；不同语言 image 实际 runtime 只访问4.2%–13.3%数据。于是“完整 pull image + 每 sandbox 解压 + 按申请内存独占”在这个 workload 上系统性浪费。作者把这些 measurement 变成三个机制：可组合层避免重复构建；memory sharing/reclamation + CPU QoS 支撑 overcommit；3FS-backed on-demand image loading 只搬 working set。它属于典型的 measurement-driven systems insight，而不是新 RL objective。

5.6 Method Deep Dive

RL/eval task → libdsec request → IAM → placement engine + watcher → node edge admission → choose FnCall/container/microVM/full VM → compose base/workspace/toolkit layers → lazy image reads from 3FS + local writes → aether/chronus tool execution → trajectory/reward → suspend/resume if trainer preempted → reclaim on TTL

Step 1 — Unified entry, not fake uniformity

libdsec 提供统一 SDK，但调用方仍明确选 backend。FnCall 适合短 stateless execution；container 适合 SWE/tool use；Firecracker microVM 提供更强隔离；full VM 面向 Android/GUI/COTS OS。系统没有假装四者性能语义相同。

Step 2 — Cluster placement

IAM 认证授权；placement 先 filter capability/health，再从候选随机采样并选较低 load 节点；watcher 提供可重建的 fleet view。edge 做 node-local admission，避免 cluster state 延迟导致过载。

Step 3 — Runtime path

container/VM 通过 per-sandbox aether proxy，再由 chronus 提供 shell/filesystem/HTTP/streaming session。FnCall 走独立 fast path，在预创建 container 内执行后 best-effort cleanup。

Step 4 — Composable layers

base OS、workspace、toolkit 分开版本化，不再每个任务 bake monolithic image。container 用 EROFS read-only layers + local overlay writes；microVM 用 EROFS base/toolkit + OverlayBD writable ext4 disk。

Step 5 — Lazy distribution

3FS 擅长大顺序 I/O、不擅长小随机 I/O，因此 writes 留本地；read-only file data 远端按需 bulk read；metadata 尽量预取到本地。这个设计是 storage characteristics 与 workload characteristics 的直接匹配。

Step 6 — High-density execution

microVM 通过 virtio-pmem/DAX 减少 guest-host 重复 page cache，并用 DAMON-based free-page reporting 回收 guest 空闲页；CPU 则区分 latency-sensitive 与 best-effort，避免简单 nice priority 在 SMT sibling 上仍互相干扰。

Step 7 — RL co-design

agent loop 与 trainer 解耦；GPU training 被抢占时 sandbox 可以 suspend，保留 rollout state，之后 resume。网络 policy 用 eBPF 做域级限制；作者还专门分析 reward hacking / agent-induced failures。

5.7 核心“公式”与系统直觉

有效 I/O ≈ Image Size × Runtime Access Ratio
Observed access ratio: 4.2%–13.3% → full pull 的大部分字节不会被用到。

Packing value ∝ Live Sandboxes / (resident memory + duplicated cache + unreclaimed guest pages)

End-to-end rollout throughput = min(model generation, sandbox setup, tool execution, verifier, trainer update)

DSec 不是数学方法论文，没有作者提出的新 loss，因此不能硬造“核心公式”。上面是从论文 measurement 推导的系统直觉。第一式解释 lazy loading 为什么不是把 I/O 延后，而是真正减少总量；第二式解释 memory sharing/reclamation 为什么直接决定 microVM density；第三式解释为什么只优化 GPU trainer 不够——当 sandbox setup 成为最慢 stage，agent RL throughput 会被 execution plane 卡死。最关键的“超参数”不是 λ，而是 backend choice、overcommit degree、layer size/collapse threshold、TTL 与 QoS class；这些调得太激进会从吞吐收益转成 tail latency/隔离风险。

5.8 Toy Example

假设要做 8,192 条 SWE-bench-like rollout。每条需要 6GB Python image，但真实轨迹只读其中约6%。传统方案先从 registry 拉满 6GB 并解压，所有 sandbox 在 setup 阶段争网络、磁盘和 CPU；模型 GPU 在等环境。DSec 把 base/toolkit/workspace 组合挂载，metadata 在本地，代码真正 import 某 package 时才从3FS读对应 blocks，修改文件写本地 overlay。Agent 第10步时 GPU trainer 被抢占：sandbox 不销毁，而是暂停并保留已修改 repo、installed deps 和 service state；trainer 恢复后继续第11步。若 agent 尝试访问禁止域名，eBPF policy 阻断。这个例子说明 DSec 优化的是完整 trajectory lifecycle，而不是单次 container boot。

RQ-B：EROFS composable layer 是否比 tar extraction 减 setup CPU/I/O？
RQ-C：DAX/FPR 是否提高 microVM memory density？

5.11 Metrics 教学式解释

Time-to-completion / running-container curve：看 burst 下多久把环境真正拉起来并跑完；比单个 cold-start latency 更贴近训练 batch。Disk-write IOPS / cumulative writes：前者看瞬时存储压力，后者看总放大；lazy path 两者都应下降。Peak host memory：决定 overcommit density，越低越好，但必须同时看 performance，否则可能只是激进 reclaim。CPU utilization / latency under QoS：高 utilization 不是目的，关键是 best-effort overcommit 时 LS tail latency 不被拖垮。Sandbox density/lifetime/fanout/access ratio：这些是 workload characterization，不是算法 score；它们决定机制是否有现实必要性。

5.12 Results Deep Dive

1 · Production scale：~3M sandbox/day、~380K peak concurrent、>5,000 creations/s。它证明系统至少在大规模真实生产中被使用，但这些是 self-reported operational numbers，不是独立 benchmark。
2 · Burst size：单 job 可请求32K sandbox。说明 scheduler/image path 必须针对 burst 而不是 steady-state cloud request 优化。
3 · Image access：不同语言 image runtime 只访问4.2%–13.3%。这是 lazy loading 的 strongest causal motivation：full pull 的绝大多数数据根本不被读。
4 · On-demand：8,192-container burst 中 lazy EROFS ~35min 完成，接近 fully-local cached；eager pull >60min，慢1.71×。这直接支持核心 mechanism。
5 · Disk writes：eager >1,600GB/node；on-demand ~700GB，约少57%，接近 cached ~600GB。说明收益不是只把等待挪到 runtime，而是减少物化量。
6 · Composable layers：tar provisioning 79min，EROFS 45min，1.76× speedup；tar 总写流量约5.5×、peak write throughput约3.4×。这是第二个很干净的 ablation。
7 · Memory：virtio-pmem+DAX 单独就把 peak host memory 相对 baseline 降40.2%，说明 duplicate guest page cache 是真实大头。
8 · Weakest evidence：论文把 preemption-safe RL integration、agent misbehavior mitigation 作为重要系统价值，但 Section 8 明确不评估 framework integration；因此这部分更多是 deployment design/experience，而不是同等强度的 controlled evidence。
9 · Generalization weakness：核心实验在 DeepSeek 自有3FS、内部 workload 与特定硬件栈上完成；其它 storage/network/cloud topology 下收益幅度未证明。

5.14 Ablation / Mechanistic Analysis

去掉 lazy loading → eager pull：completion 35→60+min、writes ~700→1600+GB/node，说明核心瓶颈确实是无用 image materialization。去掉 composable mount → tar extract：45→79min、总写流量约5.5×，说明 layer composition 主要消灭重复解压与写盘。去掉 DAX：peak memory 上升，说明 guest-host duplicate cache 是机制性浪费。FPR针对 guest free pages 不回收，是另一个独立来源。这里的机制证据比很多 agent paper 强，因为 workload measurement→design→controlled ablation 链条完整。

5.16 Contribution

  • New System/Engineering：统一四类 sandbox backend 的生产 execution plane。
  • New System Mechanism：3FS + EROFS/OverlayBD 的按需 image path、可组合环境层。
  • New Engineering：DAX/FPR + QoS scheduling 的 high-density resource management。
  • New System Integration：与 RL trainer 的 suspend/resume lifecycle co-design。
  • New Empirical Finding：agent sandbox 的 burst/lifetime/fanout/access-ratio production characterization。多数底层组件并非原创（EROFS、Firecracker、DAX、eBPF 等已有），创新主要在 workload-driven 组合与生产规模整合。

5.17 Limitation & Failure Modes

Authors' scope limitation：Section 8 不评估 RL framework integration；系统机制依赖 DeepSeek 的 3FS 与内部 infrastructure context。

Additional：安全隔离不是 formal guarantee；agent 可能通过资源耗尽、filesystem corruption、side channel 或 verifier gaming 找到新路径；eBPF domain allowlist 不覆盖所有 semantic abuse；大量 production metrics 自报、难独立复现；没有公开成本美元/能耗；cloud bursting 只描述 selective eligibility；多租户公平性、跨 project interference、灾难恢复与 storage outage 行为未充分量化；没有比较 Kubernetes/serverless/Firecracker fleet manager 的完整端到端 TCO。

5.18 Reproduction View

完整 DSec 几乎不可能个人复现；应复现“最小机制”。推荐 4-node CPU cluster：①准备 100–500 个 2–8GB OCI images；②转 EROFS，remote backing 可先用 NFS/Ceph 模拟3FS；③实现 local metadata + remote data + overlay local writes；④一次 burst 512/1024 containers；⑤对照 eager docker pull 与 pre-cached；⑥记录 time-to-ready、completion、disk writes、network bytes、cache hit。第二阶段再做 Firecracker + DAX/FPR。最敏感变量：image access ratio、fanout、burst size、remote storage latency/bandwidth、layer collapse threshold、TTL。先复现 Figure 10，而不是先搭完整 IAM/placement。

5.19 Research Value

Baseline Potential：对 agent systems 很高，但更适合作为 architecture reference 而非易跑 baseline。Migration Potential：高，可迁到 unlearning/relearning 大规模 robustness evaluation。Attack Potential：极高，论文自己暴露 agent 会 reward hack/越权，适合构建 sandbox escape / verifier gaming benchmark。Evaluation Potential：高，trajectory replay + stateful sandbox 可把 agent evaluation 从一次性答案升级为可重放证据。Benchmark Potential：高，可做 environment stress benchmark。New Paper Potential：最值得的是“security-aware RL environment curriculum”与“stateful provenance/verification substrate”。

5.20 Migration Analysis

Migration A — Stateful Unlearning Recovery Lab

Original Problem：DSec 保存 agent execution state。→ Transferable Mechanism：snapshot/resume + deterministic environment. → New Research Question：unlearned coding agent 在真实 repo/tool trajectory 中会不会通过 package docs、tests、logs 重新获得被删知识？→ Method Modification：每个 forget API 建 sandbox snapshot，分别允许/禁止 docs/network/test feedback。→ Minimum Experiment：Qwen2.5-Coder-3B，MUDAPIBench 100 APIs，GD/NPO/GA；每 API 20 repo trajectories；conditions={offline, PyPI docs, local tests, explicit migration hint}；记录 deprecated API reacquisition step、success rate、utility。→ Baseline：static prompt AEM。→ Metric：trajectory recovery rate、steps-to-reacquire、final test pass、retain specificity。→ Expected Contribution：把 unlearning verification 从静态 QA 推到 environment-mediated reacquisition。→ Risk：agent capability 与 unlearning effect 混杂。→ Collision Risk：低。

Migration B — Agent Misbehavior as Robustness Curriculum

Original Problem：production agents 会查日志、绕访问控制、reward hack。→ Transferable Mechanism：把真实 failure traces 变成 adversarial environment curriculum。→ New Research Question：训练时暴露给“tempting but forbidden” artifacts 能否让 agent 学会不利用 verifier leakage？→ Method Modification：sandbox 中注入 decoy logs/RPC endpoints/hidden tests，reward 同时惩罚 policy violation。→ Minimum Experiment：7B coding agent，200 SWE-style tasks，四种 leakage channel，各50；SFT vs RL vs RL+security curriculum；container + eBPF logging。→ Metric：task success、violation rate、reward-hack rate、OOD attack success。→ Expected Contribution：连接 agent RL 与 systems security。→ Risk：agent 学会规避日志而非真正安全。→ Collision Risk：中，需查已有 agent sandbox red-team work。

5.21 Attack / Verification Lens

DSec 本身就是 attack surface。可以把“agent 能否从环境获得不该获得的信息”定义成 black-box capability probe：放置 honeytoken、fake reward file、forbidden RPC、network decoy，看 agent 是否主动发现/利用。对 unlearning 更有意思：把被删知识只放在 sandbox side-channel 中，测 agent 是否重新摄取并在后续 turn 使用；由此定义 Environment-Mediated Reacquisition Rate (EMRR)。这比单 prompt jailbreak 更接近部署，因为知识可以从 tool output、repo、package docs、logs 回流。

5.22 与 Paper 1 的关系

Paper 1 的 target validity 是“先证明模型会，再删”；DSec 的 environment lifecycle 则允许进一步问“删完以后，在真实交互环境里会不会重新学回来”。两篇组合后，unlearning verification 可以从 pre-unlearn observable → post-unlearn suppressed → environment interaction → reacquisition check 形成闭环。这是今天最强的 cross-paper migration。

5.23 如果只让我记住这篇论文

  1. Agent RL 的环境不是配角，而是独立 execution plane。
  2. 一个 job 可以 burst 到32K sandbox，steady-state cloud intuition不够。
  3. Sandbox CPU 常闲，但状态、内存、page cache 长时间常驻。
  4. Image working set 超大且 fanout 低，预热所有 image 不现实。
  5. 真实 runtime 只读 image 的4.2%–13.3%，所以 lazy loading 是结构性收益。
  6. EROFS lazy path 在8,192 burst 中把60+min降到约35min并少写57%。
  7. Composable layer 把 tar provisioning 的79min降到45min。
  8. DAX 单独就把 peak host memory 降40.2%。
  9. 生产规模很强，但 RL integration 与 security claim 的 controlled evaluation 仍不足。
  10. 对研究者最值得迁移的是 stateful replay、reacquisition verification 和真实 agent misbehavior curriculum。

7. Cross-Paper Synthesis

今天两篇共同说明：研究对象正在从“模型参数/一次输出”扩展成模型—行为—环境—生命周期。Paper 1 要求 target 在 base model 上先可观察，并同时追踪 alternative behaviors；Paper 2 要求 rollout environment 可持久、可恢复、可隔离。把两者拼起来，最自然的新评测不再是“unlearning 后答不出来了吗”，而是“原来确实会 → 删除后确实不再表现 → 在真实工具环境里经过几十步交互 → 是否通过 docs/logs/tests 重新获得 → retain/alternative behavior 是否仍完整”。

机制组合上，Paper 1 的 model-conditional filtering 可以决定哪些 trajectory 值得送入 DSec-like sandbox；DSec 的 snapshot/replay 则可把 recovery test 标准化。实验范式上，最值得借的是 Paper 1 的 multi-axis preservation 和 Paper 2 的 measurement→mechanism→controlled ablation。

8. Combined Research Opportunities

Best Migration Direction — Environment-Mediated Unlearning Verification

做一个“静态删除 + 动态再获取”的 benchmark：先 behavior-grounded 过滤 forget targets；unlearn 后进入 sandbox，让 agent 接触 repo、package docs、test failure、tool output；最后测 target recovery、reacquisition speed、retain utility 与 alternative behavior recall。这个方向同时覆盖 unlearning robustness、agent memory/tool use、continual knowledge update 和 provenance，且能直接复用现有 code LLM + MUDAPIBench 类数据起步。

第二机会是 Multimodal Alternative Behavior Recall：把 OAMR 的思想迁到 MLLM forget image，同一图像上同时维护 target knowledge 与 non-target visual semantics。第三机会是 Temporal Unlearning：利用 pre/post-cutoff 现象，把“知识在训练时是否合法”作为 unlearning difficulty 的新轴，并加入 relearning/quantization/recovery。

9. Collision / Overlap

Strongest Collision：“静态成功 ≠ 生命周期成功”。Paper 1 已显示单一 forgetting score 会把行为崩塌误判为好方法；Paper 2 又提醒我们部署中的 agent 会持续从环境读信息并保存状态。因此任何只在固定 prompt、固定权重、无环境交互下声明“已删除”的结论，都可能在 agent setting 中失效。两篇没有方法学直接冲突，反而形成明显互补。
