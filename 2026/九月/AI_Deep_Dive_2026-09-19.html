4. Paper 1 Full Deep Dive

Paper 1 — An Empirical Study of Harness Design for Coding Agents

5.1 基本信息

Authors：Run-Ze Fan, Zihao Zhang, Simin Ma, Yebowen Hu, Shouju Wang, Kaiqiang Song, Fei Liu, Hamed Zamani, Xiaoyang Wang。Affiliation：UMass Amherst、Emory University、UNC Charlotte；部分工作在 Zoom Video Communications 实习期间完成。Date：2026-09-17。Status：arXiv:2609.20804v1 preprint。Paper：arXiv / HTML / PDF。论文页未确认官方代码仓库。

5.2 一句话定位

把 coding-agent harness 拆成 planning、action space、context management 三个可控组件，回答同一模型换外壳后为什么会变强、变弱、变贵或变便宜。

5.3 人话版

本文不是再造一个 agent，而是做“harness 解剖”。作者固定 ReAct loop、安全、诊断和 stuck detection，只改变 plan、工具接口和 context policy，在 Nemotron-3 30B/120B/550B 与 Mistral-Medium-3.5-128B、SWE-Bench Verified 与 Terminal-Bench 2.1 上形成 176 个 matched settings。最重要的发现是：context management 的大部分收益来自避免小窗口 overflow；recoverable recall 几乎没人主动用；planning 对弱模型是能力脚手架，对强模型主要省冗余成本；structured tools 对 bash 弱模型有帮助，而强 shell 模型反而可用 bash-only 组合更密集动作。贡献不在某个单独组件，而在证明 harness 设计必须 model/task/budget-aware。

5.4 Background & Research Gap

完整 agent 系统比较会把 prompt、plan、tools、context、verification 混在一起。例如 32k 窗口下 agent 还没 edit 就因 grep/read 输出爆窗；加入 summarization 后成功率上升，不代表“推理更聪明”，可能只是活得更久。本文通过固定执行 substrate 并对 trajectory phase 做标注，填补“组件贡献不可归因”的 gap。

5.5 Core Insight

核心 observation 是 组件边际价值是条件性的。Context management 更像 survival mechanism；planning 改变 trajectory 停止位置；action space 改变单次操作粒度。这是经验/系统发现，不是理论定理。它反驳“planning 总有益”“memory 可恢复总有益”“工具越丰富越好”等默认假设。

5.6 Method Deep Dive

Task + repo/container → fixed ReAct loop → planning ON/OFF: persistent update_plan → structured tools OR bash-only → tool execution + observation → context T0–T4 → fixed safety/diagnostics/stuck detection → repeat ≤300 steps → verifier + cost + trajectory analysis

T0 无管理；T1=M1 elision；T2=M1+M2 external store/recall；T3=M3 LLM summarization；T4=M1+M2+M3。T4 在 soft threshold 先删除 bulky middle observations 并存档，hard threshold 才 summary；preamble 与最近至少两轮保持 verbatim。Structured interface 提供 read/write/edit/list/glob/grep/web_fetch/bash；bash-only 移除这些 workspace tools。Planning 启用时 plan 每轮注入但不累积进普通 history。

5.7 核心公式与数学直觉

if tokens(H) ≥ B1: elide bulky middle observations; archive originals if tokens(H) ≥ B2: summarize oldest middle events B1=.60×window; B2=.85×window; recent=.30×window SR = solved/tasks paired significance = exact McNemar + BH FDR q<.05

B1 越低越早丢细节但越抗 overflow；B2 越低 summary 越频繁、成本与失真风险越高。论文没有训练 objective，数学核心是预算策略与 paired inference。Strongest causal baseline 是 T0；planning/action 的基线是 T4/128k full-tool+plan。

5.8 Toy Example

Voyager 修 session-index bug：前20轮 grep/read 已产生45k tokens。32k 的 T0 直接死；T1 把旧 grep 输出变 stub；T2 虽可 recall，但模型若从不调用 recall_event 就几乎等于 T1；T4 先 elide，逼近85%再 summary。强 shell 模型可以一次 grep && edit && pytest，bash-only 省交互；弱模型则需要 typed tools 防命令错误。

5.10 Experiment Setup Deep Dive

Models：Nemotron-3 30B/120B/550B、Mistral-Medium-3.5-128B；SGLang BF16，temperature=0，top-p=.95，单轮最多16384 tokens。Datasets：SWE-Bench Verified 500题；Terminal-Bench2.1 89题。Budgets：32k/64k/96k/128k × T0–T4；planning/action ablation 仅 T4/128k；共176 settings。LangGraph+Harbor，最多300 steps，tool output 24k chars，最多8 read-only tools 并行。RQ：context 收益是否随窗口缩小？recall 是否真被用？planning 是否随能力变角色？structured tools 是否总更好？

5.11 Metrics 教学式解释

SR↑：verifier 通过率；直观但不解释失败阶段。Mean Cost↓：按 token 价格算每题成本，不等于 latency/energy。Overflow rate↓：解释 context policy 的关键中介变量。Trajectory phase/length：区分“改变策略”和“只是延寿”。McNemar+BH：同任务 paired outcome，控制多重比较，比只看百分点可靠。

5.12 Results Deep Dive

  1. 32k SWE：30B T0 约9.4%，T3 23.8%、T4 21.2%，小窗管理显著救活 run。
  2. 32k Mistral：T0 12.6%，T1 64.4%、T2 66.2%、T4 63.8%，极大 survival gain。
  3. 64k 550B：T0 29.4%，T3 65.8%、T2 64.6%。
  4. 96k Mistral：T0 66.2%，T4 68.6%，窗口放大后边际收益收敛。
  5. Terminal 32k Mistral：T0 21.35%，T3/T4 42.70%。
  6. Terminal128k 550B：T4 44.94%，bash-only 50.56，强 shell 模型受益。
  7. 同设置30B：T4 13.48%，bash-only 3.37%，方向反转。
  8. 30B no-plan 时68.6% run 从未 edit；开 plan 后27.8%；卡 localization 58.4→10.4。
  9. 32k unmanaged median约20–30 turns，managed约50–180 turns，而 phase ordering 基本不变。
Strongest：context policy 的收益能被 overflow/trajectory 机制解释。Weakest：T4 并非每格最高；recall machinery 很少被用；planning/action 没做全 factorial。

5.14 Ablation / Mechanistic Analysis

去 context management 后小窗 run 多在 Localize 阶段死；加入后 trajectory 变长但 phase shape 相近。去 planning 后弱模型大量不 edit；强模型主要减少 post-edit verification。换 bash-only 后强模型 action 更密、弱模型 shell 错误更多。Action-space intervention 捆绑 schema/state tracking/diagnostics，所以不能把结果归因于“工具数量”单变量。

5.16 Contribution

5.17 Limitation & Failure Modes

作者边界：具体实现不代表普遍定律；planning/action 只测 T4/128k；action interface 捆绑多项变化；每题每 setting 一次；Terminal 仅89题；trajectory 使用 LLM judge。额外风险：API cost≠GPU/latency；SWE 主要 Python；未测恶意 summary、memory poisoning、tool injection、跨 session/handoff、多 agent；压缩可能删掉审计关键证据。

5.18 Reproduction View

最小复现：两个强弱开源模型，SWE Verified 100题，32k/128k，T0/T1/T4 + plan-off + bash-only。优先复现32k overflow/SR 与弱模型 no-edit rate。实现 history budget、middle selector、stub/store、summary runner、plan injector、action schema、trajectory logger。注意 summary 也计 cost、usable context 要扣 system/tool schema、bash-only 不得偷留 structured diagnostics。

5. Paper 2 Full Deep Dive

Paper 2 — SoL-Pi: Recursively Scaling Auto-Research Loops for Efficient Agent Harness

5.1 基本信息

Authors：Haozhe Liu, Tian Ye, Sensen Gao, Qihang Cao, Yitong Li, Mingchen Zhuge, Duomin Wang, Ruihua Zhang, Ping Luo, Jiawang Bian, Lei Zhu, Ligeng Zhu, Enze Xie, Song Han。Affiliation：NVIDIA、NTU、MIT。Date：2026-09-17。Status：arXiv:2609.20519v1。Paper：arXiv / HTML / PDF。Project：NVLabs。Code：official GitHub，MIT license，Pi standalone extension。

5.2 一句话定位

让 agent 自动研究和改造自己的 harness，在约150方向、约500可执行环境里筛出四个跨任务/跨 backend 的 token-efficiency 机制。

5.3 人话版

长程 agent 很多成本不是“思考”，而是重复传上下文、重复大 tool output、edit 后再单开一轮测试、让昂贵主模型读超长日志。SoL-Pi 不训练模型，而让 research agents 看 trajectory、提改法、实现、review、实验，再通过预先冻结的 capability/efficiency gate。152 个方向最后留下 Action Fusion、Online Context Compact、ObservationPack、Evidence-Preserving Reducer。EdgeBench 上 GPT-5.6 Sol 的完整 efficiency stack 相比 Pi token 2.1538B→1.0990B（-49.0%）、成本1339→894美元（-33.2%），score 44.833→42.003；在未参与搜索的 Opus5 上仍 token -44.7%、cost -33.5%、score 保留94.3%。但 Terminal-Bench4 只解15/63，Pi解18/63，因此效率提升不是无损神话。

5.4 Background & Research Gap

已有效率工作多降每token成本；agent浪费却发生在task level。已有 automated harness search 又容易 search/eval leakage：在开发任务上持续 patch，最后“自我改进”只是过拟合。SoL-Pi 要解决的是：如何用 isolated lineages、frozen gates、one-way held-out validation 自动发现可复用 harness mechanism。

5.5 Core Insight

Insight有三层：一，token waste 有结构性 harness 来源；二，RSI 的现实入口可能是 agent 自动改 harness，而不是模型直接改权重；三，held-out 结果必须单向使用，否则 auto-research 会把验证失败继续修成通过。最后一条是本论文最可迁移的方法学贡献。所谓 recursive efficient improvement 仍是未来愿景，并未做多代复利实证。

5.6 Method Deep Dive

Pi + development trajectories → Oracle Analysis → 152 directions / 6 families → isolated disposable lineages → propose → implement → independent review → fixed experiment → frozen capability gate → efficiency gate → nondominated retention → integrate four survivors → freeze source/config/metrics/tolerances → one-way EdgeBench held-out → Opus5 / Terminal / IMO / swarm

四机制：Action Fusion 合并 mutation+follow-up command；Online Context Compact 在 plan-step completion 估算未来 input saving 与 cache rewrite cost；ObservationPack 对>10KiB output 前两次完整发，第三次起用 handle+1KB excerpt，可 exact page recall；Evidence-Preserving Reducer 用低价模型压 build/test log，再以 schema/source hash/exit status/exact quote 做 deterministic verification，失败返回原日志。

5.7 核心公式与数学直觉

Accept(candidate) iff: every capability metric stays within frozen tolerance AND at least one declared efficiency metric improves retain nondominated candidates Token Efficiency = API Cost / Aggregate Task Score Compact iff projected repeated-input savings > estimated cache rewrite cost + margin (or window pressure forces compaction)

这不是无约束最小 token，而是 capability-constrained optimization。最敏感的是 capability tolerance：太松会把“少做事”误当效率，太严则把统计波动当退化。Strongest baseline 是 Pi，因为 SoL-Pi 就是 Pi extension。

5.8 Toy Example

agent edit session_store.ts 后通常下一轮才跑 test；Action Fusion 合成一次调用。测试吐30KB log，Reducer 抽出3个 failing tests 与 exact stack lines，verifier逐条核 quote/hash；失败就返回原文。ObservationPack 前两轮仍发全量，第3轮后只发 handle/头尾 excerpt；未来需要中间行再 exact recall。完成一个 plan step 后，Context Compact 估算剩余请求，只有未来节省超过 cache rewrite 才压缩。

5.17 Limitation & Failure Modes

作者承认搜索成本高、breadth/depth scaling law 未建立、多 backend training 与 recursive improvement 属未来。额外：主要从GPT-5.6搜，可能 backend-shaped；EdgeBench公开集仅51；Performance point按backend选最佳单机制；Terminal明显掉点；Reducer远程处理日志有隐私风险；Pack本地archive生命周期需治理；未测 adversarial log/prompt injection；未证明自动搜索优于同预算人类专家。

5.18 Reproduction View

5.21 Attack / Verification Lens

Reducer attack：把关键error藏在长日志低频位置或插入prompt-like文本；Pack attack：让关键信息第三轮后才变重要；Compaction attack：plan-step boundary前埋未来依赖。可定义 Evidence Preservation P/R、Fallback Correctness、Compression-Induced Task Delta、Held-out Harness Generalization Gap。迁到unlearning可把auto-search变成black-box recovery probe generator。

5.22 与另外 Top Paper 的关系

SoL-Pi 对 Paper1 的 conditionality 给出部分反驳：完整 stack 确实能 GPT→Opus transfer；但最佳 Performance mechanism 从 ObservationPack 换成 Action Fusion，又印证“不存在 universally optimal harness”。最自然组合是自动搜索 + factorial audit + backend-aware controller。

7. Cross-Paper Synthesis

共同趋势：agent研究正在从“模型会不会”转向“harness能否正确释放能力”。组合范式是 Search → Freeze → Factorial Audit → Model/Budget-aware Deployment。先自动广搜机制，再冻结候选；随后跨模型、预算、任务做控制实验；最终部署的不是固定harness，而是轻量controller选择plan/tools/compaction/pack/fusion/reducer。Paper1最适合作evaluation baseline；Paper2最适合作system/auto-research baseline。

9. Collision / Overlap

Strongest Collision：Transferable Mechanism vs Conditional Harness Effect。SoL-Pi完整stack能GPT→Opus迁移，说明不是纯backend overfit；但最佳Performance mechanism从ObservationPack换成Action Fusion，而Paper1的planning/tools/context也发生能力与预算crossover。因此更准确的结论是：存在可迁移mechanism family，但最优组合与触发策略必须model/budget-aware。
