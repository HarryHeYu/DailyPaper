NgramRL: Accelerating RL Post-Training for Structured Generation via Rollout-Aware N-gram Speculative Decoding

作者：Nilesh Prasad Pandey、Jangseon Park、Jason Kong、Onat Gungor、Tajana Rosing。机构：UC San Diego、West Virginia University。时间：arXiv v1 2026-10-23；Venue：未核实正式录用；状态：预印本。Paper：摘要 / 全文 HTML / PDF；Project/Code：未核验到作者官方仓库，不编造链接。

一句话定位

NgramRL 把 RL 后训练中“同一个 prompt 的旧 rollout”当作随策略同步更新的无模型 speculative drafter，并用预测验证结果的 CPU–GPU 预取把接受长度优势转换成实际执行时间收益。

人话版（约 300 字）

假设你在用 GRPO 训练一个会写 SQL 的模型。为了得到奖励和 advantage，同一道题每个 epoch 可能让模型生成多个答案；这些 SQL 往往只在少数列名、别名或条件上变化。普通自回归推理依然每次一个 token 地算，即使昨天已经生成过几乎相同的答案。NgramRL 不训练另一个小模型，而是在 CPU 内存为每道题保存最近几轮输出的 n-gram 续写；再次遇到相同题目时，先草拟一串 token，再由正在训练的目标策略一次验证。它用标准 speculative sampling 校正，因此理论上不改变目标采样分布。真正难点在于 CPU 查缓存会让 GPU 等待：作者进一步在 GPU 验证当前草稿时，提前准备不同“接受长度＋下一个 token”分支。实验里，Spider 上 Qwen3-8B 的稳定期每次目标 forward 可提交 7.77 token；预取相对同步版的测得 rollout throughput 为 1.38 倍。注意：7.77 token/forward 绝不等于 7.77 倍实际吞吐；训练总耗时的加速也没有直接证明。

1. Background & Research Gap

GRPO 后训练的计算图可拆成 rollout、reward、policy update。训练前先针对 prompt p 采样 G 条 trajectory，奖励函数给每条一个标量，再在组内归一化形成 advantage，最后对策略参数做更新。对于需要长思维链的任务，rollout 逐 token 采样使 GPU 反复进入 decode 阶段；作者引述既有研究称它可能超过训练 step 时间的 70%，但这个百分比不是其全部工作负载的统一实测。

旧范式一是额外 draft model（如 EAGLE / Medusa 一类），以更便宜的模型提出候选，目标模型并行核验；在推理服务里合理，但训练 GPU 同时放参数、梯度、优化器、KV cache，额外常驻模型很贵。旧范式二是 prompt lookup，从当前 prompt 或本次上下文里复制 token；自由生成的 reasoning trace 与问题本身不一定共享长串。旧范式三是固定 datastore / global suffix tree，能重用其他请求的字符串，但并未按“相同训练题目随 epoch 反复出现”这个时间结构建索引。

具体例子：题目要求统计某公司行业，epoch 1 输出 SELECT COUNT(*) FROM Companies WHERE Industry IN (...)，epoch 2 可能改成 OR 条件，epoch 10 可能和上一轮完全相同。用全局 SQL 模板库会找到很多无关表名，用 prompt 原文查找又找不到 SQL；同一题的最近 rollout 才是信息密度最高的候选源。研究 gap 不是“还没人做 n-gram”，而是“非平稳 RL 策略中如何获得持续对齐的草稿，并避免 CPU cache 变成新的同步瓶颈”。

2. Core Insight：时间局部性不是静态语料重复

Figure 2 给出三个相邻 epoch 的 Spider 示例：早期两条 SQL 重合约 50%，中期约 81%，后期可达 100%。作者还报告同 prompt 的跨 epoch 轨迹可共享 48%–96% 内容，重复片段长 7–23 token。它是经验观察，不是任何 GRPO 算法都保证的数学定理：若 prompt 从不重复、采样温度很高、策略每步剧烈变化，这个规律会弱化。

第二个观察是系统层面的：把缓存放在 host 虽然不抢 GPU 显存，但同步验证结果、CPU 查找、重新调度 kernel 的链条会造成约 29% 的 decode iteration GPU idle；lookup 本身并非主要耗时。因此只提高 n-gram 命中率不够，必须把验证后才知道的下一个上下文提前分叉准备。论文的机制创新可以分为“同 prompt 历史条件化”与“结果条件化的异步预取”，前者是算法/数据结构选择，后者是 CPU–GPU 调度创新。

3. Method Deep Dive

Input: prompt p, current policy πθ, recent rollouts Rp → per-prompt cache Cp → draft k tokens → exact target verification → outcome (j,b) → async prefetched next draft / fallback → committed rollout → update cache

Step 1 · 以 prompt 身份组织历史，而不是把所有输出混在一起

每个训练题目 p 持有自己的 C_p。对历史输出遍历 n_min 至 n_max 的连续 token 片段，把前 n−1 个 token 作为 context key、后一个 token 作为 continuation，记录频次与最近 step。与纯字符串匹配相比，频次能在多个可能续写之间给出经验 q(x|c)，最近时间用于淘汰过期记录。作者描述了按 step 窗口 W 淘汰，同时实验表格用最近出现次数 w 进行窗口消融；复现时要明确这两种计数单位不能混淆。

Step 2 · 草拟一串 token，真正提交仍由 πθ 决定

解码到上下文 c 时优先查最长匹配 n-gram，沿缓存建议继续扩展最多 k 个 token；缺失则回退标准 decode。目标模型一次 forward 评估草稿各位置的目标分布 p=πθ，按 speculative sampling 逐个接受或拒绝，并从残差分布补采样。关键不是“过去答案一定正确”，而是“过去答案只是 proposal”；目标策略始终拥有最终决定权。这使训练的采样分布理论上不因缓存变化而改变。

Step 3 · 预测尚未发生的验证分支

当前 k 个草稿中，目标模型可能接受 j 个，并在下一位置输出 bonus token b；j 的取值 0…k，而 b 来自词表，下一轮 cache key 依赖两者。若等 GPU 结束才知道 (j,b)，CPU 的查找与 launch 会串行暴露。预取器因此在 GPU 忙时，根据近期的 j 直方图与候选 bonus 频次，选择少量最可能的 (j,b)，提前准备下一轮 draft，并把查找表送到 GPU。命中时直接 O(1) 取出；未覆盖时只对该请求退回同步查找，不改动已经提交的 token。

Step 4 · 有限预算 N 的分配与状态更新

对每个 j 分配 f_j 个 bonus 候选，预算 N=Σf_j。贪心每次把名额给“新增一个候选带来的预期 coverage 最大”的分支；这是一个离散资源分配问题，不是学一个额外 RL policy。当前 step 的采样轨迹完成后写回缓存，旧项按窗口淘汰。训练仍由 verl 的 GRPO 执行，作者强调 reward model、optimizer 和 policy architecture 不必改动。实现层要特别注意不同 rollout worker 的 prompt ID 稳定性与异步更新顺序。

4. 公式与数学直觉

paccept(x|c) = min(1, πθ(x|c) / q(x|c))

q 是缓存提议分布，πθ 是当前策略。若草稿 x 在 q 中比目标策略更常见，则接受率低于 1；拒绝后从 [πθ−q] 的正部归一化分布重新采样。单 token 层面，这个校正保证最后输出遵循 πθ 而非 q。若只用“匹配就直接复制”，训练分布会偏向旧答案，可能导致策略过度自我模仿甚至 reward hacking；严格校正避免这种采样偏差，但不自动证明不同并行随机数实现会得到逐 bit 相同的训练轨迹。

max Σj P̂(j)·ĉj(fj)，s.t. Σj fj=N

P̂(j) 表示近期接受 j 个 token 的概率，ĉ_j(f_j) 表示在这个分支只预取前 f_j 个 bonus 候选时的覆盖率。目标是最大化“真正发生的分支已经被预取”的概率。增大 N 通常提高 coverage，却增加 CPU 工作；在 GPU forward 时间无法覆盖 CPU 预取时，反而失去重叠优势。作者发现全接受分支的 bonus 往往高度可预测，给一个候选就可能足够。

Speedup(c) = (Tgpu + Tcpu) / (Tgpu + (1−c)·Tcpu)

这是作者的重叠模型：c 为预取命中率，T_gpu 是设备忙时，T_cpu 是同步链暴露的主机时间。c=0 无收益，c=1 的上限为 1+T_cpu/T_gpu。模型隐含预取能被 GPU 计算完全掩盖，且未覆盖分支的回退不引入额外拥塞。真实部署必须同时测 GPU utilization、CPU 调度、PCIe 传输和批处理尾延迟，不能拿公式直接当测量。

5. Toy Example：从 SQL 轨迹到精确采样

设同一 prompt 的最近两个答案都含 SELECT COUNT(*) FROM orders WHERE status =。缓存对上下文 WHERE status 给出下一个 token 的经验概率 q(“=”) = 0.8、q(“IN”) = 0.2，而目标策略当前概率 p(“=”) = 0.6、p(“IN”) = 0.4。草稿提出“=”时接受概率 0.6/0.8=0.75；提出“IN”时接受概率 min(1,0.4/0.2)=1。于是直接接受“=”的概率 0.8×0.75=0.6，“IN”的直接接受概率 0.2；剩余拒绝质量 0.2 全部转到“IN”，最终得到 (0.6,0.4)，恰好是目标分布。

进一步设草稿长度 k=3，当前轮可能接受 j=3 后输出 bonus “;”，也可能接受 j=1 后输出 “AND”。预取器根据近期统计给这两个分支分配候选；若实际 (3,“;”) 命中，下一轮 SQL 续写已经备好。若出现从未见过的 “OR”，则正常 CPU lookup，已提交的 “OR” 不被篡改。这个 toy 说明正确性来自校正与回退，而不是缓存预测总正确。

10. Ablation / Mechanistic Analysis

去掉 per-prompt key 改 global bucket：plateau 3.05→2.41，说明主要信息不是 n-gram 数据结构本身，而是 prompt 条件化。把 SuffixDecoding 从 10k 增到 40k responses 只升至 2.65，进一步削弱“纯容量不足”解释。减小历史窗口 w：显著省内存但降低部分 TPS；无限窗口不一定更好，验证新旧策略漂移是机制变量。去掉异步 prefetch 回到同步：相同草稿接受能力下，暴露 host chain，Spider 1.38× 的额外 wall-clock 收益消失。

这些属于受控系统消融，能够支持组件贡献；但尚未证明“历史重复来自 reward 学到的能力而非模板坍缩”，因为该因果问题需要联合 reward、正确率、轨迹熵和 prompt 多样性做干预。

11. Claim vs Evidence

Authors Claim：同 prompt 旧 rollout 是自更新 drafter；标准校正保留 target 分布；CPU–GPU 预取能接近 host-overlap 上限。Experiments Actually Show：两个 7–8B 模型、三类任务上的 TPS 增益；一个特定 profiling rig 上 Spider 的实测 1.38×；per-prompt 与窗口消融有支持。What Is Not Yet Proven：跨 32B/70B、极大 batch、分布不断变化的 online RL、无重复 prompt 的任务、全训练总 GPU-hours 与能耗的收益。exact sampling 是算法层面的性质，实际实现还需检查随机数、数值精度和并行调度。

PAPER 2AGENT / HARNESSBACKFILL

HarnessMM: Recursive Self-Improvement for Harness Token Efficiency

作者：Yuhua Jiang、Chang Xu、Feifei Gao、Li Zhao。机构：Tsinghua University / Microsoft Research Asia（论文署名）。时间：arXiv v1 2026-10-23；Venue：未核实正式发表；状态：预印本。Paper：摘要 / HTML 全文 / PDF。Project/Code：未核验到作者公开的独立实现仓库；论文引用的 Codex、DeepSeek Harness 不等于 HarnessMM 官方代码。

一句话定位

HarnessMM 把 Agent 已经推理完成的后续工具动作编译成带因果依赖与公共状态守卫的可执行图，在工具反馈后满足条件时直接执行，从而减少不必要的再次调用大模型，并对每次省掉的回调提供可审计证据。

人话版（约 300 字）

一个 Coding Agent 已经决定“写文件→编译→测试”。传统 ReAct 风格 harness 往往写完文件后又问模型“接下来做什么”，编译成功后再问“接下来做什么”，即使这些步骤在第一次规划时就已经确定。HarnessMM 的做法不是压缩每次 prompt，而是让第一次慢推理同时产出一张 Executable Decision Graph（EDG）：每个节点包含完整工具参数、前驱节点和只依赖可观察回执的守卫。执行时，Guarded Decision Reuse（GDR）检查“前一步真的成功了吗”“参数是否早已确定”；满足才允许复用。Certified Callback Substitution（CCS）通过原工具接口执行，并记录它实际绕过了哪次慢模型回调。遇到新语义判断、模糊条件或异常则回到原模型。论文在 HumanEval 上报告 Codex 成功率保持 90.82%，每任务 token 从 66.72k 降到 47.02k；DeepSeek Harness 从 96.28k 降到 11.62k，成功率还提高。重要的是，这些大幅下降属于整套 harness 的集成结果，不能全部归因于 EDG；作者另用 MBPP 消融隔离 GDR 与 CCS。

1. Background & Research Gap

Agent 的常见循环是“LLM 思考→发起工具调用→读取工具反馈→再问 LLM”。这个循环适合开放环境：工具返回错误时，确实需要重新推理。但很多工具反馈只告诉你一个预期事件是否完成。例如模型已经生成完整 patch，并决定在 patch 成功后运行 pytest tests/test_parser.py；文件写入成功的回执只是触发条件，不应强迫模型重新生成 pytest 命令。重复推理消耗输入历史、输出思考 token，还可能引入新的不一致决策。

已有三类办法：LLMLingua / history compression 缩短每次模型输入；fast–slow routing 把部分决策交给便宜模型；Voyager-style skills 或 ReWOO / LLMCompiler 保存可执行程序与依赖。它们都合理，但缩短调用不等于取消调用；跨任务 skill 也不等于本次 episode 已完全确定的字面动作。HarnessMM 填补的是“某个工具反馈是否只改变执行就绪状态，而没有改变决策语义”的边界。

具体例子：Agent 已写好 cmake --build build 和 ctest --test-dir build 两个动作。编译成功后直接执行测试是安全的候选；但如果编译报错，需要根据错误内容改代码，原先的测试动作即使参数完整也不再语义适用。只检查参数是字符串远远不够，还必须有前驱成功与失败时回退。

2. Core Insight：把“决定是什么”与“何时执行”拆开

作者提出“Substitution Paradox”：想省掉模型调用，通常又需要模型判断是否能省，容易把节省的 token 重新花掉。它将决策分成两层：慢模型负责先把未来动作的语义和字面参数确定下来；执行时只读取公共工具回执，使用简单守卫和候选 ID 选择器决定是否可以执行。图中的节点不是一般自然语言建议，而是具备原生 tool name、exact args、predecessor、guard 的 commitment。

这属于执行架构上的机制设计，不是从训练数据推导出的理论最优策略。关键的“语义闭包”是作者主动承认的假设：参数已经写死，不代表动作在未来状态一定正确；守卫检查通过只证明它定义的公共条件成立。论文附录 D.2 明确区分 literal closure 与 semantic closure，这一点比 headline 的大幅 token saving 更值得认真读。

另一条洞察是审计：过去许多 Agent 加速论文只报告总 token 减少，但难回答“究竟哪次推理真的没发生”。CCS 把 graph hash、节点 ID、前驱回执、原始参数、工具回执和被绕过的 callback ID 绑定为证书。它证明的是执行路线发生了替换，不是证明被省掉的那次模型调用本来一定会输出同样动作。

3. Method Deep Dive：逐节点解释

Input: task + public state → slow actor authors EDG → validate literal args/dependencies → tool receipt → GDR eligibility → selector ID / abstain → CCS native dispatch or slow fallback → receipt ledger → next boundary / terminal score

Step 1 · 原 harness 的慢推理先决定当前动作和可预见后续动作

固定 actor 权重 θ、原工具接口和 benchmark scorer。慢模型在某个 decision boundary 输出当前 tool action，同时可附带一个有界有向无环图 G_i=(V_i,E_i)。每个 future decision d_j=(a_j,arg_j,pred_j,g_j)：a 是原生工具类型，arg 是完全确定的字面参数，pred 是必须先完成的前驱，g 是从公共状态到布尔值的守卫。图必须无环；缺参数、非法依赖、未支持工具都不能进入可执行队列。

Step 2 · 接收真实工具回执，更新运行时状态而不是改写已决定的动作

执行完节点后，将工具的 exit code、stdout/stderr 摘要、文件状态或 UI 截图等纳入 public state。图的内容本身不变；只更新哪个前驱完成、哪些 guard 为 true、哪些节点仍未执行。这样可以追踪信息流：一条工具回执只应该改变执行许可，不应该悄悄生成新的命令行参数。若命令需要引用未来才知道的文件路径，就不符合 literal closure，应交还慢模型。

Step 3 · GDR 选择已决策动作，必要时 abstain

对于每个未执行节点，必须同时满足：前驱完成、守卫通过、参数闭合。若唯一 eligible 节点可直接选择；多个节点时使用类型受限 selector，仅输出候选 ID 或 abstain，不能改写参数。无候选、观测不足或 abstain 时回到原 actor。作者在论文中强调 selector 的 token 也要计费；若每次选择都要花长推理，所谓加速便会失效。

Step 4 · CCS 真正替换回调，并生成证据链

如果选择节点 d_j，就直接通过原生 tool dispatcher 执行先前保存的字面参数；不调用本应出现的 slow reasoning callback。之后把 graph_hash、decision_id、predecessor_receipt、exact_args、tool_receipt、bypassed_callback_id 记录为证书，并对照物理请求账本核验原回调确实没有发生。这个“证书”不是密码学上对工具环境真实性的普适证明，前提是日志、适配器与回执可信。

Step 5 · RSI 是离线配置优化，不是任务内随意自改权重

HarnessMM 还让外层训练反馈提出 harness 指令、上下文设置、适配器规则等候选修改，使用不重叠的 validation 选择，测试前冻结。MiniWoB++ 展示了八轮 training-guided RSI；它不是“模型权重在线更新”，也不能把同一训练集上逐轮上升直接当成 held-out generalization。论文把 EDG/GDR/CCS 核心执行机制与 instruction-only 等 companion configuration 分开做证据归因，这个分离对复现至关重要。

4. 关键公式与数学直觉

minπ C(π)，subject to Rb(π) = Qb(h0) − Qb(hπ) ≤ εb

C(π) 是在执行策略 π 下，完整任务实际支付的模型 token 期望；Q_b 是 benchmark b 的官方质量分数；R_b 是相对原 harness 的能力损失。目标不是盲目最少 token，而是在可接受成功率下降 ε_b 以内节省调用。若 ε=0，理想情况下不允许平均质量退步；若允许小幅回退，必须报告 Pareto front，而不能只挑最省 token 的点。

eligible(d,s) = 1[pred completed] · 1[g(s)=true] · 1[args closed]

三个指示函数相乘表示任何一项失败都不得直接执行。pred 保证因果顺序，g(s) 将真实回执映射为执行许可，args closed 保证没有需要 LLM 填的未知参数。它不保证动作一定有利于任务：比如 pytest 虽然在 build success 后可执行，但任务要求先更新依赖版本时仍可能不合适。作者附录把这个差距表述为“eligible⇒valid”额外依赖守卫质量的假设。

κ = (graph_hash, decision_id, predecessor_receipt, exact_args, tool_receipt, bypassed_callback_id)

κ 是结构性归因证据。它允许你重放：哪张图提出哪个动作、为什么此时有资格执行、实际调用了什么、原先哪个 callback 被跳过。它不包含反事实模型输出，因此不能单凭证书给每次 bypass 分配“省了 800 token”这种不存在的精确值；论文使用同任务集的完整账单比较总成本。

Cepisode = Σphysical calls c(input_tokensc+output_tokensc)； C̄N = Cdev/N + E[Cepisode]

第一式避免“只统计成功调用”或“忽略 graph authoring”导致虚高收益。第二式说明部署规模 N 越大，离线规则开发成本越容易摊销；短期小规模任务可能因开发成本不划算。这里的成本单位是 token，不是 wall-clock、美元或能源；不同 provider 的 cache accounting 与 token 定价可能改变经济结论。

5. Toy Example：从一次构建到两次真实工具执行

假设 Coding Agent 收到“修复 parser 并运行测试”，第一次慢调用确定动作 A：写入 src/parser.py，后续动作 B：python -m compileall src/parser.py，动作 C：pytest -q tests/test_parser.py。图中 B 的 pred=A，guard 为“文件写入回执成功”；C 的 pred=B，guard 为“编译 exit_code==0”；B/C 参数在 author 时都已确定，不需要用未来日志拼接字符串。

A 执行成功后，GDR 检查 B 三项全真，CCS 调用原生 terminal 执行 B 并生成 κ_B。若编译成功，C 再次满足 guard，CCS 直接执行 C 并生成 κ_C；这两个边界都省掉了“下一步干嘛”的慢回调。若 B 失败，C 的 guard=false，系统回到慢模型分析报错，重新写 patch 和新的图。若作者只给了 pytest tests/{unknown}，参数未闭合，绝不能猜一个文件名后执行。

这个例子也展示安全问题：如果工具回执被恶意修改为 exit_code=0，系统会执行错误的后续动作；如果前一步成功但环境发生外部变更，guard 也可能过时。因此要加 receipt provenance、状态版本、工具副作用白名单和失效检查。上述代码路径是说明用的 toy，不是论文实际实验命令。

10. Ablation / Mechanistic Analysis

W/o GDR：图只允许一次未来执行，成本 18.03k；Full 保留图，13.17k，差 4.86k（26.91%）。这更直接支持“同一张图跨工具反馈重复使用”的价值。W/o CCS：保留慢回调，16.37k；Full 13.17k，差 3.20k（19.52%），说明真正省掉模型请求是收益的一部分。W/o EDG execution：作者仍生成图但不执行，16.19k，成功率 95.33%；Full 13.17k，成功率 93.77%，揭示 EDG 在某些状态下做了不理想的语义替代。

附录给出 407 次 certified substitutions，其中 201 张图发生第二次及以后 bypass。这个计数证明机制在运行时确实发生；它并不说明每一次 bypass 都因果性提高质量。想要真正机制归因，还应对同一个 episode 做 counterfactual replay：保持工具环境快照，分别用 GDR 与慢回调决策，比较动作一致率、错误回退率和后续任务成功率。

11. Claim vs Evidence

Authors Claim：重复 reasoning 可由已决定的动作替代；guarded graph 能跨反馈复用；证书能审计替换；RSI 可改进 harness。Experiments Actually Show：98 HumanEval 与 257 MBPP 的原生集成对照、MBPP 四条件消融、多个 benchmark 的配套配置研究、MiniWoB++ 同训练任务的 RSI 迭代。What Is Not Yet Proven：通用 semantic closure 的安全性、跨真实长期生产 Agent 的稳定性、工具被污染时的鲁棒性、跨模型与硬件的 wall-clock 优势、与 ActionEngine / LLMCompiler / ReWOO 的全面实证优越性，以及 RSI 在新任务分布上自动持续改善。

12. Contribution、Limitation 与 Failure Modes

  • Contribution 1 · New Mechanism / System：episode-specific Executable Decision Graph，记录 exact action、dependency、guard；与已有程序规划相邻但边界更严格。
  • Contribution 2 · New System / Engineering：GDR 的可观察状态守卫与持续复用；没有发明 DAG，却改变了工具反馈后的执行控制。
  • Contribution 3 · New Metric / Protocol：CCS 的 callback omission 证书与完整物理 token 账本；可审计性强于只报 token saving。
  • Contribution 4 · New Empirical Finding：在 Codex、DeepSeek Harness 的特定任务和 backbone 上存在显著节省空间；同样存在 quality regression。
  • Contribution 5 · Existing Components Combination：外层 RSI 的 prompt / configuration 迭代来自已有优化思想，不能简单等同于全新自改算法。

Authors’ Limitation：没有可复用的已决策动作时收益小；authoring、selector、fallback 可能抵消省下的调用；public-state adapter 依赖任务；小开发集令策略级质量差异不确定。Additional Limitation：公共回执可能被 prompt injection、恶意工具输出或不完整日志污染；副作用工具不能像只读查询那样安全重放；跨进程并发、状态过期、文件内容被外部修改都可能破坏 guard 语义。模型在首次 author 时写错命令，会把错误变成可执行承诺并传播到后续节点；这是 memory/skill 污染的执行版本。

尤其不能把“exact args”误解为“正确 args”。字面闭包是程序验证问题，语义闭包是开放世界推理问题。证书只说明在特定边界确实执行了某个工具并跳过模型，不能证明环境状态没变、动作没有越权或结果对最终目标有利。

13. Reproduction View：从最小 Hook 到完整审计

优先在开源 coding harness 的 tool-call boundary 加一个旁路 controller，不修改模型权重。定义 EDGNode(id, tool, args_json, predecessor_ids, guard_spec, graph_hash)；限制工具为 write_file、shell、read_file 等已有 native actions；禁止未声明占位符与任意 Python guard 执行。guard_spec 采用白名单谓词，如 exit_code_eq(0)、file_exists(path)、stdout_contains(text)。先只允许无副作用或可回滚工具，再扩大范围。

实验 1：MBPP-sanitized 257 个 test task，按论文 85/85/257 split 固定训练与验证，测试时四臂共享 backbone 和温度：original、single-use EDG、persistent EDG with retained callback、Full。记录 success、每个 physical model call 的 input/output、graph authoring、bypass 数、guard reject、fallback、每次工具退出码。实验 2：为每个 bypass 写 JSONL 证书，并用独立 audit 脚本核对 graph hash、exact args、predecessor receipt、真实 tool receipt、缺失的 callback request ID。先验证 Full 与 W/o GDR 的 token 差异方向，再检查 Full 是否像论文一样存在少数质量回退。

最容易踩坑：把 EDG 的 token 成本排除在外；对失败任务不计费；把模型自己生成的“成功”当工具回执；guard 允许执行任意 shell；在有多个 eligible 节点时 selector 自行修改 args；把工具执行的系统时间误算成 token saving；在同一测试任务上调规则造成泄漏。作者官方实现尚未核验，因此上述是基于方法描述的最小可行复现，而非运行过的代码。

14. Agent 专用分析：State、Long-Horizon 与 Failure Propagation

Architecture：Input → Slow Planner / EDG Author → Native Tool → Public Receipt → GDR Eligibility → Typed Selector → CCS Dispatch / Slow Fallback → New Receipt → Task Scorer。Agent State：EDG 是本 episode 的程序性记忆；工具回执是 episodic evidence；selector 与 guard 是轻量控制状态；并不等于跨用户的长期语义记忆库。

Long-Horizon：理论上图可跨多个工具边界复用，但论文最直接的编码机制实验是有限长度任务。任务越长，环境漂移、并发修改、隐藏依赖与 guard 误判概率越可能累积。应跟踪 action depth、graph age、stale receipt rate、回退次数与成功率，不能仅凭 407 次 bypass 推断千步 Agent 的可靠性。

Failure Propagation：首次慢模型错误 author → 错误 EDG 作为程序性记忆被保留 → guard 接收过时或恶意 receipt → 触发错误 tool → 后续节点继续执行 → 最终任务失败。与普通 Agent 不同，错误可能绕过本可纠正的中间 reasoning。安全设计应加入状态版本号、只读验证、不可逆动作强制慢审批和按任务风险调整 guard 强度。

15. Attack / Verification Lens

最值得设计的是 Guard-Validity Benchmark：在固定任务中对工具回执注入可控错误（退出码错误、stdout 缺行、文件版本被替换、超时后重试、并发修改），比较普通 ReAct、无 guard 宏、HarnessMM 风格 guarded reuse 的成功率、危险动作执行率、fallback precision 和 token cost。还可以做 black-box probe：仅观察工具日志与模型调用日志，推断是否存在“预先承诺的动作”被错误触发。

建议定义 unsafe_bypass_rate = 语义不应执行却发生 bypass 的边界数 / 所有 bypass 边界；guard_recall = 安全可复用边界中成功复用的比例；recovery_cost = 误触发后恢复到正确状态的额外 tokens + tool time。这些是本报告提出的候选指标，不是论文官方指标。

16. Research Value 与两条迁移

Baseline Potential：原始 DSH / Codex、single-use EDG、W/o CCS 构成清晰对照。Migration Potential：可以进入多 Agent workflow、研究 Agent、IDE 自动化。Systems Potential：原生接口与物理账本使上线可观察。Attack Potential：guard 误判和工具回执污染是新攻击面。Evaluation Potential：callback-level causal audit 可复制到其它 harness。Benchmark Potential：可构造任务深度×状态漂移×回执真实性矩阵。New Paper Potential：“可验证决策复用”与“可恢复性”联合建模，而非仅仅提高 bypass rate。

Migration A · Multi-Agent Shared Decision Provenance

Original Problem：单 Agent 已确定动作在工具反馈后被重复推理。Transferable Mechanism：EDG + receipt-bound certificate。New Research Question：多个 Agent 交接时，能否只共享带 provenance 的可执行承诺，避免接手 Agent 再次推理，同时不扩大错误传播？Method Modification：在 EDG 增加 author_agent_id、owner lease、tool permission、state_version、handoff_hash；只有接手 Agent 持有 lease 且公共状态版本一致才可执行。Minimum Experiment：构造 100 个代码修复任务，每个由 planner→editor→tester 三 Agent 执行；对比自然语言 handoff、共享摘要、共享 EDG、共享 EDG+lease+guard；每个任务运行 3 seed，记录 token、成功率、重复工具调用、非法并发动作与恢复时间。Model：Qwen3-8B 或统一 API backbone。Dataset：MBPP-sanitized 子集与自制多 Agent handoff case。Baseline：ReAct、LLMCompiler-style static plan、single-agent EDG。Metric：pass@1、tokens/task、duplicate-action-rate、unsafe-bypass-rate。Expected Contribution：跨 Agent 可审计执行语义。Risk：分布式时钟、工具副作用、责任边界。Collision Risk：与 workflow DAG / ActionEngine / shared memory 项目相近，创新须落在状态版本和错误传播实验。

Migration B · Risk-Calibrated Agent Reuse / Recovery

Original Problem：固定 guard 只能二值决定是否跳过慢推理。Transferable Mechanism：能力约束的 token 优化 + 结构性回退。New Research Question：能否根据动作风险和恢复成本动态决定何时继续复用、何时重新思考？Method Modification：增加 risk score r(s,d)（工具是否可逆、receipt 新鲜度、参数影响范围），阈值 τ 控制 reuse；高风险动作必须经过 slow confirmation，低风险动作保持 fast path。Minimum Experiment：在 257 个 MBPP 测试任务中生成 4 类回执扰动（正常、错误 exit code、过期文件、部分 stdout），每类随机 20% 工具边界注入；比较 always slow、always reuse、固定 guard、risk-calibrated guard；阈值 τ∈{0.2,0.5,0.8}，记录成功率、tokens、误触发、回退时延与平均恢复成本。Model：Qwen3-8B。Dataset：MBPP + 注入的受控工具环境。Baseline：Full HarnessMM-style guard、single-use EDG。Metric：unsafe-bypass-rate、success、token、time-to-recover。Expected Contribution：可恢复性约束下的动态执行预算。Risk：risk score 自身可能被工具输出欺骗。Collision Risk：与现有 selective prediction / fast–slow routing 相近，需通过真实执行级消融体现差异。

Cross-Paper Synthesis · 共同趋势

这两篇都说明，下一代 AI 效率不一定靠更小的模型或更少的 Transformer 层，也可以靠识别“已经付过成本的计算”。NgramRL 重用旧 rollout 中的 token 候选，但必须由当前策略精确校正；HarnessMM 重用旧 reasoning 中已经确定的动作，但必须由真实工具回执和执行守卫许可。两者都是 history → candidate → verify/guard → commit → feedback，差别在验证对象：前者是概率分布，后者是环境语义。

NgramRL 的分布校正有明确数学性质，但仍受系统时延约束；HarnessMM 的守卫可审计，却没有一般性的语义正确性证明。这形成研究上的关键互补：把 speculative token drafting 用于尚未完全闭合的 Agent 决策，把 EDG 直接执行只用于已闭合且可验证的工具动作。它们可以组成一个分层 Agent 执行器：先判断是否能直接执行已决策动作；不能时再调用模型，而模型内部用历史轨迹做 lossless drafting。

Combined Research Opportunities

Idea 1 · Verified Reuse Controller（优先）

建立统一决策器，输入状态包括 cache age、重复度、guard validity、action reversibility、模型预测熵；输出三种路线：直接执行已闭合动作、speculative 生成并 exact verify、完全 slow reasoning。最小验证：同一批 coding Agent 任务在不同工具回执扰动率下测 quality–tokens–latency 三维 Pareto；固定 backbone 与执行环境，比较单独 NgramRL、单独 EDG、两者串联、风险控制串联。真正的新意必须是“何时可以安全跳过哪一层计算”的形式化协议，而不是简单拼接两份代码。

Idea 2 · Recovery-Aware Cache / Memory Budget

NgramRL 用历史重复度决定 n-gram 价值，HarnessMM 用守卫决定动作是否复用；二者都没有直接把错误恢复成本放进预算。可以估计每次复用的 expected net value = saved compute − expected recovery cost，并用任务完成率约束优化。第一版不需要学习新模型：从日志统计 miss、fallback、tool failure、后续重试次数，按阈值做预算；随后才尝试 contextual bandit 或 offline RL。

Idea 3 · Benchmark：Reusable Yet Unsafe

创建同一任务多轮重复、输出结构可控、工具状态可变的压力测试。两个轴分别是 token-level entropy 与 action-level environment drift；评价 quality-conditioned speedup、unsafe bypass、fallback recall、recovery tokens。它能区分“文本相似但动作错误”和“动作相同但环境不再允许”，更可能形成可复用 benchmark 而非单点启发式论文。

Collision / Overlap

Strongest Collision（潜在研究交叉，而非已确认同题论文）： NgramRL 的“预测分支命中”与 HarnessMM 的“守卫许可执行”都在决定是否跳过昂贵计算。若简单把旧 Agent 轨迹缓存后直接执行，会与已有 executable planning、ActionEngine、LLMCompiler、ReWOO 等方向重叠，而且可能牺牲正确性；若仅把 EDG 转为 token cache，又丢失其语义许可边界。真正值得检验的 gap 是 verified action reuse + exact token drafting + recovery-aware budget 的联合质量约束。

特别声明：这是基于两篇方法的潜在机制 Collision，不是声称已有文献已经证明相互冲突。HarnessMM 自身附录也明确指出尚未对所有可执行 planner 做直接实证比较。
