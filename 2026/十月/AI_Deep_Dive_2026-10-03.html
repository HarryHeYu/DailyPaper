TitleAgSpec: Pushing the Limits of Retrieval-Based Speculative Decoding in Coding Agent Pipelines
Authors / AffiliationSumin Lee, Sukmin Cho, Suengjae Lim, Youngjin Kwon · School of Computing, KAIST
Date / Status2026-10-01, arXiv v1, cs.CL；未从正文确认正式 venue。

12.2 一句话定位

把 speculative decoding 的优化单位从单次 request 提升到整个 coding-agent session / workspace / role：让 agent 的 trajectory 直接决定“从哪里复制 token、一次 speculative 多长”。

12.3 人话版

coding agent 会反复读文件、写 patch、跑测试、根据日志重试，因此大量输出其实来自刚看过或刚生成过的文本。传统 retrieval speculative decoding 却常只索引当前 prompt 或固定 datastore；上一轮 patch、完整 workspace 文件可能根本不可检索，而且 unified-diff 的输出 token 与原文件 token 还不一样。AgSpec 建立 session、workspace、global 三类 corpus，并把 workspace 文件额外变换成 agent 真正会输出的 emission form；随后用离线 role-specific cap 与在线 verification feedback 调整 draft length。它不改 suffix-tree/automaton 检索器本身，而是在检索器上方加 agent-aware policy。三种 24–27B 模型、SWE-bench Verified / TeamBench 上多数 setting 达最高或第二高 generation throughput，最高相对 AR 为 4.76×；无 repository 的 LiveCodeBench 甚至达到 7.94×。

12.4 Background & Gap

Speculative decoding 用便宜 drafter 先猜若干 token，target model 并行验证；被接受的 token 省掉未来串行 decode step。但 draft 错得越多，verification waste 越大，尤其 batch 大时更明显。retrieval-based SD 对代码很合适，因为 identifiers、代码片段、日志高度重复。旧方法的问题有两个：availability——有用文本在上一 call/session/workspace 中，却没被索引；matchability——语义相同文本因输出协议不同而 token 不同。比如文件里是 return x，unified diff 输出时前面多空格或 “-”，原文件 corpus 无法 exact suffix match。本文真正填的是“retrieval policy 不理解 agent lifecycle/scaffold”这个 gap。

12.5 Core Insight

作者先测到：把 per-call corpus 换成跨-call session corpus，accept length 显著上升；再加 workspace 与 emission form 还有增益。与此同时，不同 role/turn 的 achievable accept length 分布明显不同：coder 进入复制 patch 阶段可接受很长 continuation，早期 reasoning 阶段则很短。因此“match 长度”不是足够的 draft-length signal。这个 insight 属于系统测量驱动的经验发现，并由 quantile-loss 视角解释在线 controller。

12.6 Method Deep Dive

Agent call → Session/Workspace/Global corpus → emission-form indexing → provenance-aware suffix match → source selection → offline Kmax → online α → target verification → accepted tokens → feedback 更新 α 与 session corpus → output

Step 1：Session corpus S 保存当前 session 的 prompt 尾部、tool output、generated tokens，跨 calls/agents 保留；Workspace W 保存本 session 打开的 repository artifacts；Global G 是评测前用不相交任务构建的静态 corpus。S/W session 结束即丢弃，G 跨 session 固定。

Step 2：Workspace 文件不仅存 raw text，还存 unified-diff 等 emission form，例如每行加空格/减号，解决“读入格式≠输出格式”的 token mismatch。

Step 3：分别计算 mS、mW、mG。live corpus 选更长 match，平局偏 session；global 必须超过 live 最佳 match 一个 margin δ 才能胜出，避免大 global corpus 的偶然匹配。

Step 4：离线 replay trajectory，为每个 model+role 估计 Kmax；运行时 α 根据 target verification 是否完全接受来升降，跟踪当前 session 的 reuse drift。

12.7 核心公式

K_i = clip(round(α^(a_i) · m_i), 1, K_max^(M,a_i))

m 是 match length，α 是 agent/role 在线 scale，Kmax 是离线上限。它把“文本证据强度”“role 的长期统计”“当前 session 的短期状态”合在一起。

K_max^(M,a) = max { k : P(R ≥ k | M,a) ≥ λ }

R 是 replay 中真实可复用长度；λ 是多验证一个 draft position 的 break-even acceptance probability。λ 越高越保守。batch 大时错误 verification 更贵，因此长 draft 更危险。

α ← α + η(τ − I[A < D])

draft 全接受时 α 增大；出现 rejection 时下降。作者将其解释为 R/m 的 τ-quantile stochastic subgradient tracking，并取 τ=1−λ。η 太大易振荡，太小则跟不上 turn phase。

12.8 Toy Example

coder 第1轮读 parser.py 并输出 patch，但测试失败；第2轮 prompt 因截断已没有完整旧 patch。PLD 只能查当前 prompt；AgSpec 的 S 仍有旧 patch，W 有 parser.py 的 raw 与 diff-form。若 live match m=18、Kmax=22、α=.6，则 draft≈11 token。target 只接受4个后 α 下调；进入大段复制代码阶段连续全接受，α 再上升。于是 reasoning 区短 draft、copy 区长 draft，而不是整次 call 固定 K=32。

Research Questions：agent-aware policy 是否提高真实 decode throughput？收益是否来自 session/workspace/emission form？adaptive draft 是否在高 batch 减少 rejection waste？无 repository/显式 multi-agent 时能否泛化？

15 Metrics

Generation Throughput：单位时间生成 token，越高越好；论文排除 prefill，所以不是端到端 task latency。Accept Length：每次 verification 接纳 draft token 数；高通常好，但不等价于 throughput。Rejected draft tokens：无输出收益却消耗 verification compute，batch 大时尤其关键。正确读法必须把 AL、rejection、throughput 三者一起看。

16 Results Deep Dive

  1. batch=1 相对 AR 2.27–4.37×；batch=16 为1.08–4.76×；平均比每个 setting 的最快 prior method 高18%。
  2. SuffixDecoding + AgSpec：throughput 平均+16.5%、AL +18.5%；SAM + AgSpec：throughput +64.6%、AL 近翻倍。
  3. Strongest：LiveCodeBench 4.87–7.94× AR，比最快 prior speculative method 高35–145%，即使没有 workspace 仍成立。
  4. Terminal-Bench 单 agent：比最快 prior method 高9.3–27.2%，AL 比对应 retrieval-engine baseline 高16.7–34.3%。
  5. per-call→session corpus：AL 1.6–2.1×；workspace 单独+26–47%，叠加 session 后仍+2.2–7.0%。

19 Claim vs Evidence

Claim：retrieval SD 应 follow agent pipeline，AgSpec training-free、engine-orthogonal。
Evidence：3个约24–27B模型、2个 repository benchmark +2个泛化 benchmark，throughput/AL普遍改善，ablation 与机制一致。
未证明：70B/100B+、闭源 API、非代码 agent、超长 context、真实端到端 completion/energy/memory，以及多租户 corpus 隔离成本。

12.1 基本信息

TitleCharacterizing High Bandwidth Flash for LLM Serving
AuthorsZack Yu, Chloe Wong, Coleman Hooper, Minjae Lee, Wonjun Kang, Youngjin Cho, Michael W. Mahoney, Yakun Sophia Shao, Kurt Keutzer, Amir Gholami

Code一手页面未确认官方代码；论文使用 trace-driven simulator，不猜测开源状态。

12.2 一句话定位

研究 agent session 的 KV 状态在“推理→工具等待→再推理”中如何跨 HBM/HBF/host 保留，并证明大容量 flash 只有和 placement + buffered admission scheduling 联合设计才真正变成 throughput/energy 收益。

12.3 人话版

Agent session 上下文越来越长，却会在工具执行时暂时 idle。若 KV 全留 HBM，容量很快爆；若每次 idle 就 evict，下轮又要 reload/re-prefill。High Bandwidth Flash 提供更大、靠近 accelerator 的 memory tier，但写耐久和访问能耗不能忽略。论文构建 HBM–HBF–host trace simulator，提出 index-first placement 与 buffered cache-aware scheduling：除了优先已有 prefix cache 的请求，还故意留 10% admission headroom，防止新请求把“马上会回来”的 session KV 挤掉。最快 HBF 配置相对 HBM-only completion time 降36.1–87.0%，modeled energy saving 最高55.8%；Qwen case 中 buffer 将 HBF lifetime 从4.77年提高到14.82年。

12.4 Background & Gap

普通 KV 管理问“显存不够时淘汰谁”；agent workload 还要问“谁现在睡着但马上回来”。传统 cache-aware scheduler 即使优先 resident prefix，也可能在之后 admission 新请求时把未来 hit 挤掉。HBF 增容量也不是自动答案：若调度导致频繁 demote/reload，flash 写流量和能耗会吞掉收益。本文填的是 memory hierarchy 与 request admission 分离设计的 gap。

12.5 Core Insight

第一，空闲容量有 option value：不把最后10%填满，反而能保护 completed-session prefix，减少未来 recompute/movement/write。第二，sparse attention 的 index 比 KV 更热，应优先驻 HBM；第三，weights 放 HBF 并非总好，某些配置 completion 几乎不变却显著增能耗。属于 systems characterization + architecture/scheduling co-design。

12.6 Method Deep Dive

Agent trace → request/turn arrival simulation → HBM/HBF/host hierarchy → weight/KV/index placement → cache-aware ranking → buffered admission → mixed prefill/decode → movement/write accounting → completion/TPOT/energy/lifetime

Step1：异步跟踪 session arrival、inter-turn gap、cache preparation、forward、movement；支持 mixed prefill/decode 与 2048-token chunked-prefill budget。

Step2：比较 HBM-only、shared-site HBM+HBF 与 H³（保留8 HBM并额外接8 HBF）架构。

Step3：sparse attention index-first：HBM 压力下先 demote KV；reload 时 index 优先回 HBM。

Step4：cache-aware 排序后再施加 admission buffer，限制 active locked state，不让新 session 过度占用 capacity。

Step5：同时统计 HBM/HBF writes、hit fraction、modeled energy 与 endurance lifetime，避免“速度换寿命”。

12.7 核心公式

L + A_i ≤ b C

C 是 weights 后可用 device KV/index capacity，L 当前 locked footprint，A_i 新 request 会锁住的完整 context。b=.9 即保留10% headroom。b 太高易 churn，太低则 queue waiting/under-utilization。

h_HBF(x,k) = s_x − h(x,k)

x 为 runtime context，k 为 HBM-resident KV tokens，s_x≤2048 为 sparse-selected token 数；h 根据 offline selection profile 估计其中落 HBM 的部分，剩余由 HBF 服务。

12.8 Toy Example

Research agent A 有40k context，刚发浏览器工具；B 正 decode；C 新到。无 buffer 时 C 被 admission，把 idle A 的 KV 挤走；20秒后 A 返回，系统重新搬运/计算。b=.9 时 C 暂缓，A prefix 留在 device tier，回来直接 hit。代价是 C 等待增加，所以这套方法优化的是固定 workload completion，不是每个 request 的最低 latency。

  • New Empirical Finding：HBF 收益高度依赖 workload/placement/scheduler，错误配置可负收益。
  • New Protocol：completion、TPOT、energy、writes、lifetime 同时评。

21 Limitations

high-throughput only；无 production controller、完整 power、wear leveling；kernel fits 限制跨硬件外推；固定 workload 不等价 online SLO；最优 b 会随 arrival/tool-gap 变化；HBF 器件参数变化可能改变排序；TPOT 恶化可能伤交互体验；没有与 speculative decoding 联合。

22 Reproduction View

先做 Qwen3-32B 25k-turn Table4：实现 request state machine、prefix cache、HBM/HBF/host capacity、FCFS/cache-aware/buffered admission。第一 sanity check 是 b=.9 应显著降低 HBF writes 并提高 future prefix hit；否则 active-lock/completed-session eviction 建模错。第二步再做 Llama 验证 completion-vs-TPOT。敏感参数：b、tier bandwidth/energy、tool gap、context length。

23 Research Value

Baseline 高；Migration 极高；Systems 极高；Attack 高；Evaluation 极高；Benchmark 高；New Paper 极高。最有价值的新论文方向是 dynamic buffer + future-reuse prediction + speculative decode 联合控制。

26 Attack / Verification Lens

可构造 cache-thrashing adversarial trace：大量巨大 prefix 的短 turn 在 eviction 后立即返回，最大化 victim recomputation/HBF writes；定义 Efficiency Amplification Factor = attacker 新增 token / 系统额外 memory traffic。还可定义 Endurance Robustness：不同 burst/return-gap 下 lifetime 的最坏分位数。

28 只记住 10 句

  1. Agent memory 问题是长 context 在工具等待后反复回来。
  2. HBF 容量本身不保证收益。
  3. 最关键机制是 buffered cache-aware scheduling。
  4. 10% buffer 把 Qwen HBF writes 21.81→6.69TB。
  5. 对应 lifetime 4.77→14.82年。
  6. 错误 HBF+FCFS 可比 HBM-only 更慢更耗能。
  7. 长 context 越重，capacity value 越大；GLM5×最快约-87% completion。
  8. 吞吐改善可牺牲 TPOT，Llama 是强反例。
  9. weights 不应机械搬 HBF。
  10. 它与 AgSpec 的统一点是“预测未来 session reuse”。

7–10. Cross-Paper Synthesis / Opportunities / Collision / Priority

两篇共同说明：Agent inference 的优化单位正在从孤立 request 上移到 session / trajectory。 AgSpec 用 session/role/turn 预测 token continuation reuse；HBF 用 session return/locality 决定 prefix/KV 是否值得保留。两者其实都在估计同一个潜变量——future reuse，只是一个作用于 decode，一个作用于 memory/scheduling。

Strongest Collision：AgSpec 没把 role/turn reuse signal 用到 KV；HBF 论文明确使用普通 autoregressive decoding，没有 speculative decoding。简单叠加也未必最优，因为 HBF admission 会改变 batch occupancy，进而改变 AgSpec 的 verification marginal cost λ。真正的新方法应联合控制 draft K、KV tier、admission b，而不是两个开关一起打开。

Combined Research Opportunity

最值得做的是 Unified Agent Reuse Control Plane：输入 role、turn、tool type、match statistics、return-gap、prefix-hit history；输出 speculative K、KV retention priority、memory tier 与 admission headroom。先用规则/online bandit 就能做最小实验，不必上复杂 RL。

Reading / Reproduction Priority

  1. 先复现 AgSpec Fig.7：最快验证 adaptive draft controller。
  2. 再复现 HBF Table4：验证 buffer→hit/write/lifetime 机制。
  3. 最后做 joint prototype：用 vLLM prefix cache + CPU/HBM tier 模拟 HBF pressure，把 α/K 与 dynamic b 联动。
