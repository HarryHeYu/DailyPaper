PAPER 01 · FRESH · INFERENCE SYSTEM

TokenRouter

Efficient Serving System for Token-Level LLM Routing · arXiv 2610.12242 · NeurIPS 2026 Accepted

01 · 基本信息 · 定位 · 人话版

Title：TokenRouter: Efficient Serving System for Token-Level LLM Routing。Authors：Tianyu Fu、Tengxuan Liu、Ruoxi Wang、Yixin Dong、Yi Ge、Yichen You、Yu Wang。日期：2026-10-08 首次提交 arXiv（v1）。状态：arXiv 预印本；arXiv 明确标注 Accepted by NeurIPS 2026，官方仓库亦确认录用。机构：论文及仓库指向清华大学相关团队，作者与机构的逐人对应以论文首页为准。论文：HTML 全文 / arXiv；代码：thu-nics/TokenRouter（已公开）；项目：Project Page。

一句话定位：它不是发明一个更聪明的 token router，而是把「小模型与大模型逐 token 接力」从难以高效部署的算法演示，变成可连续批处理、可跨模型恢复状态的实际 serving 系统。

人话版（核心逻辑）

想象你让一个小模型解数学题：简单词由小模型生成，遇到困难的推理节点就请大模型接管一两个 token，然后再交还小模型。纸面上很省计算，但工程上会不断切换模型，原来的推理服务器通常假设一个请求只由一个模型连续处理，于是每次切换都要重新进入队列、做前缀匹配、维护 KV Cache；如果所有模型按统一步长同步，更快的小模型还得等更慢的大模型。结果是算法看起来省了 FLOPs，实际吞吐反而很糟。

TokenRouter 的解法分三层：用 route/send/receive 把路由语义写成请求视角的简单接口；为每个模型运行独立子服务器，用第三条跨模型消息循环和 pending 状态完成无须重建本地缓存的 handoff/resume；再让大模型适当等一等，凑齐更多请求后批量执行。作者在五类路由算法、不同长度与并发工作负载中报告相对可用较强系统基线 2.01–64.15 倍的解码吞吐提升。真正值得记住的是：细粒度算法的系统收益，常常取决于状态能否保留与调度能否适应不规则到达，而不只是模型每 token 算了多少。

02 · Background & Research Gap

现实问题。企业服务有成千上万条请求：一些只需要 0.6B 模型，另一些需要 32B 的深度推理。如果整条请求都交给一个模型，query-level routing 虽简单，却无法让一个请求内部的「简单 token」和「难 token」分别获得合适算力。Token-level routing 理论上能做得更细，但其控制流不再是一条请求绑定一个 worker 的常规自回归循环。

旧范式一：整请求路由。RouteLLM 一类方法在请求开始时选一次模型。优点是缓存与 batching 都容易管理，缺点是对一条长推理中的局部难点无能为力。例如一道数学题的前 500 个 token 只是抄写条件，真正关键的第 501 个 token 决定分情况讨论，query router 只能全程付大模型价格或全程冒小模型错误风险。

旧范式二：算法原型直接驱动多个引擎。R2R、CITER、Co-LLM、R-Stitch 等会在生成中途切换模型。最朴素实现是在外部 Python dispatcher 中逐 token 调两个服务：请求每回来一次就被当作新请求。对于单次推理耗时几毫秒的小模型，这个 dispatcher 的前缀匹配、缓存锁和重建开销可能远大于一次真正的神经网络计算。

旧范式三：共享 step barrier。若一个 batch 中有请求在小模型、另一些在大模型，强行要求它们按同一 logical step 前进，就把整批吞吐绑在慢模型上。改为两个模型各跑各的还不够：大模型接到的 token 到达不均匀，频繁小 batch 使算力利用率低。本文填的 gap 是为不规则跨模型流动建立一套可复用的 serving 抽象、可恢复状态机和有吞吐依据的 batching 规则。

具体例子。三条请求分别在第 20、21、24 个 token 遇到困难。立即逐条唤醒 32B 模型，可能形成三个近乎空载的 decode step；稍等第三条到来后一起处理，会增加第一条的等待，却减少总体 GPU step 数。是否值得等，不应靠直觉固定 5ms，而要根据并发量、模型速度和路由概率估算。

03 · Core Insight：两个瓶颈不是同一个问题

观察 A：step desynchronization。token 级切换破坏了单模型连续执行的前提。不同模型的 decode 速度、输入前缀长度与请求到达时刻不同，因此不能用一条全局时钟驱动所有请求。作者通过 Figure 4 的同步/异步调度示意给出工程层面解释：同步浪费等待时间；异步则暴露下一种瓶颈。

观察 B：batch admission delay。即使子服务器独立运行，请求也会在目标模型执行中途抵达，错过正在运行的 batch，只能等下一个 step。更糟糕的是：如果模型每收到一条请求就立即启动小 batch，后到请求会反复错过批次。作者反直觉地提出「主动等待一小段时间」反而能降低平均入批延迟，并提高系统 throughput。

观察 C：每次交接丢状态比一次前向还贵。附录 Table 10 在 Std. Serving 的 SLM 侧测到 prefix matching 7.78ms、RadixCache update 12.12ms，而 SLM inference 仅 1.56ms。它说明优化真正应该瞄准重复控制与缓存管理，不是继续减少一点 attention FLOPs。

证据性质。这些是系统 trace 与 profile 驱动的工程观察，离散时间马尔可夫链提供在明确假设下的吞吐模型；它并不等于证明任意实际到达过程都应使用相同阈值。创新点不是「有路由」或「有 batching」，而是把跨模型状态恢复、独立事件循环、阈值选择联合起来。

机制判定：TokenRouter 主要属于 New System / Engineering，其 delayed-batching 的 DTMC 优化属于有分析模型支持的调度机制；不要把 64.15× 误读为同一模型少算了 64.15 倍 FLOPs。

04 · Method Deep Dive：从请求到输出

全链路

Input（prompt, route policy, model set） → entry subserver → decode → route() → send() → peer receive() → peer decode → handoff/resume → delayed batching → Output

Step 1｜请求视角的 route/send/receive

开发者只实现三个语义钩子。route(result) 看当前 logits、entropy 或 learned deferral score，决定留在当前模型还是交给某个 peer；send(req) 决定携带哪些 token、哪些已在 peer 的缓存里，不一定把整段历史重新发送；receive(msg) 决定是否接受 peer 的 token、是否需要回滚或重算。一个算法是否需要重训 router 与 TokenRouter serving runtime 是否要重训，是两件事。

R-Stitch 例子最直观：小模型算出归一化 entropy，超过阈值就把「刚刚产生但不确定的 token」从消息中排除，让大模型在同一前缀上重新生成；大模型侧在低 entropy 时交还小模型。若 send 错把不确定 token 当成已确认 token，模型间会产生语义漂移；若 receive 错误拼接，会造成重复或遗漏。

Step 2｜模型中心的独立子服务器

每个模型持有自己的 scheduler、runner、KV-cache pool；前端只暴露一个兼容常见 chat completion 的入口。一个子服务器有 client-server loop（接请求、发流）、decode loop（形成 batch 并前向）、inter-model loop（跨模型发送/接收 peer 消息）。第三条循环是关键：一条请求转交后，原模型仍可继续服务别的请求，不再被跨模型 RPC 阻塞。

每个模型本地 KV 是按其自身权重计算的，不能直接把小模型 KV 当成大模型 KV。交接传的是 token/context 与缓存位置标记；目标模型仍需补齐自己尚未编码的前缀。本文的「保留 KV」主要指原模型在请求回来时不用把自己的本地 KV 重建，绝不是异构模型 KV 无损共享。

Step 3｜pending 状态与 handoff-resume

常规请求只有 running/finished 两态；作者加入 pending。交接时把请求从本地 decode 候选中暂时移走，但保留其请求对象、已算 KV、prefix anchor 与调度元数据。peer 返回时根据消息将 pending 改为 running 或 finished，追加新 token 并恢复调度。

为什么这比外部 dispatcher 强？因为请求没有经历完整「新建→查找前缀→申请缓存→构造 extend」路径。主要风险是乱序消息、重复交接、错误的缓存 anchor 或并发取消；这些需要状态机断言和序列号保护，属于复现时应补的 correctness tests。

Step 4｜延迟批处理与阈值选择

对于每个子服务器 i，维护待运行队列长度 kᵢ，只有达到阈值 Bᵢ 才启动新 batch。B=1 就是 eager-async；B 太大则请求排队甚至饥饿。系统根据并发 N、每模型 decode step 时延 Lᵢ、转移概率 pᵢⱼ、一次转移确认的 token 数 cᵢⱼ，求最大吞吐的阈值组合。

这里优化的是系统提交 token 数 / 总运行时间，而不是单个请求 TTFT 或 P99 latency。因此上线时应附加延迟 SLO 约束，不能直接把离线吞吐最优 B 当作所有产品场景的默认值。

Step 5｜额外工程栈

附录还做了 shared GPU KV 容量联合分配、extend-mode CUDA graph capture、in-process router、跨子服务器并发数同步。尤其 extend CUDA graph 不是小细节：token 路由会频繁以「补上 peer 返回 token」形式进入 extend，而传统 serving 主要优化 decode 的 CUDA graph。该栈和调度收益必须分开计量，否则会把通用工程改造误当成新的路由理论。

05 · 核心公式与数学直觉

1｜路由矩阵与请求状态

P = [pᵢⱼ], Σⱼ pᵢⱼ = 1； C = [cᵢⱼ]； B = (B₀,…,Bₘ₋₁)； s = (k₀,b₀,r₀,…,kₘ₋₁,bₘ₋₁,rₘ₋₁)

pᵢⱼ 是模型 i 一步完成后切到 j 的概率；cᵢⱼ 是这次转移实际确认的输出 token 数；Bᵢ 是模型 i 的 batch 启动门槛；kᵢ 是等待数，bᵢ 是正在执行的 batch 数，rᵢ 是剩余计算时间。这里状态不是 LLM 的语义 state，而是服务系统的排队状态。作者假定转移概率在分析窗口内近似平稳、请求间独立，单模型连续步数因而近似几何分布。

2｜Markov 模型为何可算

Lᵢ = dᵢ · δ； πᴮ = (Tᴮ)ᵀ πᴮ； Σₛ πᴮ(s)=1

把各模型 step 时间 Lᵢ 离散成共同时间量子 δ 的整数倍，就能把「谁先完成一个 batch」视作状态跳转。Tᴮ 是给定阈值向量 B 的转移矩阵，πᴮ 是稳态概率。不是说真实 GPU 时延完全离散或转移独立，而是为了可枚举与预测，使用有边界的系统近似。δ 变小可减小量化误差，但状态空间膨胀。

3｜真正的目标函数

T(B) = [ Σₛ πᴮ(s) Σᵢ∈A(s) Σⱼ bᵢ cᵢⱼ pᵢⱼ ] / [ Σₛ πᴮ(s) τ(s) ]； B* = argmax_B T(B)

分子是每次状态转移期望确认的 token，分母是期望耗时；最大化 T(B) 就是在稳态下提高总 token/s。它不同于只优化 router 的 accuracy–cost 目标，也不同于 SGLang 的默认 continuous batching：后者不显式建模请求在多个异速模型之间反复迁移。可行性条件 Σᵢ(Bᵢ−1)<N 防止所有子服务器都因凑不齐阈值而死锁。

4｜一个路由信号的公式

H(p) = −Σᵥ p(v)log p(v) / log|V|； route_to_LLM = 1[H(p)>τ]

R-Stitch 的归一化 entropy 越高表示分布越不确定；阈值 τ 下降会更频繁调用大模型，可能提高正确率也会增加切换与成本；τ 上升则相反。这里的 entropy 是路由策略本身的旧算法，不是 TokenRouter 新提出的 objective。需要区分「router quality」与「serving efficiency」两层。

06 · Toy Example：三条数学请求的接力

设模型 S 是 0.6B、每 step 6ms；模型 L 是 32B、每 step 27.9ms。三条并发请求 A、B、C 在小模型的第 20、21、24 个 token 分别触发高 entropy。假设 S 对 A 生成了可疑的「因此」，route 决定交给 L，send 丢掉这个尚未确认的 token，并只发送 L 尚未见过的后缀。S 将 A 标记 pending；B、C 仍可在 S 上继续。

在 B=1 的 eager 策略下，A 到达 L 立即开始 27.9ms step；B、C 在其运行中途到达，只能等下一批，可能连续产生两个小 batch。把 L 的门槛设为 B=2 后，A 稍等 B，一次处理 A+B；C 是否与下一轮同批取决于到达时间。假设两个 L step 因合批减少为一个，那么省掉的是重复 batch 启动与入批等待，并非 L 的某个 attention 头突然少算了一半。

当 L 返回替换 token 后，A 在 S 侧从 pending 恢复，S 继续使用原本保留的本地 KV，加上从 L 接收的新 token 完成必要的本地增量计算。若 L 返回顺序与原 token 边界不一致，系统必须先修正 token 序列与缓存位置；否则下一步的条件分布就是错的。

这一例的 6ms/27.9ms 来自论文附录 R2R profile；三条请求与事件顺序是教学构造，不是作者实际测得的单次 trace。它说明同一条请求会在多个模型之间移动，但真正持续存在的是 request state，而不是某个模型独占的 execution loop。

11 · Ablation / Mechanistic Analysis

去掉 delayed batching：N=8 从 372.48 降到 296.86 token/s，约下降 20.3%；说明在有足够并发且 token 切换频繁时，主动聚合可改善平均批效率。N=1 从 73.02 到 73.02，说明并发是必要条件。去掉 async：296.86→230.79，约下降 22.3%；证明模型独立进度而非全局同步的重要性。

12 · Claim vs Evidence · Contribution · Limitation

Authors Claim

TokenRouter 让多种 token-level routing 算法易于实现且高效部署，显著提高解码吞吐，并把原本算法层面的 accuracy–cost 优势转化为 serving 层面的 throughput–accuracy 优势。

Experiments Actually Show

在 8×A100、指定路由模型与三个工作负载下，它比原实现及 SGLang dispatcher 基线快；pending-resume 减少重复前缀工作；async 与 delayed batching 都有可观消融收益；基于平稳转移概率的 DTMC 在所测 R2R 场景预测了最优阈值。

What Is Not Yet Proven

尚未证明所有动态路由分布都符合几何停留假设；没有完整生产 P99/energy/多租户隔离与故障恢复数据；没有展示对任意 VLM、视频模型或 MoE 的等幅加速；也没有证明路由本身的推理正确率因 TokenRouter 改善。

Contribution 标签与创新判断

Contribution 1 [New System / Engineering]：request-centric route/send/receive API，把算法逻辑与服务系统解耦，属于新的系统抽象而非新的语言模型 objective。Contribution 2 [New Mechanism / System]：tri-loop + pending handoff-resume，在跨模型 token 接力中保留本地 serving state；状态机组合是关键创新。Contribution 3 [New Scheduling Mechanism]：delayed batching 与 DTMC 阈值优化，创新在于面向不规则模型迁移的吞吐分析；Markov 建模与 batching 本身是已有工具。Contribution 4 [New Empirical Finding]：证明常见 token-routing 的原型系统 overhead 可能主导延迟。

Authors' Limitation

作者明确承认数学模型假设两次发送之间的 token 数服从几何分布，对违反该假设的边角情况尚未处理。

Additional Limitation

跨模型频繁补前缀会重复 prefill；若路由策略极端高频切换，异构 KV 不可直接复用可能吞噬收益。队列门槛可能伤害低并发与尾延迟；缺少动态负载漂移与 bursty arrival 下的在线重调阈值。CUDA MPS、CUDA graph 与特定 SGLang 版本构成硬件/软件依赖；系统能跑并不代表跨 tokenizer、异构位置编码与结构差异能无缝共享 token。若用训练得到的 router，还需独立审计其质量与分布外鲁棒性。

02 · Background & Research Gap：为什么静态 Judge 不够

现实问题。一辆车在雨夜绕开路边障碍，文本 reasoning 可能非常流畅，但最终轨迹依然擦到障碍；反过来，一段简短但正确的安全判断可能被偏好长解释的 LLM judge 打低分。Agent 优化目标是安全决策与可解释推理，而不是只获得漂亮的语言评分。

旧范式一：固定人工标注。可靠却昂贵，随着 policy 变化需要不断覆盖新的失败模式。旧范式二：固定 reference-based judge。依赖参考答案或高质量示范，可控但对开放式、多解的具身任务不灵活。旧范式三：reference-free LLM-as-a-judge。能够按 rubric 评价没有唯一标准答案的行为，但它本身有偏见，可能对新型错误不敏感。

旧范式四：仅优化 policy。每一轮继续用旧 judge 给 GRPO reward，训练数据也从旧分布随机抽样。这相当于在不断变化的环境里坚持使用一把旧尺子；模型越会迎合尺子，尺子越不可靠。

Gap。如何在 policy 自我改进过程中同时改进评价器，并避免使用同一个不断变化的 judge 来证明自己越来越好？作者引入固定的 reference-based anchor evaluation、动态 reference-free judge、失败导向 curriculum、少量人类 coactive calibration。与普通「多训练一个 reward model」相比，真正值得关注的是评价器何时应更新、更新数据从哪里来、如何监测更新是否与真实任务对齐。

03 · Core Insight：优化目标与评估标准必须解耦

观察 A：policy 与 judge 的能力边界会共同移动。新 policy 不再犯旧错误，却会暴露过去少见的边界情形。如果 judge 的训练数据只包含旧策略的输出，它对新错误缺乏辨别力；只把 judge 当成不变的 reward oracle 会让优化逐渐偏离真实能力。

观察 B：curriculum selection 与 reward supervision 是两个可分开的杠杆。judge 既可以决定「哪些样本值得训练」，也可以决定「这些样本训练时得到什么奖励」。Table 2 固定 reward judge，只改变 curriculum，仍有明显增益；说明不应把全部改进都归功于 reward 数值本身。

观察 C：锚定评估是对抗自我证实的必要条件。若 judge 在每轮都更新，用它给 policy 打分再报告分数升高，会出现评价尺度漂移。作者用独立、固定的人类标注 reference-based evaluator 追踪策略，并比较动态 judge reward 与 anchor performance 的变化。

观察 D：校准不是简单地让人给一批最终答案打分。人类与 Agent 共同检查分歧，允许修正 rubric 维度、评价解释，甚至修订不合理的人类旧标注。累计保留正例和负例，使新 judge 既学习新失败，也尽量不忘旧边界。

04 · Method Deep Dive：两个循环怎样咬合

全链路

Input（policy πₜ, data pool, judge Jₜ） → rollout & failure mining → judge-guided curriculum → GRPO/SFT policy update → anchor evaluation → stagnation/gap trigger → human-agent rubric calibration → judge distillation → πₜ₊₁,Jₜ₊₁

Step 1｜构造独立的 policy 评估锚点

从人工质检数据中固定 anchor set P，与动态训练集和 judge calibration set 分离。作者在驾驶任务中给出 2,134 条 anchor policy evaluation、2,772 条独立 policy test；judge 校准使用不同的 selected scenarios。锚点不是每轮随 judge 改写的分数表，否则无法区分 policy 真的进步还是尺子变松。

Step 2｜Policy Improvement Loop：挑数据、给奖励、更新策略

当前 policy 在候选情景上生成 driving reasoning 或轨迹；reference-free judge 按 rubric 输出多维诊断与总分。根据 judge 找出高价值训练样本，构成 curriculum Dₜ。驾驶 policy 使用 GRPO，以 judge 总分为 reward；导航任务使用 SFT，judge 主要负责选出高质量示范，而非直接对每个 token 给 RL reward。两种优化目标不能混为一谈。

Step 3｜监控是否出现「分数涨、能力不涨」

计算固定 anchor 上的 policy 变化 ΔPₜ，以及动态 judge score 变化 ΔRₜ。若若干轮平均 policy 进步接近零，或两种变化差距 Gₜ 很大，说明当前 verifier 可能已成为瓶颈。触发阈值与检查频率由附录定义；在没有逐项读到阈值前，不能编造一个「0.05」当作作者设定。

Step 4｜构造最有信息量的争议样本

从新 policy的 rollout 中抽取 judge 不确定、评分不一致或影响很大的案例，形成 Hₜ。必须保留正例与负例：只收低分案例会让 judge 学会一味挑错，只收高分会让它失去错误边界。再与此前累计样本 Jₜ₋₁ 合并，构成 Jₜ，减轻对旧错误模式的遗忘。

Step 5｜Coactive calibration 与 teacher→student

专家先基于物理场景与候选动作给出粗校准；Agent 自动提出 rubric 修改、用争议案例比较修改效果；当双方仍不一致时，人类重新检查具体维度并确认或修订。作者使用 Claude Opus 5 作为 rubric teacher，再将评估能力蒸馏到 Qwen3-VL 2B 的 student judge；student 采用适配物理世界的视觉预训练和分类式 rubric subscore 预测。

Step 6｜闭环而非一次性再训练

05 · 核心公式与数学直觉：Reward、KL、触发器

Policy 优化的抽象

max_θ Eₓ Eᵧ~πθ(·|x)[R_Jₜ(x,y)] − β · KL(πθ || πref)

x 是视频/环境上下文，y 是 policy 输出的 reasoning 或行动，R_Jₜ 是当前 judge 的 reward，πref 是参考策略，β 控制偏离程度。增大 β 使更新保守，减小 β 可提高探索但更容易利用 judge 漏洞。本文驾驶实验使用 GRPO；此式是论文策略目标的抽象表达，具体 group advantage、ratio 与优化实现应以作者方法公式为准，不能擅自等同 PPO 的完整 clipped objective。

导航场景的 SFT 目标

L_SFT(θ) = − E_(x,y*)~Dₜ [ log πθ(y*|x) ]

y* 是 judge 选择的高价值/高质量目标数据，Dₜ 是本轮 curriculum。这里 judge 不直接成为可微损失项，而是决定哪些训练样本进入集合。最小化负对数似然使 policy 更倾向产生 y*。如果 Dₜ 只包含简单示范，loss 也许下降得很快，但对长尾困难任务没有帮助。

ΔPₜ=Pₜ−Pₜ₋₁； meanΔPₜ=(1/K)Σₖ₌₀ᴷ⁻¹ΔPₜ₋ₖ； Gₜ=|ΔR_judgeₜ−ΔPₜ|

06 · Toy Example：一次「假进步」如何触发 Judge 改进

设自动驾驶 Agent 的第 0 轮在 100 个固定锚定场景上获得 60 分，当前 judge 的平均分为 68。第 1 轮经过 GRPO 后，judge 平均分升到 75，但 anchor 只升到 61；第 2 轮 judge 再升到 80，anchor 仍为 61。假设 K=2，则最近两轮平均 anchor 增幅仅 (1+0)/2=0.5，而 judge 分数与 anchor 的变化差距在第二轮达到 |5−0|=5。

12 · Claim vs Evidence · Contribution · Limitation

Authors Claim

通过 policy、curriculum 与 judge 共同演化，持续提高具身推理能力；人类–Agent 协同校准能够改善 verification，进而支持 GRPO 与 SFT 两种 policy 优化方式。

驾驶任务三轮后 RB/RF reasoning score 提升，ADE/minADE₆ 小幅改善；固定 reward judge 的 curriculum 消融有稳定正收益；teacher rubric 校准与 student judge 结构有对齐/效率分析；导航任务有跨优化范式的定性与实验支持。

16 · 方向专用：RL / Agent / Attack Lens

RL Formulation

State：多视角视频、场景描述、历史轨迹与当前 policy；Action：驾驶推理或导航动作；Policy：Alpamayo 1.5 8B driving model；Trajectory：多视角观测、预测轨迹与推理文本；Reward：reference-free judge rubric score；Advantage：GRPO 的组内相对 reward；Objective：GRPO policy update，导航则为 SFT；KL：用于限制策略偏移；Credit Assignment：仍主要依赖轨迹级 judge reward，VeriFine 的核心不是发明 token-level credit assignment。

Reward Analysis / Efficiency

reward 主要来自 learned judge 而非每条轨迹都能用规则验证；多维 rubric 有助于解释，但也可能被策略迎合。human coactive calibration 能纠正部分偏差，却引入人工成本。文中给出 2,700 steps/25K samples 的受控 policy 比较，但未核实完整 rollout tokens、每轮 GPU-hours、训练 wall-clock 与 judge 总调用成本；这些应标为 Not Reported，不能从 2M clips 推断实际训练成本。

Agent State / Long Horizon / Failure Propagation

架构为 Video/Environment → Policy → Trajectory/Reasoning → Judge → Curriculum/Reward → Policy Update → Anchor Check → Judge Update。Agent state 包括场景观测、轨迹与失败记录；judge state 包括 rubric 版本、累计校准集与 teacher/student 模型版本。若一次 judge 把危险轨迹评高，错误会经 reward 进入 policy，下一轮产生更多相似危险样本，形成反馈放大；若 anchor/test 泄漏进校准，又会制造看似进步的假象。

Attack / Verification Lens

设计 JudgeGapBench：生成文本解释流畅但物理轨迹错误的对抗场景，检查 RB/RF score 与 minADE/ADE 是否分离；设计 RubricDrift：每轮引入一种新失败类型，测试 evolving judge 对旧失败的遗忘与新失败的识别。可定义 Reward–Ability Gap = normalized Δjudge_reward − normalized Δanchor_success、Judge Forgetting = max_past_alignment − current_alignment_on_old_cases；这是研究提案，不是原论文指标。

Combined Research Opportunities｜两条组合实验

Idea 1｜Calibrated, Quality-Aware Token Routing

新问题：现有 token router 多以 entropy/uncertainty 决定调用大模型，但 entropy 高不一定意味着错误，低 entropy 也可能自信地错。把 VeriFine 的可校准 judge 当成更接近真实任务能力的反馈，能否学习一个在 accuracy、throughput、TTFT 之间更稳健的 router？

Minimum Experiment：选择 200 条可验证数学或代码任务，固定 0.6B/8B 模型与相同采样种子，构造 4 个 routing：always-small、entropy threshold、uncalibrated learned judge、calibrated rubric judge。用 100 条 train / 50 条 anchor / 50 条 test 分离；每个任务记录路由次数、每次模型切换、输出 token、wall-clock、hidden-test correctness、judge score 与 P95 latency。把 judge 推理开销计入总成本。只有当真实 task success/second 上升而非单纯 judge score 上升时才认定有效。

Idea 2｜Verifier Drift Under Adaptive Compute

新问题：动态路由策略可能逐渐学会只在 judge 敏感的 token 上调用大模型，制造「judge 认为更好，但真实质量没有提升」的 reward hacking。建立固定 anchor 的路由–验证闭环，测 reward–ability gap 随训练轮数变化。

Minimum Experiment：固定 3 轮策略更新，每轮相同训练预算与任务划分；对照 frozen judge、evolving judge、evolving judge + fixed-anchor trigger。记录每轮准确率、judge MAE、router big-model token fraction、token/s、GPU-hours 与 P99。再用 SwitchStorm 对抗输入检查缓存正确性和 verifier 漏洞是否耦合。

最值得借用的实验范式：TokenRouter 的逐组件性能消融 + VeriFine 的固定 reward judge 选样消融。若只比较端到端最终分数，无法区分「服务优化」「router 训练」「judge 变准」「数据选得好」四种效应。

Collision / Overlap｜真正的研究张力

最强 Collision：「用模型不确定性分配计算」与「用独立验证器衡量真实能力」之间的冲突。entropy router 可以很快，却可能把高置信错误留给小模型；learned judge router 可以更精确，却可能自身昂贵或被 policy 钻空子。问题不是简单地把两个系统拼起来，而是能否证明校准后的质量信号在真实 wall-clock、batch-size scaling、分布外输入下仍值得它的计算成本。

Novelty 边界：continuous batching、multi-model routing、rubric judge、RLHF/GRPO、evolving verifier 均已有研究。只有提出新的跨层指标、可验证的路由–评价因果机制、独立测试集上的优势，或一个真实系统 benchmark，才可能成为独立论文。今天两篇之间不存在已证实的直接文献冲突，因此 Collision 指的是机制张力与新研究问题，不是作者互相否定。
